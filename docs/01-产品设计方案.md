# 远程算力工作台 · 桌面客户端设计方案

> 定位：一个运行在本地 Windows 上的图形化客户端，用桌面隐喻管理远程 HPC 上的文件、显卡和任务。
> 手册只作为"通信协议"和"平台约束"的输入，不作为产品形态的蓝本。

---

## 0. 一句话定位

**把「SSH + 一堆记不住的命令」包装成「一个能拖文件、能租显卡、能看到东西在哪跑」的桌面应用。**

它不是 HPC 的管理后台（那是网管的事），也不是实验室的内部平台。它是**单个研究者的个人工作台**——面向"我要把数据传上去、跑个实验、把结果拿下来"这条日常链路。

---

## 1. 设计原则

这五条会贯穿后面所有取舍，先立在这里。

**① 操作必须可解释。**
每个图形操作旁边都显示它等价的那行命令（可折叠）。用户点"租 2 张 A100 跑 4 小时"，界面角落写着"等价于 `srun --gres=...`"。
理由：目标用户是从命令行迁移过来的，信任建立在"我知道它干了什么"上；同时这是最好的学习路径。不做黑盒。

**② 默认安全，危险操作要"贵"。**
删除、覆盖、递归改权限都不设一键快捷入口。危险按钮不是默认焦点，确认文案写清后果（"将删除 12,847 个文件，无法恢复"）。

**③ 桌面隐喻服务于效率，不服务于拟真。**
不做 Windows 复刻。图标、拖拽、右键、任务栏这些**直觉**要保留；但"每个功能一个可拖动窗口"是负担——用户同时只干三件事。详见 §2 决策二。

**④ 慢操作必须可中断、可观察。**
任何超过 2 秒的动作（上传、提交、查询）都有进度、可取消、失败有原因。不出现转圈然后失败。

**⑤ 不做平台规则之外的事。**
不提供"保活脚本""自动抢卡""刷点数"这类功能。反过来，要提供"空闲自动释放"——因为手册里明确写了有人用 sleep 占资源，这是被点名的问题行为。工具应该缓解它，不是放大它。

---

## 2. 三个关键决策

这三个决定了后面 80% 的成本，先说清楚，也说明被否掉的方案。

### 决策一：本地客户端，不是浏览器应用

**选择：原生桌面客户端（Electron），SSH 是唯一通道。**

被否方案：部署在 HPC 上的 Web 应用，浏览器访问。

否决理由（按严重程度）：

| 问题 | 说明 |
|---|---|
| 拖拽失效 | 浏览器里"拖本地文件到网页"本质是上传到 Web 服务，需要服务端接收。要支持大文件、断点续传、目录拖拽，等于自己重写一个上传服务 |
| 无处常驻 | 服务端进程要么跑在跳板机（手册明令禁止大负载），要么占一个作业位（等于为了用工具先花点数） |
| 访问本身要 CLI | 打开网页得先 `ssh -L` 端口转发。为了不用命令行，先用命令行——逻辑闭环不成立 |
| 内网穿透被禁 | 手册明确禁止内网穿透工具，没有别的暴露方式 |

反过来，本地客户端天然解决拖拽（能拿到真实文件路径）、能常驻、能存密钥、能弹系统通知。

**代价**：需要分发安装包，需要处理密钥存储和跨平台差异。这个代价是值得付的。

### 决策二：桌面是"启动器"，不是"容器"

**选择：混合形态——桌面层做入口，功能区用全屏布局，只有工具类用浮动窗口。**

被否方案：完整窗口管理器（每个功能一个可拖动、可缩放、可最小化的窗口）。

理由：真正的窗口管理是隐藏的成本黑洞——层级栈、焦点管理、拖拽、八向缩放、贴边吸附、多显示器、最小化动画。做完要几周，而用户 90% 的时间只在三个界面之间切换：**文件、显卡、状态**。

折中方案（这是核心）：

- **桌面层**：壁纸 + 图标网格 + 右键菜单。承担"我该干什么"的引导。双击图标打开对应功能区。
- **功能区**：全屏分区布局（类似 IDE），左侧导航，右侧主区。切换用标签，不用窗口。
- **工具类**：终端、实时日志、GPU 监控、传输队列——这些**用浮动窗口**，因为需要和主区并排看。

这样既保留了"桌面"的直觉（图标、拖拽、右键、任务栏），又避免了窗口管理的成本。用户感受到的是"桌面应用"，不是"网页"。

### 决策三：所有远程数据靠 CLI 适配层，且必须可降级

**选择：为每种数据源写一个 Adapter，输出统一的结构化对象；Adapter 解析失败时降级到"显示原始输出"。**

这是整个项目最大的技术风险，必须前置设计。

HPC 没有 REST API、没有 gRPC、没有数据库直连权限。能拿到的只有：

| 数据 | 来源 | 稳定性 |
|---|---|---|
| 集群状态 | `sinfo -N -o "自定义格式"` | 中（自定义格式可控，但字段可能变） |
| 作业队列 | `squeue` 或 `squeue --json` | 中高（新版 SLURM 支持 JSON） |
| 作业历史 | `sacct --json` | 中高 |
| 点数额度 | `scir-account` | **低**（自定义工具，无稳定输出约定） |
| GPU 单价与空闲 | `scir-watch -s` | **低**（同上） |
| 存储配额 | `mmlsquota` | 中（GPFS 标准工具，格式相对固定） |
| 文件系统 | SFTP `readdir` | 高（协议标准） |

设计对策：

1. **Adapter 接口固定，实现可替换**。每个 Adapter 声明 `parse(raw) -> Model`，并保留 `raw` 原文。
2. **解析用"宽松匹配 + 必填校验"**。不假设列位置，用正则抓关键 token；关键字段缺失就判定失败，不猜。
3. **失败可见**。界面上出现"数据可能过期/无法解析，查看原始输出"，而不是静默显示空列表。**静默失败是这类工具最恶劣的 bug**——用户会以为集群空了。
4. **可手动覆盖**。GPU 价格表允许用户手工填一份本地缓存，Adapter 挂了也能估算费用。
5. **版本指纹**。记录首次成功的解析样本，集群升级后输出变化时能快速定位差异。

## 3. 核心功能模块

六个模块。标 ★ 的是 MVP 必须有的。

### 3.1 ★ 连接中心

职责：管理"我能连到哪台机器"。

- 连接配置：主机、端口、用户名、密钥、跳板机（ProxyJump 语义）
- 首启动向导：检测本地是否有 `~/.ssh/id_rsa`，没有则引导生成 + 显示公钥文本（方便贴进申请邮件）
- 密钥管理：导入 / 生成 / 查看指纹，**私钥只存系统钥匙串，不进配置文件**
- 连接状态：已连接 / 重连中 / 断线（带原因）
- 会话保活：心跳间隔可配（对应 `ServerAliveInterval`）
- 多账号：一个用户可能有多台集群或旧账号

边界：不做账号申请流程（那是邮件和人的事），但如果检测到没有权限，提示应该找谁。

### 3.2 ★★ 文件管理器

职责：本地 ↔ 远程的文件搬运与整理。这是最高频、最刚需的模块，也是最能体现"桌面体验"的地方。

**布局**：双栏对照（左本地、右远程），可切换单栏聚焦。地址栏支持路径直达、面包屑、书签（常用位置：数据集目录、模型目录、实验输出目录）。

**拖拽语义**（关键设计，四种方向四种处理）：

| 拖拽方向 | 实际动作 | 关键点 |
|---|---|---|
| 本地 → 远程 | 上传 | 并发队列、断点续传、冲突检测 |
| 远程 → 本地 | 下载 | 同上 |
| 远程 → 远程（同一集群） | **服务端直接 mv/cp，数据不落地** | 这条最容易做错。如果实现成"下载再上传"，10 GB 数据要过两遍网络 |
| 拖到应用图标上 | 作为输入 | 例：拖一个 yaml 到"提交作业"图标 = 用这个配置建作业 |

**传输引擎**（分三档，按场景自动选，也允许手动指定）：

| 场景 | 方式 | 理由 |
|---|---|---|
| 海量小文件（>1000 个） | 本地或远程 `tar` 打包后流式传输 | SFTP 逐文件握手开销巨大，1 万个小文件可能比一个 tar 慢 10 倍以上。手册里"先 tar 再传"的建议直接产品化 |
| 单个大文件（>2 GB） | 分块 SFTP + 断点续传 | 可暂停、可续、失败只重传缺的部分 |
| 少量文件（<100） | 单流 SFTP | 简单可靠 |

**智能提示**（把平台知识变成产品能力，而不是文档）：

- 拖入目录且文件数 > 5000 → "检测到 12,847 个文件，逐个传输会很慢，建议打包后传输"，并提供一键打包
- 单文件 > 20 GB 上传到家目录 → "大文件建议放在数据集目录，避免 checkpoint 写入时挤爆配额"
- 目标目录所在配额 > 90% → 写入前警告

**其他操作**：重命名、新建目录、删除（进回收站式的中间层，不是直接 rm）、修改权限（只提供 644/755 这类安全组合，**不提供 777**）、压缩/解压、复制路径。

**传输队列**：常驻侧栏，不是弹窗。显示每个任务的速度、剩余时间、已传/总大小；支持暂停、重试、全部取消。失败项标红并给原因（权限拒绝 / 磁盘满 / 连接断开）。

### 3.3 ★★ 显卡租借

职责：把"写 sbatch 脚本"变成"下单"。这是替代 CLI 的核心价值。

**两种租法，对应两种真实需求**：

- **租一台来用**（交互式）：申请资源 → 拿到一个"远程节点"图标 → 双击进终端/远程桌面。适合调试、跑 notebook、看数据。
- **跑一个任务**（批处理）：填表提交 → 作业卡片 → 等结果。适合长训练。

**租借流程（五步，可跳步）**：

1. **看货**：卡片式展示各型号 GPU。每张卡显示：型号、显存、单价（点/卡/小时）、当前空闲数、所在节点名。
   - 排序：按"性价比"（单价/显存）或"最快能排到"（空闲数最多）
   - 筛选：显存 ≥ 40 GB、单价 ≤ X
2. **选配**：
   - 卡数（1/2/4/8）
   - 时长：1h / 4h / 12h / 24h / 自定义
   - 环境：conda 环境 / enroot 容器镜像 / 裸环境
   - 启动命令（可选，留空则进交互终端）
   - 工作目录
3. **算账**（这一步 CLI 完全没有，是核心差异点）：
   - 显示"预计预扣 **480 点**，你有 **1,200 点**，本月剩余 22 天"
   - 明确标注"**预扣制**：按最大时长先扣，提前结束按实际时长返还"
   - 如果余额不足预估的 1.2 倍，黄色警告
4. **提交**：显示排队中，并给出**人能看懂的排队原因**（见下表）
5. **拿到**：作业卡片变成可交互状态——"打开终端""打开 TensorBoard""打开监控"

**排队原因的人话翻译**（`squeue` 的 reason 字段直接给用户看毫无意义）：

| 原始 reason | 界面文案 |
|---|---|
| Priority | 前面有更高优先级的作业在排队，你的位置：第 3 |
| Resources | 暂时没有满足条件的空卡，预计等待 20 分钟 |
| QOSMaxJobsPerUserLimit | 你同时运行的作业已达上限，先等一个跑完 |
| PartitionTimeLimit | 申请时长超过该分区上限，建议改为 X 小时 |
| ReqNodeNotAvail | 指定节点不可用（可能故障或在维护） |

**作业详情**（右侧抽屉，不打断主界面）：
- 实时日志流（尾随，可暂停滚动、可搜索、可高亮 error）
- GPU 利用率 / 显存占用曲线（最近 30 分钟）
- 已运行时长、已消耗点数、当前状态
- 操作：取消、延长、下载产物、查看等效命令

**状态机**（UI 必须严格按这个走，否则会出现"卡在 RUNNING 但其实已失败"）：

```
草稿 → 提交中 → 排队中 ⇄ 运行中 → 已完成 / 已失败 / 已取消 / 超时
                     ↘ 提交失败（参数错 / 余额不足 / 无权限）
```

**空闲自动释放**（体现设计原则⑤）：
运行中的交互式作业，若 GPU 利用率连续 15 分钟 < 3%，弹提示"看起来闲置了，要释放吗？还有 32 分钟到期"。不强制，但默认建议释放。这既省点数，也缓解了手册里提到的抢占问题。

### 3.4 ★ 资源仪表盘

职责：一屏看清"我能用多少、还剩多少、别人在用什么"。

三块：

- **集群**：分区列表 + 节点状态（空闲/部分占用/满载/故障/维护），GPU 型号分布与空闲数。数据每分钟刷新。
- **我的配额**：存储水位条（0–5 TB 安全区 / 5–6 TB 警戒 / 6–9 TB 宽限期 / 9 TB 硬限），点数余额与本月消耗趋势（按天柱状图）。
- **我的作业**：运行中 / 排队 / 今日已完成。点进去看详情。

**告警规则**（本地计算，不依赖服务端）：
- 存储 > 5 TB → 黄色
- 存储 > 6 TB → 红色 + 显示宽限期剩余天数
- 点数余额 < 3 天平均消耗 → 黄色
- 作业失败 → 立即系统通知

### 3.5 快捷通道（体验增强）

把"每次都要敲一遍"的东西变成"点一下"：

- **端口转发管理器**：预设 TensorBoard / Jupyter / VNC / Grafana 监控，一键建立隧道并在浏览器打开。状态可见（端口占用冲突时提示换端口）。
- **内嵌终端**：不是给日常用，是给"救急"用——图形操作失败时能立刻下去看一眼。
- **镜像/环境管理**：列出已有的 conda 环境和 enroot 镜像，显示体积，支持删除。

这三个不解决核心痛点，但极大提升"这是个完整工具"的感觉，放在 Phase 3-4。

### 3.6 设置与安全

- 密钥：存储位置、指纹查看、轮换
- 传输：并发数、单任务限速、冲突策略（覆盖/跳过/重命名）
- 通知：哪些事件弹系统通知
- 外观：主题、壁纸
- 审计：本地操作日志（我什么时候传了什么、跑了什么），只存本地

## 4. 界面布局

### 4.1 整体结构（五区）

```
┌──────────────────────────────────────────────────────────────┐
│ ① 标题栏：连接状态灯 · 集群名 · 点数余额 · 存储水位 · 搜索     │
├────┬─────────────────────────────────────────────────────────┤
│ ②  │                                                          │
│ D  │  ④ 工作区（当前功能区，全屏）                             │
│ o  │     ┌────────────────────┬──────────────────┐            │
│ c  │     │  主区（列表/双栏）   │  详情抽屉（可收） │            │
│ k  │     └────────────────────┴──────────────────┘            │
│    │                                                          │
├────┴─────────────────────────────────────────────────────────┤
│ ③ 任务栏：窗口列表 · 传输队列 · 通知中心                       │
└──────────────────────────────────────────────────────────────┘
```

- **① 标题栏**：自绘（frameless window）。左侧连接状态，中间全局搜索（Ctrl+K），右侧常驻三个关键数字——**点数余额、存储水位、运行中作业数**。这三个是"电量"级别的信息，必须永远可见。
- **② Dock**：左侧图标启动器，7 个图标——桌面、文件、显卡、作业、仪表盘、终端、设置。当前项高亮。
- **③ 任务栏**：底部。左侧是打开的功能区标签，中间是传输队列缩略，右侧是通知铃铛。
- **④ 工作区**：主战场。左侧列表 + 右侧详情抽屉（Inspector 模式），抽屉可拖动调宽、可折叠。

### 4.2 桌面层

壁纸 + 图标网格（4-6 个图标，不超过两行）。图标不是"功能入口"的重复，而是**情境入口**：

- 「我的数据集」→ 直接打开远程数据集目录
- 「上次的实验」→ 打开最近的作业详情
- 「显卡商店」→ 打开租借页
- 「拖文件到这里」→ 一个巨大的投放区，拖进去默认上传到家目录

右键空白处：新建文件夹、刷新、打开终端、粘贴。

### 4.3 三个核心界面的信息密度

**文件管理器**：双栏，每栏顶部是地址栏 + 视图切换 + 排序。列表列：名称、大小、修改时间、权限。图标左侧加类型徽标（目录/权重/数据/脚本/图像）。文件多时虚拟滚动，**不要分页**（分页会打断拖拽）。

**显卡租借**：上半是卡片网格（3 列），下半是"最近租用"列表。卡片上是型号、显存、单价、空闲数、一个"立即租用"按钮。选中后卡片展开成配置表单，不跳页。

**仪表盘**：三栏垂直堆叠，每块一个卡片。数值用大字，趋势用小图。

## 5. 关键交互细节

### 5.1 拖拽的即时反馈（决定"像不像桌面"）

- 拖动中：被拖对象半透明跟随光标，源位置留虚线占位
- 悬停到合法目标：目标区域淡色高亮 + 边框加深
- 悬停到非法目标：红色禁止光标 + 一行说明为什么不行（"这是只读目录"）
- 悬停到应用图标：图标放大 1.1 倍 + 气泡"作为输入传给：提交作业"
- 松手后：立即出现任务条目（进度 0%），**不要等到有数据了才显示**

拖 500 个文件时，不能每个文件一条 —— 合并成一条"上传 500 个文件（3.4 GB）"，展开才看明细。

### 5.2 空状态与错误状态

这类工具最常见的失败是"空白界面让人不知道发生了什么"。每个界面都要设计：

- **空列表**：不是"暂无数据"，而是"还没有作业。租一张卡试试 →"（带按钮）
- **加载中**：骨架屏，不是转圈
- **解析失败**：黄色条"无法读取集群状态，可能输出格式有变化"，右侧"查看原始输出"
- **断线**：顶部横幅"连接已断开，正在重连（第 3 次，12 秒后）"，功能降级为只读

### 5.3 危险操作的三重防线

1. 不可逆操作（删除、覆盖）→ 二次确认，确认按钮不是默认焦点，需要看清文案
2. 批量操作 → 显示总数和总量，要求输入数字确认（超过 1000 个文件时）
3. 权限修改 → 只给 644 / 755 / 600 三个安全选项，不给 777

## 6. 技术选型

### 6.1 推荐栈

| 层 | 选择 | 理由 |
|---|---|---|
| 壳 | **Electron 30+** | 桌面隐喻 80% 是 UI 工作，Web 技术最擅长；生态最全；调试方便 |
| UI | React 18 + TypeScript | 组件化、类型安全 |
| 样式 | Tailwind + 自绘组件 | 不引重 UI 库，避免"网页感" |
| 状态 | Zustand | 轻量，不需要 Redux 的仪式感 |
| 虚拟列表 | TanStack Virtual | 远程目录上千项必须虚拟化 |
| 窗口管理 | 自研轻量（浮动窗口层）<br>或 react-rnd | 只给工具类窗口用，不做完整 WM |
| SSH/SFTP | **ssh2**（Node，主进程） | 支持 exec / SFTP / 端口转发 / 多路复用，一个库全包 |
| 本地存储 | SQLite（better-sqlite3） | 存作业历史、传输记录、设置 |
| 密钥 | Electron safeStorage / keytar | 走系统钥匙串，不落明文 |
| 打包 | electron-builder | Windows NSIS 安装包 |

**备选：Tauri 2**。体积从 ~150 MB 降到 ~10 MB，内存占用低一半。代价是要写 Rust 侧的命令桥接，对初学者不友好。**如果体积不是硬需求，不要为了省 140 MB 去学 Rust。**

**备选：PySide6**。如果想全程用 Python。拖拽和文件系统能力足够，但"桌面感"的视觉打磨成本高很多（自绘标题栏、动画、阴影都要手写）。不推荐作为首选。

### 6.2 架构分层

```
┌─────────────────────────────────────────────┐
│ Renderer（React）                            │
│  纯 UI，无 Node 权限，contextIsolation 开启  │
└──────────────┬──────────────────────────────┘
               │ 窄 IPC（只暴露白名单方法）
┌──────────────┴──────────────────────────────┐
│ Preload                                      │
└──────────────┬──────────────────────────────┘
               │
┌──────────────┴──────────────────────────────┐
│ Main（Node）                                 │
│  ├─ 连接池（多集群 / 多会话复用）             │
│  ├─ 传输引擎（队列、分块、续传、限速）        │
│  ├─ CLI Adapter 层（解析 → 结构化模型）       │
│  ├─ 轮询调度器（5-15s，按数据类型分频）       │
│  └─ 持久化（SQLite）                         │
└──────────────┬──────────────────────────────┘
               │ SSH（唯一通道）
┌──────────────┴──────────────────────────────┐
│ 远程 HPC —— 零安装，无 agent                  │
│  exec 命令 + SFTP + 端口转发                  │
└─────────────────────────────────────────────┘
```

**关键点：远程零安装。** 不在集群上部署任何东西。这既是约束（没 root、不能常驻），也是优势（不需要网管批准、不会影响别人、升级只升客户端）。

### 6.3 数据流

单向为主：Main 定时拉取 → Adapter 解析 → 推事件给 Renderer → UI 更新。

Renderer 从不直连远程，所有操作走 IPC → Main → SSH。这样权限最小化，也方便做统一的重试和错误处理。

**轮询频率分档**（避免打爆跳板机）：
- 作业状态：5 秒（仅当有运行中作业）
- 队列/集群：15 秒
- 配额：5 分钟
- 文件列表：手动刷新 + 写入后刷新（不做自动轮询，太贵）

## 8. 难点与风险

按"会不会让项目死掉"排序。

### 致命级

**R1. 所有数据靠解析 CLI 文本，没有 API。**
这是根本性脆弱点。集群升级、网管改脚本、字段顺序变化，都可能让解析失效。
缓解：Adapter 隔离 + 宽松解析 + 保留原始输出 + 失败时明确告知（绝不静默返回空）。预留"手动填价格表"的降级路径。

**R2. 传输性能可能远低于预期。**
SFTP 逐文件传输在海量小文件场景会慢到不可用。如果 v1 只做 SFTP，用户传一个数据集要 6 小时，产品就废了。
缓解：**第一天就把 tar 流式传输做进 MVP**，不要留到"以后优化"。这是刚需不是优化。

**R3. "租借"语义与真实调度不符，会导致信任崩塌。**
HPC 是排队共享，不是云厂商的即时实例。如果 UI 承诺"立即启动"，用户点了没反应就会认为工具坏了。
缓解：文案上从一开始就说"提交排队"，并给出预计等待；状态机严格区分"排队中"和"运行中"。

### 高危级

**R4. 跳板机连接不稳定。**
长时间挂机会被踢，网络抖动会断。多窗口共享连接时，并发 exec 可能打满 channel 上限。
缓解：连接池 + 指数退避重连 + 会话恢复（记录最后状态，重连后重新拉取）+ 限制并发 exec 数（如 5）。

**R5. 状态不一致。**
文件列表是缓存，远程可能已被别人改动（共享目录）。作业状态在两轮轮询之间可能已经变了。
缓解：写入前做 mtime/size 校验；作业历史用 `sacct` 补齐错过的中间态；界面标注数据时间戳。

**R6. 密钥安全。**
明文存私钥 = 严重事故。
缓解：只用系统钥匙串；配置文件中只存 keyRef；日志和错误信息脱敏；导出配置时剔除密钥。

**R7. 命令注入。**
所有远程命令都涉及文件名拼接，文件名里可能有空格、引号、分号、`$(...)`。
缓解：**一律用参数化执行，禁止字符串拼接**；对无法参数化的场景做严格转义；文件名只允许通过 SFTP 操作，不拼进 shell。

### 中危级

**R8. 大目录列表卡顿。** 上万文件的目录直接渲染会卡死。虚拟滚动 + 分批拉取（先取前 500，滚动再取）。

**R9. Windows 环境差异。** Windows 自带 OpenSSH 但没有 rsync；路径分隔符不同；杀毒软件可能拦截打包下载的二进制。缓解：优先用 SSH 内置能力，不依赖外部命令行工具；路径处理统一用 path 模块。

**R10. 跨平台。** 如果要做 macOS/Linux，钥匙串、通知、安装包都要各写一套。建议**先只做 Windows**，验证后再扩。

**R11. 范围膨胀。** 桌面隐喻很容易让人想加"时钟挂件""便签""音乐播放器"。坚决不加。

### 合规与伦理风险

**R12. 不能成为"占资源"的工具。**
手册明确提到有人用 sleep 占卡，管理方已开始限制。工具如果提供"保活"或"自动重试抢卡"，会成为问题的一部分。
反向设计：提供空闲检测与自动释放建议，并在提交时提示"请勿申请超过实际需要的时长"。

**R13. 不要绕过配额。**
不提供"多账号合并""借用他人额度"的自动化。点数借调是人和人之间的事，工具只做展示。

## 9. 分阶段开发计划

原则：**每个阶段结束时，工具都能被你自己的日常用起来**。不能用的阶段不算完成。

### Phase 0 · 技术验证（约 1 周）

不做界面，只验证三个"如果不行，整个方案要改"的假设：

1. `ssh2` 能否稳定连上跳板机，并执行命令拿到结构化输出
2. SFTP 传一个 1 GB 文件的真实速度；传 2000 个小文件的速度
3. tar 流式传输（本地打包 → 远程解包）能否工作，比逐个传快多少

**通过标准**：三个都能跑通，且对速度有量化认知。
**如果 2 或 3 不达标**：立刻重新评估方案，不要往下走。

### Phase 1 · 能替代 WinSCP（约 3 周）

- 连接中心（单连接即可）
- 双栏文件管理器 + 拖拽上传下载
- 传输队列（三档引擎，至少要有 tar 和 SFTP）
- 断点续传、冲突处理

**验收**：连续一周用它传数据，没有打开过 WinSCP。

### Phase 2 · 能替代写 sbatch（约 3 周）

- CLI Adapter 层（sinfo / squeue / sacct / 配额 / 点数）
- 显卡商店 + 租借表单 + 费用预估
- 作业列表 + 详情 + 实时日志
- 仪表盘（三块）

**验收**：连续一周不手写 sbatch，所有实验都从界面提交。

### Phase 3 · 变成"桌面应用"（约 2 周）

- 桌面层（壁纸、图标、右键、投放区）
- Dock + 任务栏 + 浮动窗口层
- 通知中心
- 全局搜索

**验收**：不点任务栏切到别的应用时，会下意识觉得这是个独立软件而不是网页。

### Phase 4 · 打磨（约 2 周）

- 端口转发一键打开（TensorBoard / VNC / 监控）
- 内嵌终端
- 空状态、错误状态、骨架屏全部补齐
- 打包成安装包，能在另一台机器上装起来用

**验收**：给一个没看过文档的同学，他能自己完成"传数据 → 租卡 → 看结果"。

### Phase 5 · 可选增强

作业模板库（常用配置存成模板，一键复现）、批量提交（参数网格搜索）、数据集目录共享、GPU 利用率历史曲线、配额自动清理建议。

## 10. 明确不做的事

写清楚边界，比写清楚功能更重要。

- **不做 Windows 复刻**。没有开始菜单、没有控制面板、没有多桌面。
- **不做多用户/协作**。这是个人工具，不共享状态、不同步配置。
- **不做远程桌面替代品**。VNC 只做"一键连上"，不内嵌实现。
- **不做计费系统**。点数只展示和预估，不做账本、不做统计报表。
- **不做作业编排**。不做 DAG、不做流水线，一次一个作业或一组参数扫描。
- **不做移动端**。
- **不在集群上装任何服务端组件**。

---

## 附：为什么这个方案值得做

如果只想要结论：**它把三类高频摩擦（传文件、记命令、看不见状态）压缩成零**。

更实际的价值在于——它是少数"自己天天用、能持续迭代、还能写进简历"的项目：涉及桌面应用架构、SSH 协议、异步任务队列、文件系统抽象、CLI 解析容错，每一块都是可以讲清楚的工程问题。而对算法岗来说，能把一个内部工具做到"同组的人在主动用"，比多刷两道题更有说服力。
