# 技术选型与传输引擎对比

> 前提：仅 Windows；全 AI 辅助开发（vibe coding）；优先级为「运行效率与响应速度 > 可视化与美观」。
> 本文只回答两个问题，不展开产品形态。

---

## 摘要

**选型**：Electron 33 + React 18 + TypeScript + electron-vite + ssh2 + tar-stream + uPlot。

理由是先把"性能瓶颈在哪"判断清楚：这个应用用户能感知的慢，只有四处——打开目录、拖入文件、传大文件、滚动长列表。前三处由网络与传输策略决定，第四处由虚拟滚动决定，**没有一处由壳决定**。壳决定的是冷启动、内存、安装包体积，那是资源占用，不是响应速度。

**传输**：不要三选一，要做「分段 tar + SFTP 双引擎 + 路由器」。分段 tar 是本方案最关键的一个工程决策。

# 第一部分 · 技术选型

## 1.1 先定位瓶颈

拆开看，用户抱怨"卡"的真实来源：

| 用户感受 | 真实原因 | 优化手段 | 壳能改善吗 |
|---|---|---|---|
| 点开目录要等 1-2 秒 | SFTP `readdir` 一次往返 + 渲染 | 预读、缓存、骨架屏 | 否 |
| 拖文件进去没反应 | 队列未启动、路径解析慢 | 立即入队、异步解析 | 否 |
| 传 10 GB 要好几个小时 | 传输策略选错 | 换引擎（10-20 倍） | 否 |
| 上万文件滚动掉帧 | 未虚拟化 | 虚拟滚动 | 否 |
| 切页面有白屏 | 路由未做预加载 | 预加载、持久化组件 | 轻微 |
| 冷启动 2 秒 | 主进程初始化、Chromium 启动 | 延迟加载、V8 快照 | **是** |
| 任务管理器占用 200 MB | 运行时基线 | 换壳 | **是** |

**结论：壳只影响最后两行。** 前五行才是"响应速度"的主体，而它们全是架构问题。

所以下面推荐的壳，是在"不牺牲前五行"的前提下，选**开发成功率最高**的那个——因为 vibe coding 的失败成本主要来自"改了跑不起来"，不是"跑起来慢 100 MB"。

## 1.2 推荐栈

| 层 | 选择 | 关键理由 |
|---|---|---|
| 运行时 | **Electron 33** | 见 §1.3 |
| 构建 | **electron-vite** | 主进程与渲染进程独立 HMR；改一行秒级生效，这是 vibe coding 的生命线 |
| UI | **React 18 + Tailwind CSS** | 这两者的组合是 AI 训练数据最密集的，出错率最低 |
| 状态 | **Zustand** | 无样板代码，AI 不需要理解 reducer 约定 |
| 虚拟列表 | **@tanstack/react-virtual** | 上万行稳定 60fps，API 极简 |
| SSH / SFTP | **ssh2**（纯 JS） | 一个库覆盖 exec、SFTP、端口转发、多 channel；**无原生编译** |
| tar | **tar-stream**（纯 JS） | 见 §1.5，不用 Windows 自带 tar.exe |
| 图表 | **uPlot** | Canvas 渲染，时间序列性能比 ECharts 高一个量级，体积 40 KB |
| 本地存储 | **electron-store**（JSON） | 刻意不用 SQLite，见 §1.4 |
| 打包 | **electron-builder** | NSIS 安装包，一条命令产出，无需额外工具链 |
| 类型 | **TypeScript strict** | AI 写的代码在编译期就暴露问题，而不是运行时 |

## 1.3 为什么不是 Tauri（尽管它更"高效"）

Tauri 2 在纸面上完全符合"运行效率优先"：

| 指标 | Electron | Tauri 2 | 差距 |
|---|---|---|---|
| 空闲内存 | ~150-220 MB | ~50-80 MB | 约 3 倍 |
| 冷启动 | 1.2-2.0 s | 0.4-0.8 s | 约 2.5 倍 |
| 安装包 | ~120-180 MB | ~8-15 MB | 约 12 倍 |

但它有三条否决理由，按权重排序：

**① 渲染性能没有差别。** Windows 上 Tauri 用 WebView2——那就是 Chromium。列表虚拟化、拖拽反馈、图表绘制，跑的是同一个引擎。Tauri 省下的是内存，**不是响应速度**。而你的核心诉求是响应速度。

**② 迭代速度的复利损失。** Rust 后端每次改动要重编译：首次 5-10 分钟，之后每次 30-90 秒。Electron 侧是秒级 HMR。vibe coding 会经历几百到上千次"改-看-再改"，这个差异累积起来是数天的差距——而这个差距恰好落在你最需要高频试错的前两周。

**③ AI 生成 Rust 的失败率明显更高。** 借用检查、生命周期标注、async 运行时选择（tokio 还是 async-std），这三类问题会让 AI 陷入"改一版→编译报错→再改"的循环。TypeScript 的类型错误在编辑器里就标红了，不需要一轮编译。

**迁移条件（写死，避免日后反复纠结）**：若实测冷启动 > 1.5 秒，**或**空闲内存 > 300 MB 且你确实感到卡顿，再评估迁移。届时 React 层 90% 可直接复用，需要重写的只有 SSH 桥接与文件系统访问。

## 1.4 两个刻意的"不用"

**不用 better-sqlite3。**
它是原生模块，安装时要 node-gyp + MSVC Build Tools 编译。这是 AI 辅助项目最经典的卡死点：`npm install` 报一堆 C++ 编译错误，AI 会开始胡乱建议装 Python、装 VS、改 node 版本，半小时就没了。
本应用的数据量——作业历史几千条、设置几十项、传输记录几百条——JSON 完全够用。用 `electron-store`，配合"防抖写盘 + 写临时文件再原子改名"即可。真到了需要 SQL 的规模（十万级记录），再迁移也不迟。

**不用 ECharts / Chart.js。**
ECharts 体积 1 MB+，初始化开销大，动画默认开启。你需要的只是"GPU 利用率随时间的折线"，uPlot 用 Canvas 直接画，40 KB，万点无压力。可视化本来就是次要诉求，用最轻的方案即可。

## 1.5 依赖层的两个具体的坑

**① Electron 32+ 移除了 `File.path`。**
从渲染进程拿拖入文件的真实路径，旧写法 `file.path` 会返回 `undefined`——**而且不报错**，表现为"拖进去没反应"，极难排查。正确做法是主进程侧用 `webUtils.getPathForFile(file)`。

**② 拖出到资源管理器需要 `startDrag`。**
HTML5 的拖放只能在应用内用。要让用户把远程文件直接拖到 Windows 桌面，必须：先下载到临时目录 → 调 `webContents.startDrag({ file, icon })` → 由系统接管。这是唯一能产生"真实文件拖拽"的路径。

## 1.6 五个真正的性能杠杆

按影响从大到小。这五条的价值远超壳的选择。

**① 传输策略（10-20 倍）**
见第二部分。这是唯一能达到数量级差异的优化。

**② SSH 连接复用**
一个 TCP 连接上开多个 channel，绝不为每次操作重新握手。SSH 握手需要 3-5 次往返，在 30 ms RTT 下就是 150 ms 纯等待。用户连续点五个目录，不复用就是 750 ms 白等。

**③ 进度事件节流（不做会直接卡死）**
传输时若每收到一个 32 KB 包就发一次 IPC，10 MB/s 意味着每秒 320 条跨进程消息，渲染进程会被消息淹没，界面直接失去响应。
**必须按时间窗合并**：每 100 ms 汇总一次，只发增量（已传字节、瞬时速度）。这是"看起来卡"最常见的真凶。

**④ 虚拟滚动 + 避免 N+1 查询**
SFTP 的 `readdir` 一次返回目录下所有条目的属性，**不要再对每个文件单独 `stat`**。1 万个文件就是 1 万次额外往返，直接多出十几分钟。

**⑤ 轮询分级 + 指数退避**
作业状态 5 s、集群状态 15 s、配额 5 min。连续失败时退避到 30 s / 60 s。不加退避的话，网络抖动时会有几十个请求排队，重连后一起涌上去把跳板机打慢——这既伤自己，也影响同组。

# 第二部分 · 传输引擎三策略对比

## 2.1 三种策略的本质差异

| 策略 | 数据路径 | 特征 |
|---|---|---|
| **A 单流 SFTP** | Node → SSH channel → 远程文件 | 一个 channel，逐文件 open → write → close |
| **B 多流分块 SFTP** | Node → k 个 channel → 远程文件 | 大文件切块并行，记录 offset 支持续传 |
| **C tar 流式** | Node 打包成流 → exec channel → 远程解包 | 数据不落地，文件边界只是 512 字节头部 |

**根本区别在每文件的固定成本。**
SFTP 每传一个文件需要 3-4 次往返（open、至少一轮 write、close、可选 setstat）。tar 没有——一万个文件的边界只是 512 字节的头部，不需要任何往返。

在 20 ms RTT 下，一个文件就是 80 ms 的纯等待。**一万个文件 = 800 秒 = 13 分钟的开销，与数据本身无关。** 这就是为什么小文件必须走 tar。

## 2.2 性能模型

```
A  T ≈ N × 4 × RTT                        + S / B
B  T ≈ N × 4 × RTT / k + 建流开销         + S / (B × k)
C  T ≈ 启动开销 + N × 极小                + S / B_tar
```

其中 N 文件数、S 总字节、RTT 往返延迟、k 并发流数。

### 实测：用真实集群校准这个模型（2026-10-31）

| 指标 | 实测值 | 说明 |
|---|---|---|
| 单次 exec 往返 | **50 ms**（p50，min 46 / max 54） | 20 次 `true` 取中位数 |
| 纯吞吐（4 MB 单流） | **42 MB/s** | 不涉及文件边界，代表链路本身 |
| tar 上传 1.00 GB / 2001 文件 | **42.9 s / 23.9 MB/s** | 含建连、解包、改名、核对 |
| tar 下载 524.5 MB / 201 文件 | **9.0 s / 58.0 MB/s** | 512 MB 大文件 + 200 × 64 KB；对账 201 文件一致、大文件 sha256 一致 |
| SFTP 单流上传 256 MB | **12.0 s / 21.3 MB/s** | `fastPut`，concurrency=1，chunk 32 KB |
| SFTP 单流下载 256 MB | **23.9 s / 10.7 MB/s** | 见下（tar 下行的对比） |

代入模型算 SFTP 路径的下界（A，k=1）：

```
2001 文件 × 4 × 50 ms = 400 s ≈ 6.7 分钟   ← 纯往返，不含任何数据
+ 1 GB / 42 MB/s ≈ 24 s
≈ 7 分钟
```

**同样的数据，tar 用了 43 秒，SFTP 的理论下界是 7 分钟**——差了接近 10 倍，而且这 400 秒跟文件大小完全无关，纯粹是"每个文件要握四次手"。这就是 §2.1 说"小文件必须走 tar"的实测量级。

**但要看清这个优势来自哪里**：单个 256 MB 文件，SFTP 上传 21.3 MB/s，tar 混合负载 23.9 MB/s——**大文件上两者几乎一样**。tar 的全部收益都来自"消除每文件固定开销"，一旦文件数量降到个位数，它反而多付了打包/解包和 2-3 秒启动成本。这正是 §2.5 决策矩阵里"单文件 > 2 GB 走多流分块而不是 tar"的原因。

**下行方向 tar 优势更大**：tar 下载实测 **58.0 MB/s**，是 SFTP 单流下载（10.7 MB/s）的 **5.4 倍**。原因有两个：
1. 下行同样要消除每文件往返，200 个小文件在 SFTP 下要多付 200 次 `open/read/close`；
2. SFTP 下行的 10.7 MB/s 是**客户端逐块写入磁盘**时的瓶颈（`fastGet` 边收边写），
   而 tar 下行是 `extract` 流式解包，磁盘写入与网络接收并行，管道更满。

> 结论：**下行的 ETA 不能沿用"上行减半"的直觉**。无目录、单文件时按 SFTP 10–11 MB/s 估；
> 有目录时走 tar，实测能到 58 MB/s，差五倍，这个差异用户是能感觉到的。

注意 23.9 MB/s 低于 42 MB/s 的单流上限：差额花在 tar 的双端 CPU、2001 次文件创建、以及解包后 `du`/`find` 的核对上。**真实批量传输不会跑满链路带宽**，预估 ETA 时按 25 MB/s 更实际。

三条约束必须写进实现：

1. **k 受服务端 `MaxSessions` 限制**，OpenSSH 默认 10。超过会直接 `channel open failure`，且错误信息不直观。
2. **客户端加解密在 SSH 库的单线程里跑**，k 增大到一定程度收益归零（一般 k=4-6 就见顶）。
3. **tar 有 2-3 秒固定启动成本**（双端进程创建 + 握手），所以文件很少时它反而更慢。

**交叉点大约在 50-200 个文件**，随平均文件大小浮动。这是选型时最实用的一个数字。

## 2.3 五维对比

| 维度 | A 单流 SFTP | B 多流分块 | C tar 流式 |
|---|---|---|---|
| **适用场景** | < 100 个文件；边浏览边传；需精确控制单个文件 | 单文件 > 2 GB；必须断点续传；网络不稳定 | > 500 个小文件；整目录迁移；数据集同步 |
| 每文件固定开销 | 4 次往返 | 4 次往返（可并行分摊） | ≈ 0 |
| 典型吞吐 | 20-40 MB/s | 60-150 MB/s（受三约束） | 50-100 MB/s |
| 1 万 × 200 KB | ~14 分钟 | ~4 分钟 | ~40 秒 |
| 1 × 10 GB | 5-8 分钟 | 2-3 分钟 | 3-4 分钟（单流） |
| **断点续传** | 需自建（文件级） | 原生，粒度最细（块级） | 不支持（除非分段） |
| **进度粒度** | 精确到文件 | 精确到文件 + 百分比 | 只有总字节流，不知道当前是哪个文件 |
| **失败影响面** | 单文件，其余继续 | 单块，可重试 | 整体中断，可能留下半解压目录 |
| **原子性** | 易做到（临时文件 + rename） | 易做到 | 需额外设计 |
| **元数据/权限** | 完全可控 | 完全可控 | 会带过来本地权限，有合规风险 |
| 服务端通道占用 | 1-2 | k 个 | 1 |
| **实现复杂度** | 低（~200 行） | 高（~800 行，状态机 + 校验 + 冲突处理） | 中（~400 行，流控 + 错误传播 + 进度估算） |
| **AI 一次写对的概率** | 高 | 中 | 中高（但边界容易漏，见 §2.7） |

## 2.4 可靠性差异（这部分比性能更值得细看）

### 失败后的状态

- **A**：单文件失败 → 该文件留下 0 字节或残缺，其余不受影响。事后可用 size 比对找出坏文件。**状态最清晰。**
- **B**：块失败 → 记录 offset，重连续传。**最健壮**，但 offset 与实际写入位置不一致时（例如远端被截断）会产生拼接垃圾。
- **C**：整体失败 → 远程留下半个目录，**且无法判断哪些文件是完整的**（tar 不写清单）。这是 tar 唯一的硬伤。

### 原子性

三个策略都有并发写同一文件的损坏风险，必须有本地锁（按目标路径 hash 加锁）。

tar 解包时对已存在文件是直接覆盖，且顺序不确定——意味着中途失败会留下"一半旧一半新"的目录。**唯一解法是解到 `dest.partial/`，全部成功后再 rename**。改名在同一文件系统内是原子的，成本几乎为零。这一条必须写进实现，不能省。

### 可验证性

- **A / B**：传输后可直接比 size + mtime，逐文件核对。
- **C**：只能比"文件数 + 总字节"（远程 `du`），无法逐文件校验。要做逐文件校验得先生成清单再核对，成本很高。

实践建议：tar 传输完成后，自动跑一次远程 `du -sb` 和文件计数，与本地统计比对，不一致就告警。这是成本最低的兜底。

### 权限与合规（这条和集群红线直接相关）

tar 会保留本地的权限位。Windows 上不存在 POSIX 权限，tar 会写入默认值或 0，上了集群可能出现权限为 `000` 的文件，或者意外带上特殊位。

**必须显式处理**：上传时统一写成 `644`（文件）/ `755`（目录），并且**永远不提供 777 的选项**。工具应该替用户守住这条线，而不是给一个"一键递归 777"的按钮——那是把安全责任推给不懂的人。

### 符号链接

tar 默认保留符号链接。如果本地目录里有指向巨大目录的链接，会被原样复制成断链；如果指向父目录，可能造成无限展开。

SFTP 则需显式决定是"跟随即复制内容"还是"创建链接"。**建议默认 dereference（跟随即复制），但对总大小超过阈值的链接给出提示**，避免一个链接把 500 GB 拉进来。

## 2.5 决策矩阵

```
avg = 总字节 S / 文件数 N

avg < 1 MB  且  N > 500        →  C（分段 tar）
avg > 50 MB  或  单文件 > 2 GB  →  B（多流分块）
N < 100                        →  A（单流 SFTP）
其余                           →  C（分段 tar）
```

界面上的呈现方式：拖入后先算一遍清单（这一步很快，只是遍历本地目录），显示"检测到 12,847 个文件 / 3.4 GB，将使用分段 tar，共 2 段"。用户可以在"高级"里手动覆盖。

**把选择过程透明化，是这个工具建立信任的关键**——用户看得见它为什么这么选，出问题时也能自己换。

> **当前实现状态（v2.1）**：A（单流 SFTP）与 C（tar）已实现，矩阵判断在 `src/main/transfer/engine.ts`，
> 返回「策略 + 理由 + 告警」三段，`describeDecision()` 直接产出上面那句文案。
> **B（多流分块）尚未实现**：矩阵命中 B 时降级到 A，并在 `warnings` 里明说"会明显变慢"，绝不假装支持。
> 决策顺序严格自上而下（行之间有重叠，先命中先返回），有单测锁定边界（N=100、avg=1 MB）。
>
> **确认框已落地**：拖拽松手后不会直接开传，而是先扫描（`src/main/fs/scan.ts`）→ 出计划（`planner.ts`）→
> 弹确认框。计划按 id 缓存 10 分钟，点"开始"时不再重新扫描。
> 含目录时强制走 tar（只有它能保住目录结构），与矩阵并列在 `planner.ts` 里判断。
>
> **tar 两个方向都通了**：`transfer/tar.ts`（上传，`session.pipe` → 远端 `tar -x`）、
> `transfer/tar-download.ts`（下载，远端 `tar -cf -` → `session.pipeOut` → 本地 `tar-stream.extract`）。
> 下载侧本地不需要安装 tar，解包用 `tar-stream` 在进程内完成，落盘走 `<dest>.partial` 再 rename。
>
> **同名处理交给用户决定**：确认框里四选一（跳过 / 覆盖 / 改名 / 中止），默认「跳过」——
> 批量传结果文件时"有一个已存在就整批停下"是最烦人的行为。
> **目录不允许「覆盖」**，因为那等于先删掉整个目录；`service.ts` 直接拒绝并建议改选。

## 2.6 推荐架构：分段 tar + 双引擎

**不要三选一。** 正确做法是两个引擎 + 一个路由器。

```
待传清单
   ↓
路由器（算 N / S / avg / 最大单文件）
   ↓
┌──────────────┴──────────────┐
SFTP 引擎                    tar 引擎
（单流 + 多流统一抽象）       （分段，默认 2 GB/段）
└──────────────┬──────────────┘
               ↓
        统一的任务队列
        （进度、取消、重试、限速、锁）
```

**分段 tar 是这个方案里最值得投入的一个决策。** 把 tar 切成约 2 GB 的段，每段独立成一次 exec：

| 收益 | 说明 |
|---|---|
| 保留 tar 的低开销 | 段内仍是流式，无逐文件往返 |
| 获得段级续传 | 断在第 3 段，只需从第 3 段重来，不用全部重传 |
| 失败隔离 | 单段失败只重传该段 |
| 进度可估算 | 按"已完成段数"就能给出像样的剩余时间，解决了纯 tar"只能看字节数"的短板 |
| 可控的峰值 | 单段 2 GB，内存与磁盘的瞬时压力可预测 |

代价是实现复杂度从"中"升到"中高"，但换来的是 tar 唯一的硬伤（不可续传）被填掉了。这是我认为这个项目最划算的一笔工程投入。

**另有一条必须记住的规则**：远程 → 远程的移动/复制**不走传输引擎**，直接在服务端执行 `mv` / `cp`。如果实现成"下载再上传"，10 GB 数据要过两遍网络，耗时是 2 倍以上——这是同类工具最常见的设计错误。

## 2.7 AI 辅助开发时的八个典型坑

这一节比前面的对比表更实用。这些不是"能不能写出来"的问题，而是"AI 大概率会漏掉"的边界。

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | tar 管道不处理背压 | 一次性读到内存 → OOM 崩溃 | 必须用 `stream.pipeline`，不要手动 `on('data')` 拼接 |
| 2 | 只检查本地 tar 退出码 | 本地成功、远程解压失败 → **静默丢数据** | 两端退出码都要检查，远程非 0 必须报错 |
| 3 | 取消时只 kill 本地进程 | 远程 tar 变孤儿进程继续写盘 | 远端记录 PID，取消时 `kill -TERM`，并确认已退出 |
| 4 | 并发数设成 16 | 超过 `MaxSessions` → channel open failure | 默认 4-6，遇错退避，不要贪多 |
| 5 | 续传不校验 mtime / size | 续的是旧文件 → 拼接出损坏文件 | 续传前三元组比对（size、mtime、路径），不一致就整文件重传 |
| 6 | Windows 路径分隔符混进远程路径 | GPFS 上出现名为 `a\b` 的文件 | 远程路径只用 `/`，统一用 POSIX 语义拼接 |
| 7 | 文件名含换行 / 引号 / `$()` 时拼 shell | 命令注入或文件丢失 | SFTP 与 tar 天然安全；但"建目录""改权限"极易手滑拼字符串——一律参数化 |
| 8 | 进度按数据包发 IPC | 每秒数百条消息 → UI 卡死 | 按 100 ms 时间窗合并，只发增量 |

补充一条：**文件名编码**。Windows 上中文文件名很常见，而 Windows 自带的 `tar.exe`（bsdtar）在某些版本对 UTF-8 处理有问题，可能产生乱码文件名。这也是推荐用 `tar-stream`（纯 JS，全程 UTF-8）而不是调外部命令的原因之一。

## 2.8 落地顺序

| 步骤 | 内容 | 理由 |
|---|---|---|
| 1 | A 单流 SFTP + 队列骨架 | 最简单，先跑通连接、UI 和进度链路 |
| 2 | C tar 流式（暂不分段） | 解决 80% 的真实痛点（小文件慢） |
| 3 | 分段 + 段级续传 | 补上可靠性，让 tar 可用于生产 |
| 4 | B 多流分块 | 只对大文件路径生效，最后做 |

**先做 A 再做 C 再做 B**，不要反过来。多流分块实现最复杂、只对少数场景有收益，先做它会拖慢整个 MVP。

---

## 一句话总结

壳选 Electron 不是因为它最快，而是因为**这个应用的速度不在壳里**；传输引擎选"分段 tar 为主、SFTP 为辅"，是因为**性能差异在这里是数量级，而不在别处**。
