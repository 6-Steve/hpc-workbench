# 次一级改进（2026-11-17 已实施，待验收）

三项：**编辑主机表单**、**作业组**、**托盘常驻**。
各自独立，可以分开做；建议顺序按"风险从低到高"：编辑主机 → 托盘 → 作业组。

## 一、编辑主机表单

### 现状

改一台机器的端口/用户名，现在只有两条路：

| 路 | 问题 |
|---|---|
| 设置 →「编辑配置文件」 | 手改 JSON，是最后一处"必须懂文件格式"的地方 |
| 设置 →「重新配置…」 | **整体重建**，有多台时全部重写 |

### 目标

切换器或设置页里点「编辑」→ 弹表单改这一台 → 保存后立刻生效。

### 关键约束（写错会出真问题）

| # | 约束 | 原因 |
|---|---|---|
| 1 | **`id` 不可改，只改 `label`** | `id` 是连接池的键（`entries.get(profile.id)`）。改了 id，旧会话成了孤儿，隧道/终端挂在上面继续跑 |
| 2 | 保存后必须 `pool.invalidate(id)` | 否则旧会话还在用**旧端口**，用户以为改了却没生效 |
| 3 | 密码永不回显 | 只在钥匙串里；表单显示「已保存（可重填）」/「未保存」 |
| 4 | 写盘用**临时文件 + rename** | 现在 `applySetup` 是直接 `writeFileSync`，写一半断电就损坏整个配置 |
| 5 | 写入前**重新读文件**，只 patch 目标项 | 切换器和设置页可能同时开着，整文件覆盖会吃掉对方改动 |
| 6 | 校验复用 `validateProfiles()` | 向导/启动读的是同一把尺子，不能再写第二套 |

### 接口

```ts
// main/ipc.ts
'profile:update': (patch: {
  id: string            // 定位，不允许改
  label: string
  host: string
  port: number
  username: string
  auth: { method: 'key' | 'password'; privateKeyPath?: string }
  password?: string     // 只有用户重填时才带；undefined = 不动
}) => { ok: boolean; error?: PlainError }
```

实现（`main/profiles-edit.ts` 新文件，纯逻辑 + 注入 fs，便于单测）：

```ts
patchProfile(fileText, patch) → { text: string; changed: boolean }
```

步骤：`JSON.parse` → 找到 id → 逐个字段赋值（`password` 走 `vault.set`，不落 JSON）→
`validateProfiles(next, path)` → 写临时文件 → `rename` → `pool.invalidate(id)`。

> 注意：**不要把 `validateProfiles` 的返回当错误码用**，它抛 `ConfigError` 且带 `issues[]`，
> 直接把 `issues` 转成字段级错误显示在对应输入框下面。

### 交互

- 入口 A：切换器面板每行末尾「编辑」（注意：整行是按钮，**不能嵌套按钮**，改成行内右侧一个独立小按钮）
- 入口 B：设置页新增「跳板机」卡片，列出所有主机 + 「编辑」/「添加」
- 表单字段：名称 / 主机 / 端口 / 用户名 / 认证方式 / 私钥路径或密码
- 底部：`测试连接`（复用 `probeLatency` 或轻量 TCP 探测）+ `保存`
- 保存成功后：显示「已保存，切换或重连后生效」，并**主动提示**当前正在用这台 → 是否立刻重连

### 边界

| 情况 | 处理 |
|---|---|
| 把唯一一台的端口改错 | 允许保存（配置是配置），但**不要**自动重连——先让用户看清 |
| 改 `id` | 输入框禁用 + 说明"id 是内部标识，改了会丢失会话" |
| 删除最后一台 | 拒绝，提示"至少保留一台" |
| 主机重名 | 允许（`id` 才是键），但 label 重复时在列表里加后缀提示 |

### 改动清单

| 文件 | 改动 |
|---|---|
| `src/main/profiles-edit.ts`（新） | `patchProfile()` 纯函数 + 原子写 |
| `src/main/ipc.ts` | `profile:update`（校验 + 写 + invalidate） |
| `src/preload/*` | 新方法 → `PRELOAD_API_VERSION` **26 → 27** |
| `src/renderer/src/components/ProfileEditorDialog.tsx`（新） | 表单 |
| `ProfileSwitcher` / 设置页 | 入口 |
| `tests/profiles-edit.test.ts`（新） | patch 语义、id 保护、原子写、坏 JSON |

### 验收（S 块）

| # | 怎么验 | 期望 |
|---|---|---|
| S1 | 把 hpc-02 的端口 2222 改成 2224 并保存 | 文件里只有这一项变了，`hpc` 原样 |
| S2 | 改完切到 hpc-02 | 用新端口连（诊断页的端口字段跟着变） |
| S3 | 改密码为空 | JSON 里不出现密码；钥匙串里也没有（或保留旧的，需明确提示） |
| S4 | 手工把 JSON 改坏，再点保存 | 报错原样显示，**不覆盖**原文件 |
| S5 | 两台同时改 | 后保存的那次不会吃掉前一次对另一台的改动 |

## 二、作业组

### 现状

`JobsView` 把 `squeue` 的行平铺，一行一个 job。一次实验交 30 个 job 就是 30 行，
而且**每个 job 结束都会单独弹一条通知**（`App.tsx` 的 `diffJobSnapshots`）。

### 目标

把"同一批提交"的作业合成一行，显示 `12/30 完成 · 2 失败 · 3 运行中 · 13 排队`；
组内全部结束时只发**一条**汇总通知。

> 真正的收益不是折叠，是**通知降噪**。30 条推送比 30 行列表更难受。

### 分组规则（保守优先）

自动合并条件，三条全满足才算一组：

1. `job.name` **完全相同**
2. 同一 `partition`
3. 相邻两次提交的 `submitTime` 间隔 ≤ **30 分钟**

**默认关闭**，用户在作业页顶部打开「按批次合并」。

> 为什么不默认开：同名不同批（比如每天都跑 `eval`）会被合到一起，
> 那比不合并更误导。默认关 + 明确开关，是唯一不会骗人的选择。

### 数据

分组**不落盘**（每次从 `squeue` 现算），只有"固定分组"（用户手动指定）存 `KVStore`：

```ts
// deps.cache（KVStore），key: 'jobs.groups'
interface JobGroupOverride {
  id: string          // group id
  name: string
  jobIds: string[]    // 用户手动拉进组的
}
```

组 id 必须**稳定**：`g:<name>:<首个 submitTime 秒>`。
不能用随机 id —— 20 秒刷新一次，每次重新生成会让组在列表里上下乱跳。

### 计算

`src/renderer/src/lib/job-groups.ts`（纯函数）：

```ts
interface JobGroup {
  id: string
  name: string
  partition: string
  jobs: Job[]
  counts: { total; running; pending; done; failed }
  firstSubmit: number
}

groupJobs(jobs: Job[], opts: { enabled: boolean; windowMinutes?: number }): JobGroup[]
```

排序：组按 `firstSubmit` 升序；组内按 `id` 数值升序。**组成员变化时不要重排整组**。

### 展示

```
▸ eval  12/30 完成 · 2 失败 · 3 运行中 · 13 排队        46 分钟
    └ 展开后是原来的平铺行（含"谁在用"、日志、取消）
```

- 组行左侧沿用现有胶囊（`running/pending/failed` 里取**最差**的那个）
- 失败数 > 0 时整组标 `state-bad`，这一眼就能看出"这批有问题"
- 展开状态记在组件 state，不进 KVStore（刷新不该记住这个）

### 通知

现有逻辑按 job 逐条推送。加一条规则：

| 场景 | 行为 |
|---|---|
| 合并模式**关** | 保持现状（逐条） |
| 合并模式**开**，job 属于某个组 | 组内还有活着的 → **不推单条**；全部离开队列 → 推一条 `eval：30 个作业全部结束（28 成功 / 2 失败）` |

> 这条要写在 `App.tsx` 通知那段的上方注释里，否则下次改通知的人会把降噪逻辑吞掉。

### 边界

| 情况 | 处理 |
|---|---|
| 组的名字很长 | 组行截断 + `title` |
| 只有一个 job 的组 | **不折叠**，直接平铺（折叠单行没有意义） |
| 组内 job 被取消 | 计数进 `done`，不算失败（`CANCELLED` ≠ `FAILED`） |
| 手动分组与自动分组冲突 | 手动优先；两条规则都命中也只生成一个组 |

### 改动清单

| 文件 | 改动 |
|---|---|
| `src/renderer/src/lib/job-groups.ts`（新） | `groupJobs()` 纯函数 |
| `JobsView.tsx` | 合并开关 + 组行渲染 + 展开复用现有行组件 |
| `App.tsx` | 通知降噪分支 |
| `tests/job-groups.test.ts`（新） | 分组规则、稳定 id、单 job 不折、CANCELLED 归类 |

**不动主进程**（`squeue` 已经给了全部字段）。

### 验收（T 块）

| # | 怎么验 | 期望 |
|---|---|---|
| T1 | 交 3 个同名作业（间隔 1 分钟） | 合并成一行 `0/3`；关掉开关后恢复 3 行 |
| T2 | 同名但间隔 2 小时的两批 | **不合并**（超出 30 分钟窗口） |
| T3 | 盯着看 1 分钟（3 次刷新） | 组的 id 与位置不变，不会上下跳 |
| T4 | 组内一个作业失败 | 组行标红并显示 `1 失败` |
| T5 | 组里 30 个全跑完 | **只收到一条**汇总通知，不是 30 条 |

## 三、托盘常驻

### 现状

```ts
app.on('window-all-closed', () => { app.quit() })
```

没有 `Tray`。挂着隧道或跑长任务时，关窗就全断了。

### ⚠️ 先说一个必须先解决的冲突

`use-poll` 的可见性逻辑是 **`document.hidden` 时完全停发**（`lib/use-poll.ts`）。

托盘驻留 = 窗口隐藏 → **作业轮询停止 → "跑完通知我"直接失效**。

这跟托盘常驻的目的正好相反。所以托盘不是"加个 Tray"就完了，必须同时改轮询条件：

```ts
// 现在
const visible = !document.hidden
// 改成
const visible = !document.hidden || trayResident
```

`trayResident` 由主进程下发（`app:residency`），窗口初始化时取一次 + 订阅变更。

### 关窗策略（设置项）

| 选项 | 行为 |
|---|---|
| **总是退出**（默认） | 保持现状 |
| 有活动任务时驻留 | 有传输中/隧道开着/作业在跑 → 藏到托盘；否则退出 |
| 总是驻留 | 关窗只隐藏 |

"活动任务"由主进程判断：`transfer.queue` 有 running、`reverseTunnels.list().length > 0`、
`terminals` 有活会话、最近一次 `squeue` 有 running 作业。

### 托盘

```ts
const tray = new Tray(nativeImage.createFromPath(join(appRoot, 'build', 'icon.ico')))
tray.setToolTip('HPC 工作台')
tray.setContextMenu(Menu.buildFromTemplate([
  { label: '显示主窗口', click: () => showWindow() },
  { label: '── 当前没有运行中的作业', enabled: false },   // 动态更新
  { type: 'separator' },
  { label: '退出', click: () => { isQuitting = true; app.quit() } }
]))
```

- 图标用现有的 `build/icon.ico`（Windows 需要 16/32px 多尺寸，现有 ico 应该已包含）
- 左键点击 = 显示窗口（Windows 习惯）
- 托盘菜单里放"当前作业摘要"是为了**不用打开窗口也知道在跑什么**

### 必须处理的三个坑

| 坑 | 处理 |
|---|---|
| `before-quit` 被"关窗只隐藏"拦住 | 用 `isQuitting` 标志：窗口 `close` 事件里 `if (!isQuitting && resident) { e.preventDefault(); win.hide() }` |
| 第二次启动应用 | 已有单实例锁；拿到锁时 `showWindow()`（现在可能只是 focus，需确认） |
| 托盘图标资源缺失（打包后路径变） | 用 `process.resourcesPath` 兜底；打包配置里确认 `build/` 被带上 |

### 不做

- 托盘气泡通知（系统通知已经有了，重复）
- 开机自启（注册表写操作，收益低、卸载不干净）
- macOS 的 dock 行为（本项目只发 Windows；将来要发再单独设计）

### 改动清单

| 文件 | 改动 |
|---|---|
| `src/main/index.ts` | `Tray` + `isQuitting` + 关窗拦截 + `app:residency` |
| `src/main/ipc.ts` | `app:residency`（读/写）+ `app:activity`（是否有活动任务） |
| `src/renderer/src/lib/use-poll.ts` | 可见性条件加 `trayResident` |
| `SettingsView` | 新增「关窗行为」单选 |
| `preload` + d.ts | 两个新方法 → `PRELOAD_API_VERSION` **26 → 27** |
| `tests/` | `use-poll` 的条件（纯函数化后表驱动） |

### 验收（U 块）

| # | 怎么验 | 期望 |
|---|---|---|
| U1 | 设置选「总是退出」，关窗 | 进程真的退出（任务管理器里没有） |
| U2 | 选「有活动任务时驻留」，开着隧道关窗 | 窗口消失，托盘图标还在，隧道仍在（集群上 `ss -ltn` 能看到端口） |
| U3 | 接着 U2，作业跑完 | **仍然弹出系统通知**（证明轮询没停） |
| U4 | 托盘右键 → 显示主窗口 | 窗口回来，状态还在（终端 scrollback 没丢） |
| U5 | 托盘右键 → 退出 | 进程退出，端口释放 |
| U6 | 驻留状态下再双击 exe | 不会开第二个实例，而是显示已有窗口 |
| U7 | 没有活动任务时关窗（选"有活动任务时驻留"） | 直接退出，不留托盘 |

## 优先级与依赖

| 顺序 | 项 | 依赖 | 估量 |
|---|---|---|---|
| 1 | 编辑主机表单 | 无 | 中低（1 个纯函数 + 1 个表单） |
| 2 | 托盘常驻 | **必须先改 `use-poll` 的可见性条件** | 中（主进程 + 一个设置项） |
| 3 | 作业组 | 无 | 中高（分组函数 + 列表重构 + 通知分支） |

> 三项都做完，`PRELOAD_API_VERSION` 会到 **27**（编辑主机与托盘各加方法，作业组不加）。
> 如果分两次发版，编辑主机那次到 27，托盘那次到 28。
