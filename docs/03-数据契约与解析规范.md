## 0. 真实数据推翻的四个假设

先说最重要的部分。这四条如果按原方案实现，都会变成线上 bug。

### ① 配额命令：工具在，只是不在 PATH 里

两次执行的结果放在一起看，结论是确定的：

- 第一次跑 `--block-size autofta`，报的是 **mmlsquota 自己吐的错误**——说明二进制存在、能执行
- 第二次报 `mmlsquota: command not found`——这是 **bash** 说的，说明裸命令不在 PATH 里

所以只有两个结论，没有第三种可能：

1. 工具在 `/usr/lpp/mmfs/bin/` 下，**必须用绝对路径调用**
2. 手册的 `autofta` 参数确实写错了，正确值是 `auto`

正确调用：`/usr/lpp/mmfs/bin/mmlsquota --block-size auto`

**这件事的意义比它本身大**：它证明文档会过时，而工具不能。所以 Adapter 必须做到——命令失败时把**原始 stderr 显示给用户**，而不是抛一个"配额读取失败"。用户看到那三行英文，立刻就知道该改什么；只看到"读取失败"，就只能来问你。

### ② drain 节点会被误当成空闲资源卖出去

`node18` 的数据：8 张 A100 80G、587 GB 空闲内存、CPU 全空闲——但状态是 `drain`。同理 `node02`、`node15`。

如果 GPU 商店只解析 GRES 数量、不看节点状态，就会把这些**正在排空、不会再接新作业**的机器展示成"有货"。用户点进去，作业永远排队。

**规则：`state ∈ {drain, drng, down, comp}` 的节点一律不进入可售库存**，但要在界面上单独显示为"维护中"，否则用户会以为机器消失了。

### ③ squeue 的排队原因不在独立的列里

实测输出：

```
JOBID PARTITION  NAME      USER  ST  TIME  NODES NODELIST(REASON)
185046  compute  exp-b001  user01 PD  0:00   2    (JobHeldUser)
```

排队时，原因是被**括号包着塞在最后一列**的。设计文档里我写"解析 reason 字段"是错的。

而且 `JobHeldUser` 这个原因很特殊——**它不是资源不够，是用户自己 `scontrol hold` 了作业**。正确的 UI 文案不是"排队中"，而是"已挂起（你手动暂停），可一键恢复"。这两种状态混在一起，用户会一直等一个永远不会启动的作业。

### ④ 版本号不能推断 JSON 能力（v1.3 新增，推翻的是本文档自己的判断）

v1.2 写着"23.02 无 `sinfo` / `scontrol` 的 JSON"。实测相反：`sinfo -V` 确实报 `23.02.3`，但四条命令的 `--json` **全部可用**，因为该构建回移了 `data_parser/v0.0.39`。

这条放在 §0 而不是只塞进 §2，是因为它推翻的不是"某条解析规则"，而是**"查版本表就能知道能力"这个方法论**。同一个教训在 §0① 已经出现过一次（手册把 `mmlsquota` 的参数写错了）——**文档会过时，工具不会**。

延伸结论：任何"支不支持"的判断都必须实测，包括本文档自己写的版本表。

### 2.1 版本能力矩阵（v1.3 按实测重写）

| 命令 | upstream 起始版本 | 本集群实测（`slurm-wlm 23.02.3`） | 结论 |
|---|---|---|---|
| `squeue --json` | 21.08 | ✅ 可用 | 直接用 |
| `sacct --json` | 20.02 | ✅ 可用 | 直接用 |
| `sinfo --json` | 23.11 | ✅ **可用** | 用，但只当分区概览 |
| `scontrol show node --json` | 23.11 | ✅ **可用** | 用，这是库存真值来源 |

**v1.2 的这张表是错的，错在两行。** 原文按 upstream 版本判断 `sinfo` / `scontrol` 的 JSON 要 23.11 才有，而本集群报的是 23.02.3，于是推断"不可用，走固定格式"。

实测结果相反：

```
$ sinfo -V
slurm-wlm 23.02.3

$ sinfo --json | head -3
{
  "meta": {
    "plugins": { "data_parser": "data_parser/v0.0.39", ... }
```

**版本号没变，但 JSON 能力在。** 原因是这个构建回移（backport）了 `data_parser` 插件，而不是升级了 SLURM。`data_parser` 正是 JSON 序列化的实现，它在，JSON 就能用。

**这件事的教训比结论本身重要**：分布式构建的版本号不能用来推断特性有无。Debian/Ubuntu 的 `slurm-wlm`、各厂商的定制版都可能带 backport。任何"按版本号写死能力"的判断都会在某个集群上翻车——包括本文档自己。

所以**唯一可靠的做法是连上去试一次**，见下面的探测方案。

**设计对策：运行时能力探测，而不是把这四个格子写死。**

连接建立后跑一次探测（`sinfo --json >/dev/null 2>&1` 看退出码），把结果缓存在 profile 里。理由：

- 集群哪天升级到 23.11+，不用改代码就自动用上 JSON
- 集群哪天降级或换了节点，也不会因为写死而崩
- 探测成本一次连接一次，可以忽略

```ts
type Caps = {
  sinfoJson: boolean
  sacctJson: boolean
  squeueJson: boolean
  scontrolJson: boolean
  slurmVersion: string | null
  // 每条探测的 command / exit code / stderr，出问题时给人看
  evidence: Record<string, { command: string; code: number | null; stderr: string }>
}
```

这份能力表随 profile 持久化，界面上放在"诊断"里——出问题时用户能一眼看到工具认为集群支持什么，而不是靠猜。

**实现注意**：探测不能只看退出码。退出码 0 但输出不是 JSON 的情况真实存在（命令认了参数却打了别的东西），所以判据是 `code === 0 && stdout.trimStart().startsWith('{')`。

### 2.2 JSON 解决了什么，没解决什么

这一节是为了避免一个很危险的误读："既然 JSON 都能用，那 §3.1 的 GRES 正则、§5.4 的 TRES 规则就不用写了。"

**解决了（原陷阱直接消失）：**

| 原陷阱 | 为什么消失 |
|---|---|
| D2 `scontrol` 值内含空格（`OS=Linux 5.15...`） | JSON 不需要按 `key=value` 切分 |
| D8 `FREE_MEM` / `CPU_LOAD` 为 `N/A` | 变成 `{"set": false, "infinite": false, "number": 0}`，`set` 就是判据 |
| D6 `sacct` 三处列宽截断 | 没有列宽 |
| 字段位置 / 列宽假设 | 按 key 取，不按位置 |

**没解决（原样保留）：**

| 保留的陷阱 | 说明 |
|---|---|
| D3 GRES 的 `(S:0-1)` socket 后缀 | `gres` 字段**仍然是字符串**：`"gpu:nvidia_h100_80gb_hbm3:2(S:1)"` |
| D4 单节点多机型 | 仍是逗号分隔的同一串：`"gpu:a:3(S:0),gpu:b:2(S:1)"` |
| TRES 通用键与带型号键并存 | `tres` 仍是 `"cpu=128,mem=450091M,billing=128,gres/gpu=2,gres/gpu:nvidia_h100_80gb_hbm3=2"` |

**新增的坑（JSON 独有，规则见 §3.0）：**

- 数值字段普遍包一层 `{set, infinite, number}`
- `state` 从单值变成**数组**，且可能多值共存：`["IDLE","DRAIN"]`
- `gres_used` 与 `gres` 语法相同、语义不同：括号里一个是 `(S:...)` 另一个是 `(IDX:...)`

一句话总结：**JSON 把"找到字段"的难度降到零，"理解字段内容"的难度一点没变。** 库存计算的核心仍然是 §4、§5 那套字符串与状态规则。

## 3. 各数据源解析契约

### 3.0 JSON 输出的四条通用规则（v1.3 新增，所有 `--json` 命令都适用）

**① 顶层信封固定是 `{ meta, <数据>, warnings, errors }`**，数据数组的 key 因命令而异：

| 命令 | 数据 key | 每条记录是 |
|---|---|---|
| `sinfo --json` | `sinfo` | 一个「分区 × 状态」分组（**不是节点**，见 §3.1） |
| `scontrol show node --json` | `nodes` | 一个节点 ✅ 逐节点 |
| `squeue --me --json` | `jobs` | 一个作业 |
| `sacct --json` | `jobs` | 一个作业 |

`errors` 数组非空时**必须当失败处理**，哪怕退出码是 0。这条和"解析失败必须保留原文"是同一个原则：宁可报错，不可静默给半份数据。

**② 数值字段普遍包了一层 `{ set, infinite, number }`**：

```json
"free_mem": { "set": true,  "infinite": false, "number": 149526 }
"cpu_load": { "set": false, "infinite": false, "number": 0 }
```

- `set: false` = 这个值没有（等价于旧格式的 `N/A`）→ 显示"—"，不参与排序
- `infinite: true` = 无上限（例如时间上限）→ 不要当 0，也不要当有限大数
- **永远不要 `Number(x)` 直接转**，会得到 `NaN`

统一解包：

```ts
type OptNumber = { set: boolean; infinite: boolean; number: number }

export function optNumber(v: OptNumber | number | null | undefined): number | null {
  if (typeof v === 'number') return v
  if (!v || !v.set) return null
  return v.number
}
```

**③ 时间字段是 Unix 秒（整数）**，`0` 表示"未设置 / 尚未开始"。不要当毫秒，也不要当字符串。

**④ 字符串里只有 `/` 被转义成 `\/`**，`JSON.parse` 直接还原，不用手工 replace。

### 3.1 sinfo

> **v1.3：`sinfo --json` 在本集群可用，但它不是逐节点的。** 下面分两条路径写清楚：
> JSON 路径用于分区概览，逐节点库存数据请走 `scontrol show node --json`（§5.4）。

#### 3.1.1 JSON 路径的形状（先看这个）

`sinfo --json` 返回的 `sinfo` 数组，**每一条是一个「分区 × 状态」分组**，不是一台机器：

```json
{
  "meta": { "Slurm": { "version": { "major": 23, "minor": 2, "micro": 3 }, "release": "23.02.3" } },
  "sinfo": [
    {
      "port": 6818,
      "partition": { "name": "compute" },
      "node": { "state": ["DOWN", "DRAIN", "NOT_RESPONDING"] },
      "nodes": { "allocated": 0, "idle": 0, "other": 1, "total": 1,
                 "hostnames": [], "addresses": [], "nodes": ["node02"] },
      "cpus": { "allocated": 0, "idle": 0, "other": 128, "total": 128 },
      "memory": { "minimum": 515609, "maximum": 515609, "free": { "minimum": { "set": false, ... } } },
      "gres": { ... }
    }
  ],
  "warnings": [], "errors": []
}
```

能拿到：分区名、该组节点的**状态数组**、节点名列表（`nodes.nodes`）、CPU/内存的 min-max 聚合、分区级 gres。

**拿不到**：逐节点的 GPU 总数与已用数。一台机器若有两种卡（D4），在聚合里会被压成一条，无法还原"哪台机器几张什么卡"。

所以 `sinfo --json` 的定位是**分区概览 / 状态分布**，不是库存真值。库存真值走 `scontrol show node --json`。

#### 3.1.2 固定格式（降级路径）

仅当能力探测判定 `sinfoJson === false` 时才走。

**实测样本**（已截取）：

```
NODEL       STATE CPUS(A/I/O/T) CPU_LOAD FREE_MEM MEMORY  GRES
node01      mix   36/92/0/128   4.56     110195   450091  gpu:nvidia_h100_80gb_hbm3:2(S:1)
node02      drain 0/0/128/128   0.02     N/A      515609  gpu:nvidia_h100:2(S:0-1)
node13      mix   12/28/0/40    3.23     13922    125000  gpu:tesla_v100s-pcie-32gb:3(S:0),gpu:tesla_v100-sxm2-32gb:2(S:1)
node15      drain 0/0/48/48     N/A      N/A      515624  gpu:a100-pcie-40gb:8(S:0-1)
```

**字段**

| 列 | 含义 | 类型 | 坑 |
|---|---|---|---|
| NODEL | 节点名 | string | 可能被 `%5N` 截断（本集群都是 5 字符，暂不触发） |
| STATE | 状态 | enum | 见下表 |
| CPUS | 已分配/空闲/其他/总数 | 4 元组 | 以 `/` 分隔，四段都要取 |
| CPU_LOAD | 负载 | float **或 N/A** | node15 实测为 N/A |
| FREE_MEM | 空闲内存 MB | int **或 N/A** | node02、node15 实测为 N/A |
| MEMORY | 总内存 MB | int | 单位是 MB，不是 GB |
| GRES | GPU 资源 | **复合结构** | 见下 |

**GRES 语法**（这是最容易写错的地方）

```
gpu:<name>:<count>(<socket-binding>)[,gpu:<name>:<count>(...)]*
```

- 单个：`gpu:nvidia_h100:2(S:0-1)` → name=`nvidia_h100`, count=2
- 多个：`gpu:tesla_v100s-pcie-32gb:3(S:0),gpu:tesla_v100-sxm2-32gb:2(S:1)` → **一台机器上有两种卡**
- 名称里含 `-` 和 `_`（`a100-sxm4-80gb`、`nvidia_a100_80gb_pcie`），不能按分隔符切
- `(S:0-1)` 是 socket 绑定信息，与空闲/分配无关，**必须丢弃**。误当成数量是典型错误

推荐按全局匹配 `gpu:([^:,()]+):(\d+)` 提取所有 `(name, count)` 对。

**v1.3：这条规则在 JSON 路径下照样要用。** `scontrol show node --json` 的 `gres` 字段仍是同一个字符串
（实测值 `"gpu:nvidia_h100_80gb_hbm3:2(S:1)"`），`gres_used` 是它的"已用"版本
（`"gpu:nvidia_h100_80gb_hbm3:1(IDX:0)"`）。所以这个正则和下面这些坑都不是白写的。

**状态枚举**：`idle` / `mix` / `alloc` / `drain` / `drng` / `down` / `comp` / `fail`。
可售集合只有 `idle` 和 `mix`。

> **v1.3 补充：JSON 里 `state` 是数组，而且可能多值共存。**
> 实测样本：`["ALLOCATED"]`、`["IDLE"]`、`["IDLE","DRAIN"]`、`["DOWN","DRAIN","NOT_RESPONDING"]`。
>
> 判断规则：**只要数组里出现任何一个"阻断"状态，整台机器就不可用**（`DRAIN` 优先级高于 `IDLE`）。
> 写成 `state.includes('IDLE')` 会把 `["IDLE","DRAIN"]` 判成可售——这正是 §0② 那个"drain 节点被当空闲资源卖出去"的
> bug，只是换了个更容易踩的形态。
>
> ⚠️ **"可售集合只有 idle 和 mix" 这句话只适用于 `sinfo`。** 套在 `scontrol` 数据上会把 16 台砍到 1 台，
> 因为这个集群的 `scontrol` 从不返回 `MIXED`，只要有作业就是 `ALLOCATED`，而 `ALLOCATED` 的机器照样有空闲卡。
> `scontrol` 路径请用"阻断/有货"两个独立概念，详见 §5.1 的 Step 4。

### 3.2 scir-watch -s

**实测样本**：

```
╭───────────────────────┬──────┬────────┬───────────┬───────────┬─────────────╮
│ GPU TYPE              ┆ COST ┆ HOST   ┆ FREE GPUs ┆ FREE CPUs ┆ FREE MEMORY │

**四个解析难点**

1. **Unicode 制表符**：`│` `┆` `╭` `╪` `┼` `╌` `╞` `╡`。分隔符在表头里甚至是混用的（第一列用 `│`，后面用 `┆`）。按 `[│┆]` 切分后 trim。
2. **合并单元格**：一个机型占多行，后续行的 GPU TYPE 和 COST 是**空白**。必须做 carry-forward：遇到空值就沿用上一行的值。
3. **内存带单位**：`102G`、`10G`、`74G`。解析成数字再统一到 GB，不要字符串比较。
4. **行分隔线**：`├╌╌╌...┼╌╌╌...┤` 要跳过，否则会切出一堆空字段。

**语义推断（待确认）**：`sinfo` 里有 10 种 GPU 型号，`scir-watch` 只列了 3 种，且这 3 种的空闲数都 ≥1。**推断它只显示有空卡的机型**。若成立，GPU 商店必须合并 `sinfo`（全量机型 + 总数）与 `scir-watch`（单价 + 空闲数），否则"售罄"的机型会从界面上消失，用户以为集群没有 A100 80G。

⚠️ **不带参数时输出完全一样**（实测 `scir-account` 与 `scir-account -d` 都是这一行）。
所以 `-d` 不是必需项，但写上更明确，也避免哪天默认行为变了。

#### 3.3.2 消耗明细：`details`

**实测样本**（默认形态，5 列）：

```
╭────────┬────────────┬──────┬────────────┬────────╮
│ JID    ┆ Job Name   ┆ Time ┆ Time Limit ┆ Points │
╞════════╪════════════╪══════╪════════════╪════════╡
│ 208896 ┆ train      ┆ 0.00 ┆ 2.00       ┆ 0.00   │
├╌╌╌╌╌╌╌╌┼╌╌╌╌╌╌╌╌╌╌╌╌┼╌╌╌╌╌╌┼╌╌╌╌╌╌╌╌╌╌╌╌┼╌╌╌╌╌╌╌╌┤
│ 211439 ┆ notifytest ┆ 0.00 ┆ 0.08       ┆ 0.01   │
╰────────┴────────────┴──────┴────────────┴────────╯
Total: 5200.00 Used: 0.02 Avail: 5199.98
```

`-r` 多一列 `Resources`，**表头同时变成 `Time(H)` / `Time Limit(H)`**：

```
│ JID    ┆ Job Name   ┆ Resources                          ┆ Time(H) ┆ Time Limit(H) ┆ Points │
│ 208896 ┆ train      ┆ node(0)=1, billing(0)=4, cpu(0.05)=4, gpu:tesla_v100-sxm2-16gb(4)=1, mem(0)=16384 ┆ 0.00 ┆ 2.00 ┆ 0.00 │
```

**五个必须按表头解、不能写死列号/位置的坑**

| # | 坑 | 后果 |
|---|---|---|
| 1 | 5 列 / 6 列两种形态 | 写死 `cells[4]` 在 `-r` 下拿到的是 `Time Limit`，不是 `Points` |
| 2 | `Resources` 列里**有逗号** | 按逗号切行会把 1 条拆成 6 条 |
| 3 | `Resources` 里各字段**顺序每次不同** | 实测同一个作业两次输出，`billing`/`cpu`/`gpu` 的排列都不一样（看起来是 HashMap 迭代序）。**只能扫 `k=v`，不能按位置取** |
| 4 | `billing` 的 key 是 `billing(0)` **带括号** | 用 `key === 'billing'` 全等比较永远拿不到值（第一版真踩了） |
| 5 | 表头 `Time` 不带 `(H)` 时**单位仍是小时** | 按表头推断单位会错。实测 `0.17` 对应 10 分钟的作业 |

**`│` 与 `┆` 混用**：表头里第一列用 `│`（U+2502）、后面用 `┆`（U+2506）。按 `[│┆]` 一起切，切完去掉首尾各一段空串。
行分隔线 `├╌╌┼╌╌┤` 要跳过（判据：整行除了框线字符没有字母/数字/汉字）。

**⚠️ `details` 没有时间过滤参数。** 它只有 `-r` / `-d` 两个开关，**一次返回账号下全部可查的作业**（实测 19 条 / 43 行）。
所以它**不适合轮询**——按 5 分钟轮询等于每 5 分钟重传一份一模一样的表。只在用户打开面板时按需拉一次。

**⚠️ `Time` 与 `Time Limit` 的单位都是小时**，不是 SLURM 的 `MM:SS`。实测 `211291`（`streamtest`）是 `0.01 / 0.17`，
对应跑了约 36 秒、申请 10 分钟。

**⚠️ 逐条相加 ≠ 表尾 `Used`，这是正常的。**
实测 19 条里只有 1 条是 `0.01`、其余 `0.00`，相加 `0.01`，而表尾 `Used: 0.02`。
原因是**每条只保留 2 位小数，平台自己已经四舍五入过一轮**。
界面必须把两个数分开列，且**不能提示"数据不一致"**——那会让用户以为程序算错了。

#### 3.3.3 送点数：`transfer`

```
Usage: scir-account transfer --points <POINTS> --target <TARGET> --month <MONTH>

Options:
  -p, --points <POINTS>  how much points you want to give
  -t, --target <TARGET>  username of the user you want to give
  -m, --month <MONTH>    how many month it will expired (the day 1 after n months)
```

**三个参数全部必填**，少一个远端报 `error: the following required arguments were not provided`（exit=2）。

**最大障碍：它要 LDAP 密码，而且是从 stdin 读的。**

实测：`transfer` 会打印 `Your Password: `，然后从 **stdin** 读密码。
本应用的 `Session.exec` 通道没有 tty、stdin 是空的，所以拿到 EOF 就当空密码：

```
$ scir-account transfer -p 0 -t nosuchuser000 -m 1
Your Password:
Error: AuthFailed            # exit=1
```

用伪终端（`script -qec`）重定向也一样，因为 stdin 还是空的。
**必须走真正的 PTY 并等提示串出现后再写**，见 `src/main/ssh/interactive.ts`。

**⚠️ 走 PTY 之后最致命的坑：不能用 PTY 的退出码判成功。**

`openShell` 开出来的是一条**登录 shell（bash）**。我们写进去的字符串是**键盘输入**，
bash 读一行、执行、回到提示符——**bash 自己不会退出**。所以：

- `scir-account` 的退出码是**命令**的退出码，PTY 的 `onClose` 只在 bash 退出时触发；
- 于是「转账成功」也会一直挂到超时，然后被判成**失败**；
- 用户看到失败会**再转一次**。钱已经出去了，这是花真钱才能发现的 bug。

解法：在命令后面追加**哨兵**，把 `$?` 打进输出，用「看到哨兵」作为唯一可靠的结束信号。

```bash
scir-account transfer --points=10 --target=user01 --month=1; printf '\n%s%s\n' '__HPC_DONE_<nonce>__:' "$?"
```

三个细节都不能省：

| 细节 | 为什么 |
|---|---|
| 用 `;` 不用 `&&` | 命令失败时也要打哨兵，否则失败场景只能等超时 |
| 带随机 `nonce` | 否则命令自己的输出里可能出现同样文本，误判成结束 |
| 成功判据 = 见哨兵 + `$?` 为 0 + 输出无 `Error:` | 单看退出码防不住「exit 0 但打了 Error」的 CLI 退化 |

反过来，**不能**用「输出里有没有 Success 字样」判成功——成功输出格式没有保证，正面关键词会误杀。

**两个错误形态要分开看**，因为用户下一步完全不同：

| 输出 | 含义 |
|---|---|
| `Error: AuthFailed` 或 `Error: LdapError(LdapResult { rc: 49, ... })` | 密码不对 / 账号没权限。rc=49 是 LDAP 的 `invalidCredentials` |
| `error: unexpected argument '-5' found` | 点数传了负数，clap 把它当成未知参数了。**必须在本地先拦住**，否则用户完全看不懂 |

**平台侧的 RPC 方法名**（从二进制 `strings` 里读出来的）：

```
account_account  account_account_can_transfer  account_used  account_available
account_gpucost  account_cpulimit  account_transfer
```

`account_account_can_transfer` 说明**服务端有额度校验**，能不能转、能转多少由平台判断，不必在客户端猜。
`ldap:///home/.../slurm-scir/src/auth.rs` 与 `ou=People,dc=cluster,dc=com` 进一步确认是 LDAP 认证。

**⚠️ 没有"向某人要点数"的反向命令。** `transfer` 只有"我付出"这一个方向。
所以 UI 上"让别人送我"只能做成**生成一段给对方的说明**（填好自己的账号名），不能做成一个按钮。

### 3.4 sacct

**实测样本**：

```
JobID        State       JobName    Elapsed  AllocTRES
203248      FAILED   exp-a-001+   00:01:25 billing=8+
203263  CANCELLED+   exp-a-001+   00:05:05 billing=8+
203343  CANCELLED+   exp-a-001+   00:00:00
```

**三处截断，全部致命**：

| 字段 | 实测值 | 问题 |
|---|---|---|
| State | `CANCELLED+` | 真实值可能是 `CANCELLED by 12345`，被 `%10` 砍断 |
| JobName | `exp-a-001+` | `%15` 砍断，无法区分 `case-retention` 和 `case-return` |
| AllocTRES | `billing=8+` | 完整值应是 `billing=8,cpu=8,gres/gpu=1,mem=...`，**GPU 数直接丢了** |

第三行还有空 AllocTRES（0 秒就被取消、从未分配）。

**必须换格式。方案已经定了：用 `sacct --json`。**

集群是 23.02.3，而 `--json` 从 20.02 就有，所以不用纠结、不用试探，直接走结构化路径。三处截断问题一次性消失。

降级路径（仅在探测到 JSON 不可用时启用）：
`sacct --parsable2 --noheader -o JobID,State,JobName,Elapsed,AllocTRES%200`
——`--parsable2` 用 `|` 分隔且不按列宽截断，`%200` 给足 TRES 宽度。

**两条实现注意**

- JSON 输出是 `{"jobs": [...]}`，一次可能几 MB。**流式解析，只取需要的字段**，不要 `JSON.parse` 整个字符串再筛——历史记录攒到几千条时这会卡住主进程。
- `--json` 与 `-o`、`-P` 互斥。探测到 JSON 可用后，不要再混用表格参数。

**绝不要用默认的 `--format` 列宽**——这是本文档里唯一一条"绝对禁止"，因为它不会报错，只会安静地给你错数据。

### 3.6 存储配额（已实测）

**真实输出**：

```
Block Limits                                    |     File Limits
Filesystem type         blocks      quota      limit   in_doubt    grace |    files   quota    limit in_doubt    grace  Remarks
gpfs01     USR          90.72G         6T         9T     1.428G     none |   371288 6291456  9437184       88     none
```

**结构**：一次返回**两个独立配额**，用 `|` 分隔。

| 段 | 列 | 含义 |
|---|---|---|
| 前置 | Filesystem / type | `gpfs01` / `USR`（用户级配额） |
| Block Limits | blocks / quota / limit / in_doubt / grace | 已用 / 软 / 硬 / 未结算 / 宽限期 |
| File Limits | files / quota / limit / in_doubt / grace | 同上，单位是**文件个数** |

**解析要点**

1. **先按 `|` 切两段**，再各自按空白切。整行 12 个字段混在一起看不出结构。
2. **单位带后缀**：`90.72G`、`6T`、`1.428G`。files 列是**裸整数**（`371288`），没有后缀。两套单位规则不能混用。
3. **`in_doubt` 非零是正常的**（这里是 1.428G）。它表示"有写入尚未结算"，不是错误。UI 上标注"数据略有滞后"即可，不要弹警告。
4. **`grace` 平时是 `none`**，超额后变成 `7 days` 之类，过期变 `expired`。这一列才是真正该报警的信号。
5. **`Remarks` 可空可非空**。按位置取前 N 个 token，不要断言字段总数。
6. 可能出现多行（多个文件系统）。逐行解析，不要只取第一行。

#### 被忽略的第二道配额：文件数

这是这次采集最重要的发现。

`quota = 6,291,456` 和 `limit = 9,437,184`，正好是 **6M / 9M**——与 6T / 9T 同步设定。也就是说你的配额是**双维度的**：容量和文件数各有一道 6/9 的软硬线。

你当前的状态：

| 维度 | 已用 | 软额度 | 占比 | 剩余 |
|---|---|---|---|---|
| 容量 | 90.72 GB | 6 TB | 1.5% | 约 5.9 TB |
| 文件数 | 371,288 | 6,291,456 | 5.9% | 约 592 万 |

平均每个文件 244 KB。按这个平均值推算：

- 容量还能放 `6 TB ÷ 244 KB ≈ 2,580 万`个文件
- 但文件配额只允许 **629 万**个

**所以文件数会比容量早约 4 倍见底。** 按当前的文件大小分布，用到 1.5 TB 左右文件数就满了，而容量还剩 4.5 TB。

两种极端情况对比：

| 存法 | 占用容量 | 占用文件数 | 结果 |
|---|---|---|---|
| 600 万个 10 KB 的 JSON | 60 GB（1%） | 95% | **文件配额先爆** |
| 100 个 40 GB 的权重 | 4 TB（67%） | 0.002% | 毫无压力 |

**这个结论改变了两件事**：

1. **配额面板必须并排显示两个维度**，并明确算出"哪个先到"。只显示容量会给出错误的安全感——用户看着 1.5% 的占用，实际快要写不进去了。
2. **打包小文件不只是性能优化，也是省 inode**。webdataset / parquet / tar 一次同时解决 GPFS 元数据压力和文件数配额，这两个收益是叠加的。

对 `exhaustionDate` 的估算也要分开算：容量按近期写入速率外推，文件数按近期新增文件速率外推，取更早的那个作为预警时间。

**降级链**（第 1 条实测可用，保留后三条兜底）：

| 顺序 | 探测命令 | 命中说明 |
|---|---|---|
| 1 | `/usr/lpp/mmfs/bin/mmlsquota --block-size auto` | IBM Spectrum Scale ✅ 已确认 |
| 2 | `lfs quota -h ~` | Lustre |
| 3 | `quota -s` | NFS + quota 服务 |
| 4 | 都不中 | 显示"无法读取配额" + 三条命令的原始输出 |

配额数据 5 分钟拉一次就够，不需要高频。

## 4. 型号归一化

实测到的 10 种 GRES 名称，命名规则完全不统一：有的带 `nvidia_` 前缀，有的带 `tesla_`，有的裸名；分隔符 `-` 和 `_` 混用。

**不能做精确匹配**，必须用"包含关键 token"的模糊归一：

| 原始 GRES 名称 | 归一 ID | 显示名 | 显存 | 备注 |
|---|---|---|---|---|
| `nvidia_h100_80gb_hbm3` | `h100-80-sxm` | H100 80G SXM | 80 GB | HBM3 |
| `nvidia_h100` | `h100-80` | H100 80G | 80 GB | **不合并**，见下 |
| `a100-sxm4-80gb` | `a100-80-sxm` | A100 80G SXM4 | 80 GB | NVLink 带宽最高 |
| `nvidia_a100_80gb_pcie` | `a100-80-pcie` | A100 80G PCIe | 80 GB | |
| `a100-pcie-40gb` | `a100-40-pcie` | A100 40G PCIe | 40 GB | |
| `nvidia_a800_80gb_pcie` | `a800-80-pcie` | A800 80G PCIe | 80 GB | **NVLink 被削减**，多卡训练需提示 |
| `tesla_v100-sxm2-32gb` | `v100-32-sxm` | V100 32G SXM2 | 32 GB | |
| `tesla_v100s-pcie-32gb` | `v100s-32-pcie` | V100S 32G PCIe | 32 GB | V100S 是 V100 的增强版 |
| `tesla_v100-sxm2-16gb` | `v100-16-sxm` | V100 16G SXM2 | 16 GB | 最便宜 |
| `nvidia_rtx_a6000` | `a6000-48` | RTX A6000 | 48 GB | Ampere 工作站卡 |

**归一失败的兜底**：显示原始名称 + 一个"未识别"标记，不要隐藏。宁可难看，不可丢失——用户至少能看到集群上有这么个东西。

**关于两种 H100 写法的处理原则：不合并。**

`nvidia_h100_80gb_hbm3`（node01）和 `nvidia_h100`（node02、node04）看起来像同款，但没有证据。它们可能是 SXM 与 PCIe 的差别，也可能是不同批次。**合并错了比不合并更糟**——价格、显存带宽、NVLink 都可能不同，用户按错误的信息选了机器，损失的是真实算力。

所以：两条独立记录，各自显示原始名称。如果将来证明是同一物理型号，再改归一表即可，这是一行配置的改动；反过来，如果一开始合并了，要排查"为什么这台的训练速度是那台的一半"会非常难受。

同理，归一表要设计成**外部配置文件**而不是写死在代码里，这样发现新机型时改配置就行，不用改代码、不用重新打包。

**A800 的提示很重要**：显存和 A100 一样是 80G，但 NVLink 带宽被削减（约 400 GB/s vs 600 GB/s）。做多卡训练的人如果不知道这点，会以为是集群性能问题。价格相同时应在卡片上标注。

## 5. 库存合并逻辑

### 5.0 一条原则：库存真值不依赖 `scir-watch`

「它是不是只列有空闲机型、是不是有缓存」这个问题答成"不清楚"，本身就是有用的信息——**它意味着不能把正确性建立在它上面**。

所以重新划分职责：

| 数据源 | 负责 | 明确不负责 |
|---|---|---|
| `sinfo -N` | 节点清单、机型、总卡数、状态、空闲 CPU/内存 | 空闲 GPU 数 |
| `scontrol show node -o` | 每个节点已分配的 GPU 数 | 单价 |
| `scir-watch -s` | **单价（唯一职责）** | 库存真值 |

空闲 GPU 由 `total − allocated` **自己算**，不从 `scir-watch` 抄。

**为什么这样更稳**：如果它是缓存且有几分钟延迟，"空闲 1 张"可能早就没了，用户点进去排队——这种挫败感会直接摧毁信任。而 `sinfo` + `scontrol` 是调度器的直接视图，实时且权威。

代价是每次多跑一条 `scontrol`。但这一条命令一次返回所有节点，成本可以忽略。

### 5.1 管线（v1.3：一条命令就够）

```
Step 1  scontrol show node --json  → 逐节点拿到全部原料：
                                     state[] / gres(总) / gres_used(已用)
                                     / cpus / alloc_cpus / real_memory / free_mem / partitions
Step 2  解析 GRES 字符串            → Map<型号, 数量>，总卡与已用各一份
Step 3  按型号分别算               → free[型号] = gres.total[型号] − gres_used.total[型号]
Step 4  过滤                       → 状态里出现任何"阻断"状态即整台剔除（见下）
Step 5  合并价格                   → 按机型左连接 scir-watch 的单价
Step 6  聚合                       → 按归一机型汇总 total / free / 最低价
```

#### Step 4 的规则变了：从"必须 idle/mix"改成"不能被阻断"

v1.2 写的是「`state ∉ {idle, mix}` 移出可售集合」。**这条规则套在 `scontrol` 数据上会把商店清空。**

实测 16 台机器里 11 台报 `ALLOCATED`，**一台 `MIXED` 都没有**——这个集群的 `scontrol` 只要有作业就跑 `ALLOCATED`，不再区分"部分占用"。而这 11 台里大部分仍有空闲卡：

```
node01  state=["ALLOCATED"]  gres=2  gres_used=1   → 还有 1 张可卖
node05  state=["ALLOCATED"]  gres=7  gres_used=6   → 还有 1 张可卖
```

按旧规则过滤，16 台只剩 1 台，而 `scir-watch` 同时显示有 9 台机器在出卡——**两边直接打架**。

正确口径拆成两个独立概念，别再混着用：

| 概念 | 判据 | 用途 |
|---|---|---|
| **阻断**（blocked） | 状态里出现 `drain` / `draining` / `down` / `completing` / `fail` / 未知 | 整台机器不计入库存 |
| **有货** | `free[型号] > 0`（Step 3 算出来的） | 决定商店里这张卡显不显示 |

`ALLOCATED`、`MIXED`、`IDLE` 都**不阻断**；有没有货只看 free。`["IDLE","DRAIN"]` 因为含 `DRAIN` 而阻断——这条不能松，它就是 §0② 那个坑。

> **`isSellable`（{idle, mix}）保留给 `sinfo` 的降级路径**，别用在 scontrol 数据上。实现见 `src/main/domain/node-state.ts`。

实测校验：按新口径算出的空闲卡数，与 `scir-watch` 的 FREE GPUs 逐型号完全一致（v100-16g 16 张、a100-80-pcie 5 张、v100s 2 张、a800 2 张、h100 1 张、a6000 1 张、a100-40 1 张）。

**为什么 Step 1 从两条命令变成了一条**：v1.2 的设计是「`sinfo -N` 拿机型/总卡/状态，`scontrol` 拿已分配」，因为当时认为 `scontrol --json` 不可用、只能解析它的 `-o` 单行格式。实测 JSON 可用后，`state`、`gres`、`gres_used`、`free_mem`、`alloc_cpus` 全在同一个对象里，一次调用就齐了——少一次往返，也少一次两源不一致的可能。

代价是体积：实测 16 节点约 52 KB（≈3.3 KB/节点）。节点数上千时会到几 MB，那时再退回「`sinfo --json` 概览 + 按需查单节点」的两段式。

**Step 3 必须按型号分别算**，不能先合并总数再减。实测 node10 一台机器两种卡：

```
gres      = gpu:tesla_v100s-pcie-32gb:3(S:0),gpu:tesla_v100-sxm2-32gb:2(S:1)
gres_used = gpu:tesla_v100s-pcie-32gb:1(IDX:0),gpu:tesla_v100-sxm2-32gb:2(IDX:3-4)
→ free    = { v100s-32-pcie: 2, v100-32-sxm: 0 }
```

若先算总数（5 − 3 = 2）再摊到型号，会得出"两种卡都还有货"的错误结论。

**降级路径**（探测到 `scontrolJson === false` 时）：回到 v1.2 的三步，`sinfo -N` + `scontrol show node <node> -o`，规则见 §5.4 末尾。

### 5.2 双源交叉验证

`scir-watch` 的 FREE GPUs 虽然不能当准，但可以做**一致性检查**：

| 两源差值 | 含义 | 处理 |
|---|---|---|
| ≤ 1 | 正常 | 用自己算的，不提示 |
| > 1 | 它有缓存，或口径不同 | 用自己算的，卡片上标注"数据源不一致" |

这样不会静默给出错数据——用户看到警告就知道该刷新，而不是等到作业排不上队才发现。

### 5.3 关键细节

- **合并键必须是 `(host, 机型)`**，不能只用 `host`。因为 `node13` 一台机器上有两种卡（3 张 V100S + 2 张 V100 32G），只按 host 会串味。
- **总数要排除 drain 节点**。否则"可用 1 / 总计 8"里的 8 包含了正在排空的机器，用户会疑惑为什么永远排不到。
- **`scir-watch` 里没有的机型 = 价格未知**，不是"不存在"，更不是"售罄"。这些机型仍要出现在商店里，价格位显示"未知"，可提交（实际扣费由调度器算）。
- **价格可人工覆盖**：归一表配置文件里留一个 `price:` 字段。`scir-watch` 挂了或某机型没报价时，用手填值兜底。这既是容错，也方便将来价格调整。

**派生字段**

| 字段 | 计算 |
|---|---|
| `freeRatio` | free / total，用于"最快能排到"排序 |
| `pointsPerHour` | 单价 × 卡数 |
| `affordableHours` | 余额 / pointsPerHour，用于"你的余额够跑 X 小时" |
| `vramPerPoint` | 显存 / 单价，用于"性价比"排序 |

### 5.4 实测确认：scontrol 的 TRES 格式

> **v1.3：优先走 `scontrol show node --json`。** 下面的 `-o` 单行格式保留为降级路径（探测到 `scontrolJson === false` 时才用）。
>
> **JSON 字段对照**（全部实测确认）：
>
> | `-o` 字段 | JSON 字段 | 类型 | 说明 |
> |---|---|---|---|
> | `NodeName` | `name` | string | 节点名 |
> | `State` | `state` | **string[]** | 可能多值共存，见 §3.1 |
> | `Gres` | `gres` | **string** | 仍是 `gpu:<型号>:<数>(S:...)`，**不是结构体** |
> | —（`-o` 没有对应物） | `gres_used` | **string** | 已用卡数与 `(IDX:...)` 列表，**算空闲就靠它** |
> | `CfgTRES` | `tres` | **string** | `k=v,k=v` 格式 |
> | `AllocTRES` | `tres_used` | **string** | 同格式，但**内存单位可能不同**（见下） |
> | `RealMemory` | `real_memory` | number (MB) | |
> | `AllocMem` | `alloc_memory` | number (MB) | |
> | `FreeMem` | `free_mem` | `{set,infinite,number}` | `set:false` 即旧格式的 `N/A` |
> | `CPUTot` | `cpus` | number | |
> | `CPUAlloc` | `alloc_cpus` | number | |
> | `CPUAlloc`(空闲) | `alloc_idle_cpus` | number | 直接就是空闲核数 |
> | `Partitions` | `partitions` | string[] | |
>
> **实测 node10（一台两种卡）的真实值**：
>
> ```
> gres      = "gpu:tesla_v100s-pcie-32gb:3(S:0),gpu:tesla_v100-sxm2-32gb:2(S:1)"
> gres_used = "gpu:tesla_v100s-pcie-32gb:1(IDX:0),gpu:tesla_v100-sxm2-32gb:2(IDX:3-4)"
> tres      = "cpu=40,mem=125000M,billing=40,gres/gpu=5,gres/gpu:tesla_v100-sxm2-32gb=2,gres/gpu:tesla_v100s-pcie-32gb=3"
> tres_used = "cpu=12,mem=48G,gres/gpu=3,gres/gpu:tesla_v100-sxm2-32gb=2,gres/gpu:tesla_v100s-pcie-32gb=1"
> ```
>
> 三个必须记住的坑：
>
> 1. **`gres` 与 `tres` 的型号顺序不一致**：`gres` 里 pcie 在前，`tres` 里 sxm 在前。
>    所以**绝不能按下标配对**，只能按型号名配对。
> 2. **`tres` 与 `tres_used` 的内存单位不同**：`mem=125000M` vs `mem=48G`。
>    同一台机器、同一时刻、同一个量，两种写法。
> 3. **`gres_used` 的括号是 `(IDX:0-1,3-6)`，不是 `(S:0-1)`**。用 §3.1 的
>    `gpu:([^:,()]+):(\d+)` 能同时匹配两者（因为括号被 `[^:,()]` 挡住了），
>    但**语义完全不同**：一个说的是物理插槽绑定，一个说的是哪几张卡被占了。别混用。

**降级路径（`-o` 单行格式）**

真实输出（node01，已截取关键字段）：

```
NodeName=node01 ... Gres=gpu:nvidia_h100_80gb_hbm3:2(S:1) ...
State=MIXED ...
RealMemory=450091 AllocMem=163840 FreeMem=110869 ...
CfgTRES=cpu=128,mem=450091M,billing=128,gres/gpu=2,gres/gpu:nvidia_h100_80gb_hbm3=2
AllocTRES=cpu=36,mem=160G,gres/gpu=2,gres/gpu:nvidia_h100_80gb_hbm3=2
```

三个确认：

1. **TRES 里同时有通用键和带型号键**：`gres/gpu=2` 与 `gres/gpu:nvidia_h100_80gb_hbm3=2`。**带型号的那个正是需要的合并键**——`(host, 机型)` 的设计成立，不用改。
2. **node01 的 `AllocTRES` 显示 2 张卡全被占用**（`total 2 − alloc 2 = 0` 空闲）→ 与 `scir-watch` 根本没列 h100 完全吻合。**此前"它只列有空闲机型"的推断被证实。**
3. **单位有三套**：`RealMemory=450091`（MB）、`AllocMem=163840`（MB）、`AllocTRES=mem=160G`（带后缀）。同一份数据里同一量有三种写法，解析时不要混。

计算规则：`free = CfgTRES["gres/gpu:<type>"] − AllocTRES["gres/gpu:<type>"]`，取带型号的键，**忽略通用键 `gres/gpu`**（它是所有型号的合计，拿来做总数校验可以，做单型号计算会错）。

### 5.5 静默陷阱：状态字段大小写不同

同一个状态，两个命令给你两种写法：

| sinfo | scontrol | 规范枚举 | 可售 |
|---|---|---|---|
| `idle` | `IDLE` | idle | 是 |
| `mix` | `MIXED` | mixed | 是 |
| `alloc` | `ALLOCATED` | alloc | 否 |
| `drain` | `DRAIN` | drain | 否 |
| `drng` | `DRAINING` | draining | 否 |
| `down` | `DOWN` | down | 否 |
| `comp` | `COMPLETING` | completing | 否 |
| — | `FAIL` | fail | 否 |

> **v1.3：JSON 路径下拿到的已经是 `string[]`（如 `["IDLE","DRAIN"]`）。**
> 映射函数要能吃 `string | string[]`：先逐项归一成规范枚举，再判断「是否存在任一不可售状态」。
> 不要图省事取 `state[0]`——`["IDLE","DRAIN"]` 的第一项恰好就是那个会骗人的 `IDLE`。

注意 `alloc` 和 `ALLOCATED` **不是大小写差异，是词形差异**——`toLowerCase()` 解决不了。

如果过滤条件写成 `state in ['idle','mix']`，而某条代码路径喂进去的是 `MIXED`，结果就是**所有节点被判为不可售，GPU 商店一片空白，而且不报错**。这类 bug 极难定位，因为每个函数单独看都是对的。

规则：
- 定义规范枚举，两个来源都映射过去，映射函数只有一份
- 过滤逻辑只吃规范枚举，不吃原始字符串
- 单测里必须有一条：`mix` 与 `MIXED` 映射到同一个值

### 5.6 解析陷阱：scontrol 的值里带空格

> **v1.3：这一节只在降级路径（`-o` 单行格式）下适用。** 走 JSON 时不存在这个问题——
> 但下面这条正则的教训仍然通用：**按"下一个 key=" 切分，而不是按空格切分**，
> §5.4 里 `tres="cpu=40,mem=125000M,..."` 那种逗号分隔的串同理。

```
OS=Linux 5.15.0-186-generic #196-Ubuntu SMP Sat Jun 20 16:09:34 UTC 2026  RealMemory=450091
```

`OS` 这个值里有 5 段不含 `=` 的内容。用 `split(' ')` 再 `split('=')` 会把 `5.15.0-186-generic` 当成新键，或者直接抛异常。

**正确做法**：以"空白 + 下一个 `key=`"为边界切分：

```
/(?:^|\s)(\w+)=((?:(?!\s+\w+=).)*)/g
```

**注意不能图省事写成 `(\w+)=([^=]*)`** —— 因为 `CfgTRES=cpu=128,mem=450091M,...` 的**值里本身就有 `=`**，会被提前截断成 `CfgTRES=` 空值加一堆垃圾。

这两条（5.5 和 5.6）是本层最容易写出"能跑但结果是错的"的地方。

### 一个需要回头修改的地方

`HPC存储使用指南_6TB.html` 那份文档是在不知道文件数配额的情况下写的，里面所有的容量规划都只算了一个维度。§3.6 发现的「文件数比容量早约 4 倍见底」实际上改变了那份文档的核心结论之一。
