## 0. 交接摘要

**这个项目是什么**：一个 Windows 桌面客户端，把 HPC 的 SSH + SLURM 命令行包装成图形界面——拖拽传文件、按卡片租显卡、一屏看资源和配额。

**现在到哪了**：Phase 0–4 的功能都已落地并在真集群上验证；2026-11 做了一轮完整的界面审查与视觉收敛
（详见 §4「界面审查与视觉收敛」）。当前 `npm test` **722 条全绿**、`npm run build` 通过。

**改界面代码前先看两件事**：① `tailwind.config.js` 顶部的 token 说明——
字号/颜色/圆角/阴影/断点只能用语义名，写死数值会被 `tests/design-tokens.test.ts` 拦下；
② 改完任何 `window.hpc` 方法，`src/shared/api-version.ts` 的 `PRELOAD_API_VERSION` 必须 +1。

**最重要的一条约束**：平台没有 API，所有远程数据只能靠解析 CLI 文本。整个架构都是围绕这个限制设计的。

**不要重新讨论的事**：Electron vs Tauri、要不要做窗口管理器、要不要在集群上装服务端。这三条已经算过成本，见 `README.md` 的「三条不可动摇的决策」。

## 2. 关键模块职责

### 2.1 连接层 `src/main/ssh/`

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `pool.ts` | 按 profile 维护连接，复用、重连 | **一个 profile 只保持一个 TCP 连接**，所有操作共享。SSH 握手 3-5 次往返，30ms RTT 下就是 150ms 白等 |
| `session.ts` | 封装 exec / SFTP / shell | 并发 exec 要有信号量，**默认 4-6**，不要超过服务端 `MaxSessions`（默认 10） |
| `capabilities.ts` | 探测 JSON 能力 | 结果缓存进 profile。**不能写死**，集群升级后要自动用上 |
| `errors.ts` | 错误归一 | 原始 stderr **必须保留并可在 UI 查看**，这是用户自救的唯一途径 |

### 2.2 解析层 `src/main/adapters/`

这是全项目最脆的部分，规则全部在 `docs/03`。

| 模块 | 数据源 | 输出模型 | 难度 |
|---|---|---|---|
| `node-detail.ts` | `scontrol show node --json` | `Node[]`（逐节点） | 中。**库存真值**。JSON 好取字段，但 `gres` 仍是字符串，且 `state` 是数组 |
| `sinfo.ts` | `sinfo --json`（降级：`sinfo -N -o`） | 分区概览 | 降级项。**本集群 JSON 可用，暂不必写** |
| `squeue.ts` | `squeue --me --json` | `Job[]` | 低（JSON），注意 `{set,infinite,number}` 解包 |
| `sacct.ts` | `sacct --json` | `JobHistory[]` | 低（JSON），默认格式会截断 |
| `quota.ts` | `mmlsquota` | `{bytes, files} × {used, soft, hard, grace}` | 中。双维度 + 单位后缀 |
| `points.ts` | `scir-account -d` | `{total, used, avail}` | 最低。单行三浮点 |
| `gpu-price.ts` | `scir-watch -s` | `Map<(host,type), price>` | 中。Unicode 表格 + 合并单元格 |

> **v1.3 变动**：四条命令的 `--json` 实测全部可用（`docs/03` §2.1），原先"最难"的 `sinfo.ts` 降为降级项。
> 但别误读：`gres` / `tres` 在 JSON 里**仍是字符串**，GRES 正则与 `(S:...)`/`(IDX:...)` 的区分照样要写（`docs/03` §2.2、§5.4）。

**Adapter 接口约定**（新 Adapter 照此实现）：

```
parse(raw: string): { ok: true, data: T } | { ok: false, reason: string, raw: string }
```

失败时**必须带上 `raw`**，UI 才能做"查看原始输出"。

### 2.3 领域层 `src/main/domain/`

不碰网络，纯函数，最容易测试。

- `gpu-type.ts` — 型号归一。**归一表要做成外部配置**，发现新机型改配置不改代码。`nvidia_h100` 与 `nvidia_h100_80gb_hbm3` **刻意不合并**。
- `inventory.ts` — 库存管线：`sinfo 总数 − scontrol 已分配`，再剔除 drain。**不要用 scir-watch 的空闲数当准**。
- `job-state.ts` — 状态枚举映射（`mix` ↔ `MIXED` 是词形差异不是大小写）+ 排队原因文案。
- `quota-guard.ts` — 容量与文件数**两条线任一触线即超额**，写入前预检。

### 2.4 传输层 `src/main/transfer/`

| 模块 | 职责 | 状态 |
|---|---|---|
| `engine.ts` | 路由器：算 N / S / avg，按 `docs/02` §2.5 矩阵选引擎，并把决策理由一起给出 | ✅ 策略 A/C（B 命中时降级并告警） |
| `tar.ts` | 打包 → SSH channel → 远端 `tar -x`；解到 `dest.partial` 再改名；传完自动核对 | ✅ 单段版 |
| `sftp.ts` | 单流上下行：`fastPut`/`fastGet` + `.part` 改名 + 大小核对；远端目录递归创建 | ✅ 单流（多流分块属后半段） |
| `queue.ts` | 并发、指数退避重试、**按目标路径加锁**、冲突策略（fail/skip/overwrite/rename） | ✅ 排队中的任务可取消 |
| `progress.ts` | 按 100ms 合并进度再发 IPC | ✅ `ProgressMeter` |

> **tar.ts 目前是单段版**，用来验证链路可行性（`docs/02` §2.2 有实测数据）。
> 分段（2 GB/段）与段级续传还没做——它需要在传输中途落盘段边界，与"多流分块"是同一批工作。
>
> **队列的一个已知限制**：只有排队中的任务能取消；已开始的一次传输无法叫停。
> 要支持它，得把 `fastPut` 换成自己分块读写——这同时也正是断点续传的前提，两件事一起做。

**远程 → 远程的移动必须在服务端 `mv` / `cp`，不走传输引擎。** 这是同类工具最常见的错误。

### 2.5 渲染层 `src/renderer/`

- `shell/` — 桌面隐喻的全部实现，**只做入口不做容器**。
- `views/files/` — 最高频模块。双栏、虚拟滚动、拖拽四方向语义（本地↔远程、远程↔远程、拖到应用图标）。
- `views/gpu/` — 卡片式商店。卡片必须显示：型号、显存、单价、空闲数、**你的余额够跑多久**。
- `views/jobs/` — 列表 + 抽屉详情 + 日志流。**`JobHeldUser` 要与普通排队严格区分**。
- `views/dashboard/` — 配额双维度水位条。

### 目录浏览延迟归因（`npm run latency-check`，真实集群实测）

| 环节 | 耗时 | 说明 |
|---|---|---|
| 链路往返（exec） | **59 ms**（偶发抖到 272） | 每次操作的地板价 |
| SFTP 通道建立 | 64 ms | 只发生一次，之后复用 |
| `realpath('.')` | 4 ms | 只有 path 为空时才调 |
| `readdir` 82 项 | 32 ms | 小目录基本无感 |
| `readdir` 429 项 | **210 ms** | **明显的来源：条目数 × 每项 longname 体积** |

加入缓存前后的对比（同一台集群，连读两次）：

| 目录 | 条目 | 冷读 | 缓存命中 | 强制重读 |
|---|---|---|---|---|
| `/home` | 429 | 658 ms | **0.0 ms** | 328 ms |
| `/home/alice` | 82 | 58 ms | **0.0 ms** | 37 ms |

**结论**：慢的不是"远程"本身，而是**条目多的目录**（`readdir` 一次要传回所有条目的
longname，服务端强制返回，客户端没法要求省略）+ **完全没有加载反馈**（用户以为点了没反应）。

三条优化，按性价比排序：
1. **缓存**（已做）：来回切目录从 300–650 ms 降到 0，这是感知提升最大的一条
2. **加载态**（已做）：哪怕只有 200 ms，有个脉冲条也不会让人怀疑程序卡死
3. **减少往返**（已做）：`listRemoteDir` 只有 1 次 `readdir`，`realpath` 结果也缓存了

**没做且做不了的**：分页/流式 `readdir`。ssh2 的 `readdir()` 会读到 EOF 才回调，
没有流式 API；要分批就得自己实现 SFTP 协议层，收益不抵成本。

### 拖出到资源管理器的时序（理解这段才不会觉得"时好时坏"）

```
用户按下并拖动远端文件
  → dragstart 被拦下（preventDefault）
  → 镜像下载到临时目录（第一次几百毫秒到几分钟，看文件大小）
  → 下载完调 webContents.startDrag()
  → 系统接管，文件"粘"在鼠标上，可以拖到桌面/资源管理器
```

**关键**：`startDrag` 最好在用户手还按着时调用。文件已缓存时整个流程只有几毫秒，
用户感觉不到；第一次拖要下载，手往往已经松开，那就得**再拖一次**。

这不是实现缺陷，是 `startDrag` 的固有限制——它只能拖真实存在的文件。
WinSCP 那类工具也是这个行为。

> **为什么不能"松手后自动落到目标目录"**：如果不在 `dragstart` 里拦截，
> 用户拖到应用外松手时，应用**收不到任何 drop 事件**——Windows 的拖放机制里，
> 拖放源只负责提供数据，落点由目标程序处理，源程序拿不到。所以"自动知道拖到哪"
> 做不到。唯一绕过的办法是写 shell 命名空间扩展（WinSCP 的 Explorer 集成模式），
> 属于 C++ COM 组件，不在本项目范围内。

### 拖拽缓存什么时候清

位置：`%TEMP%/hpc-workbench-drag/<hash>/<name>`。

**每次启动应用时整体清空**（`main/index.ts` 里调 `clearMirror()`）。

为什么选启动时而不是退出时：
- 退出时清 → 下次开机缓存全没，"同一个文件再拖瞬间开始"就失去意义
- 启动时清 → 每次运行从干净状态开始，本次运行内拖多少次都命中缓存，既不占地方又保住手感
- 还有个隐患：用户可能正在别的程序里打开着镜像文件，退出时删会失败

**会话内不设上限**：拖很多大文件会把 temp 撑大，这是用户自己的选择。

       2. 作业被控制器清理（`MinJobAge`，默认结束后 5 分钟）才退回 `sacct` + 命名约定
          （`.out` 和 `.log` 各三种，一次 shell 循环问完）。
       定位逻辑抽在 `domain/job-log.ts`，有 9 条单测覆盖三条分支。
     - ✅ **「跟随输出」**（`tail -F`，`jobs:log-start`/`jobs:log-stop`）
       - 对**排队中的作业**也能点：路径是精确的，`tail -F` 会等文件出现，
         作业一开始跑就自动流出来
       - 增量文本由主进程**按 120ms 合并**后推送（和传输进度同一个教训：
         一秒几百行、一条一块地发会把渲染层打死）
       - 日志区最多留 20 万字符（约 3000 行），超了从头砍；跟随期间往上翻过就不自动滚到底
       - 关弹窗时**必须 `stopJobLog`**：远端 `tail -f` 不会因为窗口关了就不跑
     - 只 `tail -n 200` 读首屏：训练日志动辄几 MB，全读回来又慢又没用
     - 找不到时把试过的路径全列出来，方便用户自己去文件页找
     - 真机验证（`npm run joblog-check`）：
       - 作业 211291（本应用流程提交、输出故意用 `.log`）：`COMPLETED` / gpu13 /
         精确路径 `stream-211291.log` / 内容 `tick 1…10` + `中文OK`
       - 排队中的 185046：`scontrol` 已给出 `slurm-185046.log`，文件还没出现，
         如实报"不存在"而不是猜别处
       - 流式：对远端每秒增长的文件跟 8 秒，增量收到 12 行、**中文无乱码**、主动中止生效
   - `sacct --json -X --starttime=now-7days -u "$USER"` → `JobHistory[]`
   - **这个版本的 sacct 不认 `--me`**（实测 `unrecognized option '--me'`），只能用 `-u "$USER"`
   - **字段结构和 squeue 完全不一样，绝不能照抄**（docs/03 §3.6 警告过，实测验证）：
     | 字段 | squeue | sacct |
     |---|---|---|
     | `state` | 字符串 `"PENDING"` | **对象** `{current, reason}` |
     | `exit_code` | 不存在 | **对象** `{status, return_code}` |
     | 时间 | `submit_time` 平铺 | `time: {elapsed, start, end, submission}`，`elapsed` 是**秒** |
     | 资源 | `tres_req_str` 字符串 | `tres.allocated[]` 数组 |
     | 节点数 | `node_count` | `allocation_nodes` |
   - `state.reason` 实测是字符串 `"None"` 而不是 null，要转成 null，别当成有意义的原因
   - **`FAILED` 的作业 `exit_code` 可能仍是 `SUCCESS`**（`-X` 只取主作业，真正失败在 `script` 步骤）。
     用 `exitCodeMisleading` 标出来，界面提示"去看 .out 日志"，不能拿退出码断定失败原因
   - 未结束的作业 `time.end` 是 0，要转成 null
3. ✅ **节点与显卡库存**（`domain/inventory.ts` + `components/NodesView.tsx`）
   - `scontrol show node --json` → `parseNodeDetail` → `buildInventory` 聚合
     - **只用 scontrol，不用 sinfo**：后者是分区聚合，拿不到逐节点 GPU
   - 顶部按型号的库存卡片：空闲/总数、涉及几台机器、有哪些机器还有空卡
   - 下方节点表：状态、显卡空闲比例、空闲核心、空闲内存、分区
   - 三条规则（都是 docs/03 实测出来的，有测试锁死）：
     1. **blocked 的机器整台不计入库存**。`IDLE + DRAIN` 也算 blocked——
        看着空闲，但调度器不会往上派活，算进去就是骗人
     2. **`ALLOCATED` 不等于没货**。`scontrol` 从不返回 `MIXED`，有作业就报 `ALLOCATED`，
        但上面照样可能空着卡。判断要看 `freeByType()`，不能看状态名
        （用 `{idle, mixed}` 过滤的话，夹具里 16 台会被砍到 1 台）
     3. **多机型节点按型号分别算**。夹具里 `v100s-pcie-32gb` 和 `v100-sxm2-32gb`
        只差几个字母，合并成 5 张就错了
   - **型号名的坑**：一开始把所有 `v100` 都翻成「V100」，真实集群 10 个型号翻出来
     只剩 6 个名字，三张卡片同名，用户对不上号。现在按「系列 + 显存 + 形态」拼
     （`V100 16GB SXM2` / `A100 80GB PCIe`），并加了回归测试断言"不同型号不能同名"
   - 实测真实集群：16 台机器 / 12 台可用（4 台 DRAIN 或 DOWN）/ 67 张卡只空 16 张，
     全集中在两台 V100 16GB 上；A100 / H100 / A800 全部 0 空闲
4. ✅ **存储配额**（页面「资源」的下半部分）
   - `mmlsquota --block-size auto` → `parseQuota`（Phase 0 写的）
   - **必须用绝对路径 `/usr/lpp/mmfs/bin/mmlsquota`**：实测这台机器上 `mmlsquota`
     不在 PATH 里（`command not found`），只有绝对路径能跑。换成裸命令名会一直失败
   - 进度条按**软限**算（软限是"该清理了"的提醒线），没设软限才用硬限，
     两个都没有就只显示已用、不画条——画个满格红条是误导
   - `inDoubt`（尚未结算的量）非零是正常现象，界面上说明一句，免得用户以为出错
   - 实测约 550 ms（要查 GPFS 元数据），所以和节点分开加载、单独一份状态，
     不拖住节点表的渲染
   - 真实数据：`dssg01` 已用 90.68 GB / 软限 6 TB / 硬限 9 TB，文件 371342 / 6291456
5. ✅ **显卡单价 + 费用试算**（资源页的型号卡片和底部试算器）
   - `scir-watch -s` → `parseGpuPrice`（Phase 0 写的，能处理 Unicode 表格和合并单元格）
   - **只取价，不当库存真值**（docs/03 §5.0）。逐节点库存以 `scontrol` 为准
   - 型号名两边是同一套（`a100-pcie-40gb` 这种），可以直接 join
   - 同型号多台机器的价格可能不同 → 聚合时取**区间**（`4–6 点/小时`），不随便挑一个
   - **`scir-watch` 只列出当前有空闲卡的型号**，所以"没报价"通常等于"现在租不到"。
     界面按这个语义分情况显示，不笼统写"无报价"（那会被理解成"不知道价格"）
   - 费用试算：单价 × 卡数 × 小时，**只做乘法**，不掺折扣或阶梯价的想象——
     集群怎么计费我们不知道，乱加规则比不给结论更糟
   - 参数非法返回 `null` 而不是 0：0 会被当成"免费"
   - 实测：4 张 V100 16GB 跑 8 小时 = 128 点；1 张 A100 40GB 跑 24 小时 = 240 点
6. ✅ **提交作业**（作业页右上角「提交作业」）
   - 三步：填参数 → **看脚本并随便改** → 选目录提交
     - 第二步是刻意的：不在后台偷偷拼参数就交。用户得知道交上去的是什么，
       否则跑错分区、时限太短被砍，根本没法排查
   - 两种模式：**写命令**（生成脚本）/ **用已有脚本**（`sbatch 参数 <已有 .sh>`，
     命令行参数会覆盖脚本里的 `#SBATCH`）
   - 脚本位置**每次都选**：`RemoteDirPicker` 自己走 SFTP 列目录
     （`dialog.showOpenDialog` 只能选本机目录，用不了）
   - 文件名 `<作业名>-<时间戳>.sbatch`，**目标已存在就拒绝**，不静默覆盖
   - 生成的脚本带 `set -e`（某条命令失败就停，否则会得到"成功"的假象），
     环境准备默认**注释掉**（猜错 module 名会让作业一起手就挂），
     头部加一行 `echo node=$(hostname)` 方便定位
   - `--gres` 是**每节点**语义，界面填「每节点卡数」并实时显示总数
   - sbatch 输出解析不出作业号就按失败处理——编个 0 出来会让用户以为交上去了
   - ⚠️ **`sbatch --test-only` 检查不到全部约束**：实测 1 卡 8 核用 `--test-only` 是通过的，
     但真实提交被集群拒了（见下一条）。**不能拿 --test-only 当"肯定能提交"的证明**
   - **本集群有个配比限制：每张卡最多配 4 个核**（scir 扩展）。
     **实测 5 种卡（V100 16GB / A100 40GB / A100 80GB PCIe / H100 80GB / RTX A6000）
     的 `cpu_limit` 全是 4** —— 这是集群级配置，不按卡型区分。换集群要重新确认。
     1 卡 + 8 核会报
     `total cpus num(8) > tres total num(1) * cpu_limit(4) (scir extension)!`
     ——这行字对用户等于没说，所以：
     - 表单默认值改成 **1 卡 4 核**
     - 表单里 `cpus > gpus * 4` 时给黄色提醒（只提醒不阻止，别的集群规则可能不同）
     - `explainSbatchError()` 把报错翻译成"把核数改成 4 或更少，或者把卡数加到 2 张以上"
   - **真实提交验证**：用和用户相同的参数（1 卡 8 核）复现，确认被拒（exit=1）且翻译准确；
     作业没有真的提交，不占资源
   - **必须设 `--chdir`（踩过的坑）**：第一版只把脚本写到用户选的目录，没设工作目录，
     结果作业在 home 下跑，`python train.py` 直接 `exit 2`（1 秒内挂），
     输出文件也落在 home，用户连日志都找不到。
     现在流程改成「填参数 → 选目录 → 预览 → 提交」，选目录时就把 `--chdir` 写进脚本，
     所见即所提交
   - **预计启动时间**：
     - 排队中的作业直接显示（`squeue` 的 `start_time`，调度器的最佳猜测）
     - 预览页有「预估什么时候能跑」按钮，走 `jobs:dry-run`（`sbatch --test-only`，
       写临时脚本→检查→删）。**保留集群返回的原始时间串不转 Date**——
       那个时间不带时区，按本机时区解析会错开几小时
     - 界面注明"只是估算"，因为 `--test-only` 不检查配比/配额限制
   - 弹框都有关闭按钮（右上角 X），不用非得点「取消」
   - **表单里可以选显卡型号**（不再只能锁死「租这个」进来的那一个）：
     Dialog 自己拉 `listNodes` + `getPrices`，列出所有型号 + 空闲数 + 单价，
     选中换型号时预估点数跟着变
   - ✅ **选完型号可以再指定具体机器**（`--nodelist`）
     - 动机：同一型号下几台机器的余量差别很大（实测 `gpu10` 卡8/核 30/48，
       `gpu11` 卡6/核 2/48——后者卡更多但核已占满，交上去大概率一直排队）。
       只给「可放 2 台」这种汇总数字，用户没法判断该等哪台
     - 选完型号后出现「指定机器」列表：每台显示 `卡N` / `核空闲/总数` / `空闲内存G`，
       并标「放得下」或「核不够/卡不够」；默认「不指定」交给调度器
     - **换型号会自动清空已选机器**：节点名和型号是绑死的，`--gres=gpu:a100:1 --nodelist=gpu10`
       永远排不上，比不指定更糟
     - 「对比各型号预计启动时间」也必须清掉 node（同理）
     - 实现：`JobSpec.node` → `--nodelist=<node>`；节点名过 `isValidNodeName()` 白名单，
       非法值**直接不生成这行**，不依赖下游 `shq()` 兜底
     - 实测：`-w gpu09` 与 `--nodelist=gpu09` 都被接受（统一用后者）。
       真提交作业 211321 钉死 `gpu10`，`hostname` 输出正是 `gpu10`
   - **「对比各型号预计启动时间」**：对每个型号各跑一次 `--test-only`
     （`--gres` 不同，必须分开问），**并发 3**。
     实测并发 4 个只花 **100 ms**——`--test-only` 是本地调度模拟，不排队
   - ⚠️ 这个对比结果**偏保守**：实测 V100 16GB 有 10 张空闲卡，却算出
     「17 小时 52 分后」，而只剩 1 张空闲的 A100 40GB 只要 53 分钟。
     原因是 `gpu11` 的 48 个核被占满、`gpu12` 占了 22/48 核，
     backfill 调度器按"现有作业跑完才轮到你"来估。**实际提交常常快得多**，
     界面上写明了"结果偏保守，实际常常更快"
   - 时限输入步长 0.1 小时（6 分钟），能填 0.1/0.3 这种
   - **无空闲的型号也能点下单**（按钮文案变成「预填排队 →」）：
     先把参数填好交上去排队，不用干等有货
   - 排队但集群没给预测（比如被 held 的作业）显示「暂无启动预测」，
     不给一个假时间
7. ✅ **点选式下单**（型号卡片上的「租这个」）
   - **没做独立的「显卡商店」页**。资源页已经有全部库存和价格，再做一页就是信息重复，
     两处数据迟早不一致。下单入口直接放在型号卡片上，一步到位
   - 只有 `free > 0` 才显示按钮：没货还摆个「租这个」是骗人

     - 表单里可以点「改成任意型号」解除

8. ⏭️ **仪表盘 —— 决定不做**

   - 真需要"一屏看完"，更好的做法是在标题栏放几个关键数字，而不是新开一页

### Phase 3 · 变成桌面应用（约 2 周）

**验收**：不点任务栏切出时，会觉得这是个独立软件而不是网页。

1. ✅ **Dock（左侧图标启动器）+ 标题栏常驻数字**
   - 顶部那排文字页签换成了左侧竖排图标（`components/Dock.tsx`）：竖排图标 + 当前项高亮
     是桌面软件的形态，顶部文字按钮是"网站导航"的形态
   - 图标手写 SVG（只有 5 个，引图标库反而多一份依赖），悬停浮出「名字 + 一句说明」
   - **标题栏右侧常驻三个"电量"数字**（`components/TitleBar.tsx`）：
     跑中 / 排队作业数、存储水位、点数余额
     - 共同点是"不看会出事"：作业挂了不知道、存储满了传不上去、点数不够跑到一半被掐
     - 点数走新加的 `points:get`（`scir-account -d`，实测 197 ms）
     - 存储按**软限**算百分比，没设软限才看硬限，两个都没设显示「—」而不是假进度条
     - 阈值：存储 ≥75% 转黄、≥90% 转红；点数 <50 转红

   - **轮询必须分级**（docs/04 §5.1 P6）：作业 20 秒、配额/点数 5 分钟；

   - 顺手去掉了原来标题栏上写死的「Phase 1」徽章——作品集里挂阶段标签像半成品
2. ✅ **通知中心**（`components/NotificationCenter.tsx` + `lib/job-watch.ts`）
   - **只报三类事件**（其余都是噪音）：
     - 排队 → 运行：「作业 X 开始运行」
     - 运行中从队列消失：「作业 X 已完成/失败/超时…」
     - **排队中就消失**：「还没开始就离开队列（可能被取消或被抢占）」——
       这条最容易被漏掉，用户会以为作业还在排队
   - **刻意不报"新出现的作业"**：那是用户自己刚提交的，界面已经弹过提示
   - 判断逻辑全在 `diffJobSnapshots()` 纯函数里，9 条单测——
     真机上很难复现"排队中被抢占"，而这条逻辑写错一次就会天天弹假通知
   - **"消失"不等于"成功"**：`squeue` 只列活跃作业，所以运行中消失只说明结束了；
     成功还是失败要再查一次 `scontrol show job`（结束后 5 分钟内还在控制器里，
     而通知在 20 秒内就会查）。查不到就如实说「已离开队列，查不到最终状态」

   - 照着这条手敲命令做的，语义**逐条对齐**：
     ```
     ssh -o ExitOnForwardFailure=yes -o ServerAliveInterval=60 \
         -R 127.0.0.1:55555:127.0.0.1:7897 hpc
     ```

     典型场景是让集群上的 codex 用上本机 Clash（7897）的代理

     | 原指令 | 实现 |
     |---|---|
     | `-R 127.0.0.1:55555:127.0.0.1:7897` | `Session.forwardIn()` **硬编码只绑 `127.0.0.1`**，没有参数可传 |
     | `ExitOnForwardFailure=yes` | `forwardIn` 的回调 err 直接抛，IPC 层翻成人话，**绝不假装成功** |
     | `ServerAliveInterval=60` | 已由 `Session` 的 `keepaliveIntervalMs` 覆盖（profile 配的 10s，比 60s 更密） |

   - 端口冲突的解释由 `domain/port-owner.ts` 负责：读 `/proc/net/tcp` 的 uid
     （所有用户可读，不需要 root）→ `getent passwd` 翻名字 → 报"被谁占着"

#### 默认端口：55555 → 55556 → 21056

三次才对：

1. 原命令用的 **55555** 被别的账号长期占着（E25），绑不上；
2. 改成 **55556**，和用户当时的 `~/.profile` 对齐。结果它落在内核的**临时端口段**
   （`ip_local_port_range` = 32768–60999）里，会被别人的出站连接临时征用，
   表现为"时好时坏、`ss -ltn` 又查不到"（E28）；
3. 最终定 **21056**——32768 以下，不会被临时端口抢走。用户集群上的 `~/.profile`
   与应用默认值同一个数。

教训写进 E28：**给"固定用途"挑端口，要选在临时端口段之外**。5xxxx 看着好记，
但那正是内核随手会分给任何人的区间。

但"默认端口"解决不了根本问题：`127.0.0.1` 是全用户共享的，**任何数字都可能哪天被占**。
所以加了一层退让（`domain/reverse-port.ts` 的 `openWithFallback`）：

1. 先按用户填的端口开，成功就结束；
2. 绑定被拒（ssh2 那句 `Unable to bind`）→ 查是谁占着 → 从 `requested+1` 往后
   一次问 12 个候选（一条命令问完，不是一个一个试），挑第一个没人监听的；
3. 换到那个端口重开一次，返回 `fallback: { requested, actual, owner }`；
4. 附近全满 → **把原始错误抛回去**，不编新原因。

为什么"退端口"必须在界面上说清楚：换了端口，集群上的 `http_proxy` 还指着老端口，
隧道等于白开。所以界面会显示一段黄框 + 可复制的三行 `export`（`shared/proxy.ts`），
并明确写明这是**一次性**的——不改 `~/.profile`，新开的终端仍会回到默认端口。

#### 一条隐性约定：监听端口 = 集群上的 `http_proxy`

隧道开成功 ≠ 有人用。集群上的程序（codex / 实验脚本）只照 `http_proxy` 里的端口连。
所以 `forward:proxy-port` 会读集群的 `~/.profile`，界面在"集群 → 本机"方向下显示
"集群上 http_proxy：127.0.0.1:xxxx"，和监听端口不一致时当场给黄条 + 三行 export。

读的方式是 **grep 出那一行原文，再用 JS 解析**（`domain/proxy-config.ts`）：
`session.exec` 跑的是非登录 shell，`$http_proxy` 是空的；而让远端 sed 抠端口又没法单测
（本机 spawn bash 会 EBUSY，见 E27）。

实测（`npm run reverse-check -- --port 5793 --fallback`）：
`5793` 被 `xqtian` 占着 → 自动改到 `5794` → 打印出口的三行 export；
同时 `http_proxy` 读到 `55555`，与 5794 不一致，界面会给出提醒。
另外注意：**55555 在 16:40 已被人释放**，同一端口的状态是会变的——
所以判断一律实时查，不能缓存。

#### 「测一下能不能用」：出口 IP 比对

隧道"已开"只说明第一关过了。真正要回答的是：从集群上连这个端口，请求有没有绕回**你这台电脑**。
所以 `forward:verify` 做两件事并**比对**：

1. 在集群上 `curl --proxy http://127.0.0.1:<隧道端口> https://api.ipify.org` → 出口 IP
2. 在本机走 Clash（HTTP 代理的绝对 URI 写法，`domain/egress.ts`）→ 出口 IP
3. 两个 IP 相同才算通；不同说明那个端口上蹲着别人的服务

这是唯一能识破"看着通了、其实走别人的代理"的手段——2026-11-04 早上正是这种情况：
55555 上是 sdchen 的代理，请求有响应，但出口 IP 是 `38.190.176.202` 而不是本机 Clash 的。

结论措辞统一在 `shared/tunnel-verify.ts` 的 `describeVerify`，五种组合各对应一种处置方式
（一致 / 不一致 / 只有集群侧通 / 只有本机通 / 两边都不通），`--verify` 与界面共用同一份。

#### 退端口不止试一个

候选端口从"探测时空闲"到"真正 bind"之间有几毫秒窗口，期间可能被别人的新连接抓走
（临时端口段里尤其常见）。所以 `openWithFallback` 最多试 **3 个**候选，先试的那个失败就换下一个；
全试完仍然失败才抛**原始错误**（指向用户要的端口）。

### 命令台 → 已实现（不在原计划里，按需加的）

标题栏「命令」按钮 / **Ctrl + 反引号** 打开底部抽屉，列出每条真正发往集群的命令：
时间、耗时、退出码、stdout/stderr。可过滤、可「只看失败」、可展开看完整命令、
可「看完整输出」、可清空。默认收着，开合状态存 localStorage。

**这个功能解决的是本项目最根本的调试痛点**：界面上一个数字不对，你无法知道
"它是发了什么命令、远端回了什么"，只能翻代码猜或另开终端重敲一遍。有了它，
任何一个数字都能当场对账。

#### 挂钩点只有一个：`Session.exec`

```
页面 → IPC → adapter/domain → Session.exec ──┬──→ 远端
                                            └──→ onTrace → TraceStore → IPC 推送 → 抽屉
```

挂在 `Session.exec` 而不是各页面里，是因为**它是唯一出口**。挂在页面上就得每加一个
功能都记得上报一次，漏掉的那个恰好就是出问题的那个。

所以"新写的功能会不会被记录"这件事不需要额外操心：只要走 `session.exec` 就自动有。

#### 四条硬约束

1. **只读**。preload 只暴露 `traceList` / `traceDetail` / `traceClear`，**没有**
   `traceExec`。这个面板一旦能执行命令，就从"可观测性"变成了"绕过业务校验的后门"。
2. **观测不许反噬**。`TraceStore.push` 整体 try/catch；订阅者（IPC 推送）抛异常也被吞；
   `Session.emitTrace` 同样 try/catch。有测试专门断言"onTrace 抛异常时命令照常成功"。
3. **有界**。`TRACE_LIMIT = 200` 条环形缓冲（轮询 20 秒一次，约等于最近一小时），
   单条输出超 `MAX_FIELD_CHARS`（16 KB）即截断。列表只发预览（4000 字），
   完整输出留在主进程按 id 取——不把几十 KB 的 JSON 全塞进 IPC。
4. **报真实长度**。`stdoutChars` 记的是**原始**字符数，不是预览长度。
   界面靠它才能说清"共 6999 字，只显示了开头"。

#### 覆盖不到的地方（不是 bug，是边界）

- `Session.tail`（跟随日志）、`openShell`（终端）、`openTunnel`/`forwardIn`：这些是长连接，
  没有"一条命令一个结果"的形状，不记。
- SFTP 传输（上传/下载/改名/删除）：走的是 SFTP 子系统，不经过 exec，不记。
- 因此抽屉里的条数**不等于**"所有动作"，只等于"所有 exec"。真要对账文件操作看传输列表。

#### 自检

`npm run trace-check`（真集群）：跑 `squeue --me --json` / `scir-watch -s` /
`scir-account -d` / 一条 `exit 7`，打印抽屉里会显示的内容，并验证 `detail` 能取回全文。
实测 4 条全部记到，`squeue` 那条 6999 字完整可取。

#### 为什么用"语义名"而不是尺寸名

字号写成 `text-[11.5px]` 时，改一处不影响别处，于是下一处就写成 `text-[12px]`——
半年后必然重新散成十几档。改成 `text-sub`（辅助信息）之后，**调数值是改一处、
改语义是改一处**，两者不再纠缠。同理 `state-ok` 在哪都是绿，不需要每次重新判断。

#### 守护测试是这套东西能活下来的唯一原因

Tailwind 有个很隐蔽的失效方式：**类名打错或没注册，样式就是不生成，编译器一声不吭**。
`text-emph` 写成 `text-emps`，页面照常渲染，只是字号没变。在 8000 行里找这种拼写错误
靠肉眼是不可能的。

所以 `tests/design-tokens.test.ts` 里有 29 条断言，其中 9 条是硬约束（`toEqual([])`，
不给"少数例外"的余地）：

```
字号不再写死像素（只用 text-page/emph/body/sub/meta）
颜色不再直接用调色板（只用 ink/accent/state 语义色）
圆角只用两档（rounded-control / rounded-surface，外加胶囊 rounded-full）
阴影只用两档（shadow-card / shadow-pop）
断点只用 compact/normal/wide，不写默认的 sm:/md:/lg:/xl:
页面骨架必须用 PageShell，不许手写 mx-auto 那一层
页面骨架都通过 PageShell 出现（组件真的被引用了）
页面标题统一走 PageHeader，不手写 h1 + 说明两件套
没有拼错的类名残骸（Tailwind 会静默吞掉它们）
```

**这九条都验证过"真的会失败"**：往 `Dock.tsx` 里塞一个
`text-[11.2px] text-sky-600 rounded-lg shadow-xl`，四条断言同时变红。
后四条是分批补的，每条都单独注入一次违规、确认变红、再还原。

> 加新样式时如果测试报错，正确做法是去 `tailwind.config.js` 注册语义 token，
> **不是**在页面里写死数值、也不是把断言放宽。

#### 组件抽出来了，但五个页面一个都没用

这是那次收敛里最蠢的一个失误，记下来是因为**它不可能被任何工具发现**。

我写了 `PageShell`（统一页面骨架）和 `PageHeader`（统一页头），
在 `ui.tsx` 里配了三段注释解释为什么要抽——然后**五个页面的 `return` 里
仍然留着各自手写的那一套**：

```tsx
<main className="selectable flex-1 overflow-y-auto">
  <div className="mx-auto w-full max-w-page wide:max-w-page-wide px-8 py-7">
```

编译器不会报"你有个组件没人用"，测试不会报，构建也不会报。
`ui.tsx` 打开看很整齐，实际上 `PageShell` 一行都没生效。直到我
`grep -rn "PageShell" src/renderer/src/`，结果是：

```
./components/ui.tsx:29:export function PageShell({      ← 只有定义，没有调用
```

也就是说：**"抽了公共组件"和"统一了布局"是两件事**，
中间那步"去每个调用点替换"才是真正的工作量，而它没有任何自动化信号。
所以现在有两条守卫盯着它——一条查"还有没有人手写骨架"，一条查
"`PageShell` 到底被几个页面用"（后者防的是把组件删了、前者悄悄失去意义）。

顺带记一个迁移时踩到的坑：用脚本批量替换开口标签很方便，但这五个文件
**结尾结构各不相同**（有的在 `</main>` 前还有一个条件渲染的弹窗 `)}` 块）。
脚本"先换开口、再匹配结尾"，一旦结尾没匹配上就留下**半截结构**——
开口是 `<PageShell>`、结尾还是 `</div></main>`，tsc 报的却是
`TS17002: Expected corresponding JSX closing tag`，指向的位置和真实原因差了好几行。
后来改成逐个手工 Edit，四次改完。

#### 新增的三档断点

默认的 `sm(640)/md(768)/lg(1024)/xl(1280)` 是给网页多设备设计的，在桌面应用里是错的：
960 宽的窗口会命中 `lg`，而那时两栏根本放不下。所以按**窗口宽度**重新定义：

| 断点 | 阈值 | 含义 |
|---|---|---|
| （默认） | < 1040 | 单栏，满宽减边距 |
| `compact` | ≥ 1040 | 标题栏放得下搜索框 |
| `normal` | ≥ 1180 | 两栏：左内容 + 右 320 窄栏（设计基准尺寸） |
| `wide` | ≥ 1480 | 栅格放宽到 1400，大屏不留大片空白 |

窗口最小宽度在 `main/index.ts` 锁了 960，所以不存在更窄的情况。
配置里还把 `sm/md/lg/xl` **重映射**到同一组数值，防止有人顺手写默认断点时悄悄引入第四套语义。

#### 启动页

冷启动时窗口 `show: false` 等着，从渲染完成到第一轮数据回来之间有 1–3 秒空白。
`components/BootSplash.tsx` 把这段时间变成三段有结论的检查：**配置 → 连接 → 队列**。

关键设计取舍：**故意不复用 `probe()`**。探针跑 9 条命令、要 2–4 秒，
启动页如果自己就是瓶颈，它就失去了意义。这里只发两条：
`echo "$USER@$(hostname -s)"` 和 `SQUEUE_COMMAND`。真机实测 **346 ms**（预算 8000 ms）。

三步是 **fail-fast** 的：第 N 步失败就不跑第 N+1 步，否则一个无关的队列错误会把
真正的连接错误盖掉。

失败时给三个出口：重试 / 去诊断页 / 仍然进入。Esc 随时可跳过。
成功时会多停 420 ms，让人看清三行都绿了再淡出——否则太快等于没显示。

自检：`npm run boot-check`（走 `app:boot-status` 同一条路径）：

```
✓ config   配置文件已找到 0ms
✓ connect  已连接 alice@login-01 256ms
✓ queue    队列里没有作业 62ms
总耗时 346ms / 预算 8000ms
```

失败分支也验过：`HPC_CONFIG=F:/nope/profiles.json npm run boot-check` 正确停在第一步并打印期望路径。

##### 启动页是全站唯一的深色页面，所以它需要另一套文字色

启动页底色是 `ink-900`(#343945)，而 `ink-*` 那套灰阶是**给浅色底用的**——
越深越"弱"。深色底上恰好相反，于是当时全部用 `text-white/30` 这类写法**凭手感**调深浅。
算完对比度才发现这批值普遍不合格：

| 用法 | 对比度 | 判定 |
|---|---|---|
| `white/20`（分隔符 `·`） | **1.86:1** | ✗ |
| `white/25`（耗时 `346ms`） | **2.16:1** | ✗ |
| `white/30`（还没执行的步骤说明） | **2.47:1** | ✗ |
| `white/35`、`white/40`（跳过、说明、标签） | 2.85 / **3.26:1** | ✗ |
| `white/45`（原始输出开关） | **3.71:1** | ✗ |
| `white/62` 及以上 | 5.57:1 | ✓ |

**`ink-900` 上白字的最小可用 alpha 是 0.53。** 启动页有 11 处落在 1.86–3.71 之间。
这批字不是"看不见"，而是**"灰蒙蒙地在那儿、读起来费劲"**——比彻底看不见更容易被忽略，
因为它看起来"像是设计成这样的"。

更严重的一处：第一步失败时，失败文字用的是 `text-state-bad`(#b91c1c)，
它衬 `ink-900` 只有 **1.79:1**——而这是"启动失败"这条最关键的信息。
（顺带一提 `red-400` #f87171 也不够，只有 4.18:1，所以不能顺手换成调色板。）

所以新增一套**只给深色底用的 `night-*` 四档**（配在 `tailwind.config.js`）：

| token | 色值 | 衬 ink-900 | 用途 |
|---|---|---|---|
| `night-sub` | `#b2b4b8` | 5.57:1 | 次要说明、时间戳、未执行的步骤 |
| `night-body` | `#c6c8cb` | 6.89:1 | 正文、按钮文字 |
| `night-emph` | `#e7e7e9` | 9.36:1 | 已完成、强调 |
| `night-bad` | `#ff9b9b` | 5.73:1 | 失败提示（深色底专用红） |

`tests/design-tokens.test.ts` 加了 5 条断言：四档基准值一致、每档 ≥4.5:1、
相邻档至少差 0.8:1（否则"三档"等于一档）、**深色底不许再写 `text-white/<alpha>`**、
**`night-*` 只许出现在确认为深色底的文件里**（目前是 `BootSplash.tsx` 和 `Dock.tsx` 的悬停提示）。

> 补这条守卫时它**当场抓到一个漏网的**：`Dock.tsx` 的悬停提示里还有
> `<span className="ml-1.5 text-white/60">`。那处实测 5.33:1，技术上达标，
> 但按新约定本该走 `night-sub`——守卫不认识"技术达标"，它只认约定，这正好是它的价值。

#### 顶部横幅合并

原来是两段独立 JSX（preload 过期、配置缺失），会**同时出现**并吃掉 100px 以上，
而且都在页面最顶上——正好是最该留给内容的位置。三条一起出现时用户会直接忽略全部。

`components/Banner.tsx` 的规则：一次只显示最严重的一条（`blocker` 优先于 `notice`），
其余折叠成「还有 N 条提示」。位置紧跟标题栏，视觉上属于"系统状态"而非"页面内容"。

#### 命令台从抽屉改成浮层

原来是 `flex-shrink-0 h-[264px]`，展开时把 264px 的页面内容顶出可视区——
在文件页上会把传输进度条挤没。现在改成 `absolute inset-x-0 bottom-0` + 点击遮罩关闭，
**不再参与主布局的高度计算**。

#### 资源页两栏

四段纵向平铺要滚三屏才答完"我能不能马上跑"。现在 `normal` 以上两栏：左边显卡卡片 +
节点表，右边配额 + 费用试算。租不到的型号折叠进 `<details>`，不再占首屏。

节点表改用 `VirtualList`：本集群 60 多台机器、每台带若干显卡 `<span>`，一次铺下来接近
800 个 DOM 节点，而这一页每 20 秒轮询刷新一次。**行高必须是常量**（`NODE_ROW_HEIGHT = 34`），
这是虚拟滚动的前提。

#### 切页面不闪白（SWR）

资源页每次切回来都重拉 `listNodes` + `getQuota` + `getPrices`，三块一起变空。
实测配额要 550 ms、价格要单独发一条 `scir-watch`。

`lib/swr-cache.ts` 是个很小的模块级缓存：**先出旧数据，再后台刷新**。
- 过期判断用"多久以前"而不是定时器：没人看的时候不需要刷新，省跳板机；
- 同一 key 的并发请求合并成一条（两个组件同时挂载时不会打两条同样的命令）；
- 用户主动点「刷新」时传 `noCache: true` 绕过缓存——那时他想看的是新数据。

9 条单测锁住三件容易写错的事：**stale ≠ 不可用**（返回 null 就等于没用缓存）、
失败时 `inflight` 必须清掉（否则第二次调用拿到同一个 rejected promise）、
失败**不写缓存**（否则一次网络抖动会被记 30 秒，比闪白更糟）。

#### 窗口不可见时停掉轮询

这个应用常驻一整天。最小化之后没人看结果，但每 20 秒仍是一次 SSH 往返。
`usePoll` 现在监听 `visibilitychange`，不可见就完全停掉，恢复可见后等
`RESUME_DELAY_MS`（400 ms）再刷新，避开切换动画。

#### 一个自己造出来的回归：状态色对比度不达标

收敛完之后回头算了一遍对比度，发现**第一版色板是错的**：

| 颜色 | 第一版 | 衬 tint 背景 | 达到 AA(4.5)？ |
|---|---|---|---|
| `state-ok` | `#059669` | 3.51:1 | ❌ |
| `state-info` | `#0284c7` | 3.81:1 | ❌ |
| `state-bad` | `#dc2626` | 4.41:1 | ❌ 差一点 |

根因是这四个值**同时被当作背景、边框、文字**三种角色用，而我按"背景色"的直觉
选了 500/600 档——那档做背景没问题，做正文就太浅。而这批颜色在界面上有
**172 处**是当正文色用的。

更糟的是还有 `text-state-bad/70` 这类写法，叠透明度后只剩 **2.95:1**。

修法两条：
1. 色板下移到 700/800 档（`#047857 / #92400e / #b91c1c / #0369a1`），全部 5.0–6.5:1；
2. **语义文字色一律不带透明度**。"弱化"该交给 `ink-*` 灰阶——语义色表达的是
   *含义*，把深浅交给 alpha，等于又回到"同一个红有好几种"的老问题。

`tests/design-tokens.test.ts` 加了 5 条对比度断言（文字/tint/白底/白字四种衬托 +
"不许叠透明度"），用的是真实 WCAG 公式，不是近似。

> 这个教训值得记住：**颜色收敛不能只看"看起来统不统一"，还要算对比度**。
> 全绿的测试不会告诉你字看不清。

#### 第二个自己造出来的回归：批量改类名改出了 14 个「不存在的类名」

上面剥 alpha 的那次批量替换（`text-state-bad/70` → `text-state-bad`）用的正则
顺手也匹配到了 `bg-state-*`，把 `bg-state-ok/60` 这类写法改成了：

```
bg-state-ok/[0.06]0          ← 方括号后面多了一个 0
```

这个类名在 Tailwind 里**匹配不到任何规则**，于是**一行 CSS 都不生成**。
受害的是 14 处"用实色标记状态"的元素：终端页的连接指示灯、资源页的配额进度条、
通知中心左键的未读徽标、文件传输进度条、日志弹窗的实时脉冲点……

后果的形态特别值得记住：

| 检查项 | 结果 |
|---|---|
| 编译 | ✅ 通过 |
| TypeScript | ✅ 通过 |
| 单元测试（当时 631 条） | ✅ 全过 |
| 界面上那 14 个元素 | ❌ 没有背景色，是一堆空 `<span>` |

**Tailwind 的类名是字符串，不是标识符**——拼错了没有任何东西会报错，
它只是安静地不生成样式。这和上面那个对比度问题是一体两面：
一个"颜色对了但看不见"，一个"元素在但颜色没了"。

修法：正则还原成实色（`bg-state-ok`），并补一条守卫
（`没有拼错的类名残骸`）——规则是 `/` 后面只能是数字、方括号或调色板档位，
**不可能出现 `]0` 这种"方括号后面还有字符"的组合**。已实测把违规类名注回去测试会变红。

> 两次回归的共同点：**都是批量脚本改的，都没有编译错误**。
> 批量改样式类名之后，除了跑测试，还要去构建产物 CSS 里确认
> "我改的那几个类真的生成了规则"——这一步当时跳过了。

#### 第三个自己造出来的：截断发生在排序之前

命令面板加入"历史作业搜索"（`sacct`，最近 7 天）时，为了给模糊匹配设个上限，写了：

```tsx
return [...actions, ...nav, ...jobs, ...history.slice(0, 200)]
```

看起来很合理，但截断的位置错了。`history` 是按**作业号倒序**的，
所以这 200 条是"最近的 200 条"，不是"和查询词最相关的 200 条"。
想找上周那个 `21130x` 时，它如果排在第 201 位就永远搜不到，
而面板只会显示「没有匹配」——用户会以为 `sacct` 没拉到数据，去查网络。

正确顺序是**全量打分 → 排序 → 再截断**，上限由面板自己施加（`RESULT_LIMIT = 100`）：

```tsx
const ranked = useMemo(() => rankItems(items, query, recentIds), [items, query, recentIds])
const results = useMemo(() => ranked.slice(0, RESULT_LIMIT), [ranked])
```

代价是每次按键都对全量打分，但这是纯字符串子序列比较，600 条也是微秒级——
拿这个换正确性不亏。

另外补了提示：被截断时 footer 显示 `100 / 250 条（多打几个字收窄）`，
不提示的话用户会以为"就这些"。

> 教训不是"别忘了排序"，而是：**任何 `slice` 都要问一句"我现在砍掉的是什么"**。
> 如果砍掉的顺序由数据源决定（倒序、按时间），那就等于在偷偷改变语义。

#### `DOCK_TABS` 一开始放错了文件

把页签清单从 `App.tsx` 移到 `Dock.tsx` 之后，`tests/command-palette.test.ts` 里
`await import('.../components/Dock')` 会让 **node 侧类型检查报 7 个错**：

#### 第四个自己造出来的：进度条永远是 0%

2026-11-05 用户实测时截了张图：正在传一个 187 MB 的文件，底栏写着

```
传输中 1 · 排队 0   ▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁   0 B / 187 MB · 0%
传输中  ↑ twinstate_medilocomo_repro_20261101        678 KB/s      187 MB
```

**同一屏里速度是 678 KB/s，总进度是 0%。** 两个数字自相矛盾。

根因在 `TransferQueue.snapshot()`：

```ts
const doneBytes = tasks
  .filter((task) => task.status === 'succeeded' || task.status === 'skipped')   // ← 少了一类
  .reduce((sum, task) => sum + (task.totalBytes ?? task.bytes), 0)
```

分子只累加**已经结束**的任务。所以只要队列里有一个正在跑的任务，它的字节就完全不贡献——
只有一个任务时进度恒为 0，直到传完才"啪"地跳到 100%。多任务时更怪：
进度会随"完成个数"呈阶梯，而不是随字节平滑增长。

**为什么那 659 条测试一条都没发现**：队列测试全是

```ts
queue.enqueue(...)
await queue.whenIdle()      // 等全部结束
const snapshot = queue.snapshot()   // 这时任务已是 succeeded，旧实现也对
```

`whenIdle()` 之后读快照，**永远看不到 `running` 状态**。这不是"测试写得不够多"，
而是"所有测试都从同一个角度切入"。正确的补法是在 `emit()` 时采样中间快照：

```ts
const original = (queue as unknown as { emit: () => void }).emit.bind(queue)
;(queue as unknown as { emit: () => void }).emit = () => {
  samples.push({ doneBytes: queue.snapshot().doneBytes, ... })   // 传输进行中
  original()
}
```

修法：`running` 也计入，且用它**实时的 `bytes`**（不是 `totalBytes`）。

顺手改的界面：任务行原来只显示总大小（永远不动的 `187 MB`），
现在运行中显示 `已传 / 总共`——一行里只有速度在跳、别的都不动时，人没法判断还剩多少。

> 教训：**"进度"这种东西一定要有"中途"的断言**。
> 所有断言都写在终态上，就等于从没测过进度。

#### 组装正确 ≠ 聚合正确

这个 bug 还有一个值得记的形状：`task.bytes` 在 `onProgress` 里被正确更新、
`bytesPerSecond` 也正确（所以速度是对的），IPC 也正确传了过去。
**每一层单独看都是对的，错在最后那个 `reduce` 的过滤条件。**
排查时先看"错的到底是哪一步"——速度对、字节对、只有汇总是 0，
那就说明不是传输层的问题，别去翻 SFTP。

### 4.9 第五个自己造出来的：「取消」不等于「已经停了」

用户实测：取消传输、选「停止并删除」，`.part` 还在。

加诊断后才看清：`queueCleanup()` **确实跑到了**，`unlink` 也**确实成功了**
（远端 `REMOVE` 返回 200），但下一秒文件又回来了。**是竞态，不是没调用。**

三层错误，一层比一层隐蔽：

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| v1 | `step` 里 `throw` 想打断 `fastXfer` | 异常冒穿 ssh2 回调栈，**整条 SSH 会话挂掉** |
| v2 | `watchAbort` 里直接 `reject()` | Promise 变灰，外层去 unlink，但 ssh2 还在发 `WRITE` → **删完又写回来** |
| v3 | `abort()` 只置位，settle 交给 `fastPut` 的 callback | 正确 |

v1 为什么挂会话：读 `node_modules/ssh2/lib/protocol/SFTP.js` 的 `fastXfer`，
`onstep && onstep(total, nb, fsize)` 是从 `writeCb` 里**裸调**的，没有 try/catch，
而 `writeCb` 在 SFTP 解析包的回调栈里。从那抛出去就一路冒到 `client.on('error')` 之外。

v2 为什么没用：`AbortController.abort()` 只影响**我们自己的 Promise**，
被取消的那个库完全不知道。所以"取消"只是请求停止，"已经被取消的对象还会继续动"。

**教训**：任何"取消后做清理"的代码都必须把两个时刻分开——
请求停止（置一个标志）vs 确认已停止（等它自己的完成回调）。
只有后者才有资格去动被操作的对象。这条对所有异步操作都成立，
不止 SFTP：`tail -f`、`docker build`、`ffmpeg` 全都一样。

配套改动：`cancel()` 返回的 `bytesDone` 现在用 `partial.bytesDone` 兜底
（`task.bytes` 来自 100 ms 采样的 `ProgressMeter`，会少报）。
测试的断言从 `bytesDone < payload.length` 放宽到 `<= payload.length`：
**取消一个刚好传完的任务是合法结果**，不该红。

## 4.9.1 第六个自己造出来的：标题栏的浮层被层叠上下文困住

**症状**（用户实测）：跳板机下拉展开后，卡片和左侧 Dock 重叠，被压在下面。

**第一反应是错的**：以为是 z-index 不够，想改成 `z-50` / `z-[9999]`。
没用——加 z-index 治不了这个。

**真因**：`TitleBar` 上有 `backdrop-blur`。CSS 规范里带 filter / 背景模糊的元素
会创建**层叠上下文（stacking context）**，于是标题栏内所有元素的 z-index
**只在标题栏内部排序**，整个标题栏作为一个整体，永远低于文档流后面的
`Dock` 和内容区。

**解法**：`createPortal` 到 `document.body`，`fixed` 定位 + JS 算位置。
关掉时 `useLayoutEffect`（不是 `useEffect`，否则会先在 (0,0) 闪一帧），
并监听 `resize` 重算。点击外部收起的判断要同时看触发按钮和面板两个 ref——
面板已经不在按钮的子树里了。

**顺带发现 `NotificationPanel` 有一模一样的 bug**（原本 `absolute right-2 top-11 z-40`），
用户只是先撞到了新加的那个。确认框也是：`fixed inset-0` 的遮罩也只能盖住标题栏
那一条，Dock 与内容区露在外面。三处一并改了。

**守卫测试** `tests/titlebar-overlay.test.ts`：断言标题栏浮层必须 portal，
且不许有成对的 `right-` + `top-` 就地定位。写正则时踩了两脚：
第一版把铃铛上的未读红点（`absolute -right-0.5 -top-0.5`）误判成浮层；
第二版 `\bright-[^-]` 仍然匹配 `-right-0.5`。正解是 `(?<!-)\bright-(?!-)`。

**规律**：毛玻璃/滤镜/transform/opacity<1 都会创建层叠上下文。
**一个元素"看起来在最上层"，取决于它所在的层叠上下文，而不是它的 z-index。**

### 4.9.1 续：同一处的第二个坑——写了个不存在的 token

**症状**（用户实测，接着上一条）：卡片风格和通知面板不一样，圆角明显更小、也没有浮起感。

**第一次的诊断方向也是错的**：以为是两处各自定了不同的圆角值，想统一数值。
实际去查 `tailwind.config.js` 才发现——

| 写的 | 配置里有没有 | 结果 |
| --- | --- | --- |
| `rounded-card` | ❌ 只有 `control`(8px) / `surface`(12px) | 不生成 CSS，圆角为 0 |
| `shadow-panel` | ❌ 只有 `card` / `pop` | 不生成 CSS，没有阴影 |

**Tailwind 对匹配不到的类名是静默的**：不报错、不警告、构建成功、
类型检查也通过（className 就是个字符串）。表现就是"这块样式没生效"。

**顺带发现定位也算错了**：按钮在标题栏**最左边**，用 `right` 对齐会有两个后果——
卡片一路伸到窗口最左沿（贴边很难看），并且横向覆盖到左侧 Dock 的头顶上。
用户要的是"贴着 Dock 右侧展开"。改成**左边缘对齐按钮左边缘**：
`left = max(8, min(buttonRect.left, innerWidth - 256 - 8))`。
其中宽度必须写成常量 `PANEL_WIDTH`，不能靠 `getBoundingClientRect()` 量——
portal 首帧里盒子还没排版，量出来是 0。

**守卫测试**：`tests/design-tokens.test.ts` 新增一条，把源码里所有
`rounded-*` / `shadow-*` 的 token 名拿去和配置注册表比对，未注册的一律红。
注意这和已有的"圆角只用两档"那条**不是一回事**：那条拦的是 `rounded-md`
（Tailwind 自带、有样式、只是不符合收敛规则），这条拦的是**根本不存在**的名字。
两者必须都在，否则第二种情况会从缝里漏过去。

注入验证：把注释里的违规词恢复成真实类名，测试立刻报
`ProfileSwitcher.tsx: rounded-card` + `ProfileSwitcher.tsx: shadow-panel`，再还原。

**规律**：**类名不是类型**。字符串形式的样式 token 写错，编译器一句话都不会说。
凡是"配置里定义的、代码里按名字引用的"东西（Tailwind token、i18n key、
环境变量名），都得有测试拿名字去配置里对。

## 4.10 已完成：跳板机切换（hpc-01 ↔ hpc-02）

### 现状：后端全通，只差渲染层

`config/profiles.json` 里两条 profile **都已经配好**（hpc:2223、hpc-02:2222，
同一台 192.0.2.46 的不同端口）。后端支持度是完整的：

| 能力 | 位置 | 状态 |
| --- | --- | --- |
| 按 id 选 profile | `pickProfile(loaded, id)` | ✅ |
| 连接池分槽 | `pool` 用 `profile.id` 做 Map key | ✅ |
| 能力缓存隔离 | `capabilityCacheKey(profileId)` | ✅ |
| IPC 接收 profileId | 几乎所有 handler 都读 `request?.profileId` | ✅ |

**唯一缺的是渲染层：没有任何地方在选择 profileId**，全部走
`pickProfile(loaded)` 默认取 `defaultProfile`。所以现在两条 profile 里
只有 `hpc` 会被用到，`hpc-02` 是死配置。

受影响的调用点共 **14 处**（全部需要注入 `profileId`）：
`App.tsx`（probe / listJobs / getQuota / getPoints / listJobHistory）、
`BootSplash.tsx`（bootStatus）、`JobsView.tsx`（listJobs / listJobHistory ×2）、
`ResourcesView.tsx`（listNodes / getQuota / getPrices）、
`SubmitJobDialog.tsx`（listNodes + getPrices）、
`TerminalView.tsx`（openTerminal）、`TunnelsView.tsx`（listTunnels / listJobs）。

### 方案：主进程持有"当前 profile"，渲染层不传 id

**不要**让 14 个调用点各自传 profileId——那等于把"当前在哪台跳板机"
这份状态复制 14 份，任何一处漏传就会静默连回默认机（而且无法测试）。
正确做法是把它变成主进程的单点状态：

1. **`ActiveProfile` 模块**（`src/main/profile-state.ts`）
   - `get()`：先读 `KVStore` 的 `connection.activeProfileId`，没有就用 `defaultProfile`
   - `set(id)`：校验 id 存在 → 写 KV → `pool.invalidate(旧 id)` 并且
     **把所有受影响的服务全部作废**（见下）
   - `pick(loaded)`：`pickProfile(loaded, get())` 的糖，替换 ipc.ts 里所有
     `pickProfile(loaded, request?.profileId ?? undefined)` —— 无参调用。

2. **切换时必须清掉的东西**（这是最容易漏的一步）
   - `pool.invalidate(新旧两个 id)`：旧机器的连接留着没意义，新的一次都没连过
   - **终端会话**：`terminal` 里的 shell 是挂在旧机器上的，必须全关，
     否则用户在"新跳板机"标题下敲命令，实际打在旧机器上
   - **端口转发与反向隧道**：转发目标是旧机器的节点名，换了机群可能根本没有
     同名节点。至少要全部断开并提示"切换跳板机已断开 N 条隧道"
   - **传输队列**：正在传的任务必须拒绝切换（给明确理由），
     或者先取消再切。不要静默丢掉别人的 187 MB
   - 远端目录缓存（8 秒 TTL 那个）里的路径属于旧机器

3. **IPC**（三个新方法）
   - `connection:list-profiles` → `{ profiles: [{id,label,host,port,isDefault}], activeId }`
     （**不要返回私钥路径**）
   - `connection:get-active` → `{ activeId }`
   - `connection:set-active` → `{ activeId }`，切换失败要回滚并给出理由
   - `PRELOAD_API_VERSION` **必须 +1**

4. **界面**：放在标题栏右侧，做成一个两行的下拉（`hpc` / `hpc-02`，
   显示"跳板机 01 · 2223"）。理由：这是**全局状态**，不是某个页面的设置——
   放设置页里用户会以为"只影响设置"。切换后必须立刻刷新标题栏三个电量数字，
   否则会拿着旧机器的数据看半天。

5. **必须写的测试**（`tests/profile-switch.test.ts`）
   - 切换后 `pool.acquire` 拿到的是新 profile 的连接（按 `profile.id` 断言）
   - 切换会 invalidate 旧连接
   - 传输进行中拒绝切换，且**队列状态不变**
   - 切到不存在的 id → 报错且 `activeId` 保持不变
   - 能力缓存不串：A 机探测的结果不会在 B 机被读到

### 落地结果（2026-11-05）

上面 1~5 全部实现，测试数 660 → **673**。

| 文件 | 改动 |
| --- | --- |
| `src/main/profile-state.ts` | **新增**。`ProfileState`（get/set/list）+ `switchBlocker`（纯函数准入判断） |

几个实现上值得记住的点：

1. **`switchBlocker` 抽成纯函数**，而不是写在 IPC handler 里。
   handler 要启动 Electron、要造六个服务，测不动；抽出来之后

2. **`drop()` 连新机器的连接也丢**。用户切回 02 通常是因为 01 卡了，

4. **切换失败不能写坏状态**。`set()` 是"先 `pickProfile` 校验、再写 KV"，
   顺序反过来（先写后校验）会让一次失败的切换把用户留在"没有机器"的状态。
   这条有测试守着，注入"先写后校验"会立刻变红。

## 4.11 已完成：文件页的多选与移动

用户提了两件事，第二句点出了第一句的痛点：
「点击文件后应该有变色……**要不然删除的时候都不知道选中的是哪个**」「希望支持多选，能多文件移动、删除」。

### 选中态：不是"没有"，是"有了但看不出来"

第一版其实**有**选中态：`bg-state-info/12`，一层 12% 的淡蓝底。
问题在于同屏还有 hover 的 `bg-ink-50`——两个都是极浅的灰蓝，
在下拉一趟文件列表的过程中根本分不清"我指着的"和"我选中的"。

改成三重标识，且都是**结构性**的而不是靠调色：

| 层 | 做法 | 为什么 |
| --- | --- | --- |
| 底色 | `bg-state-info/15` + `text-ink-900` | 比 hover 重一档，且整行文字一起加深 |
| 左边界 | `absolute inset-y-0 left-0 w-0.5` 实色条 | 不占宽度（否则名称列会左右跳），但一眼能定位到"哪一行" |
| 焦点行 | `ring-1 ring-inset ring-state-info/60` | 键盘移动需要一个"我现在在哪"的落点，否则按↓像凭空跳 |

还有一个容易漏的点：选中和 hover 必须是**互斥分支**（三元表达式），
不能写成 `'hover:bg-ink-50 ' + (active ? 'bg-...' : '')`。
后者在鼠标划过选中行时，hover 的底色会赢——看起来像"选中丢了"。

### 多选：抽成 `lib/selection.ts`

看起来只是"记住点了哪些"，实际有四套语义交叉：

- 单击 = 替换 / 再点同一个 = 取消 / Ctrl = 增删 / Shift = 拉区间
- **锚点**：Shift 的起点是"上一次不带 Shift 的点击"，不是"当前选中项"
- **焦点**：键盘移动需要"当前行"的概念，即使那行没被选中
- 刷新后要 `pruneSelection` 剔掉已经不存在的名字（**不能整体清空**，
  刷新不该让用户重新选一遍）

抽成纯函数后 25 条单测直接断言行为，组件里只留一行 `applyClick`。

**测试抓到一个语义写错**：第一版把 Ctrl+Shift 写成"把区间并进已有选择"，
和 Windows 资源管理器不一致（那里 Ctrl 不改 Shift 区间的语义，
想选两段要分开操作）。这条是写测试时对出来的，不是靠肉眼。

### 移动：新增 `fs:move`，两个必须自己判的规则

`moveLocal` / `moveRemote` 都是"改名到另一个目录"，但有两条前置判断
`fs.rename` 和 SFTP 的 `RENAME` **都不会替你做**：

1. **目标同名必须先 stat 再拒绝**。两个底层实现都**默认覆盖**，
   而集群上没有回收站——覆盖了就真没了。这条和 `copyLocal` / `renameLocal`
   的语义也一致（全项目不存在"静默覆盖"）。
2. **不能把目录移进它自己的子孙**。底层会照做不误，结果是子树从原位置消失、
   新位置又挂在自己下面，整棵树变成打不开的孤儿。界面上一次误操作就能触发。

`fs:move` 的批量语义和 `fs:delete` 一致：**逐条做、逐条报**。
一个文件被占用不该让其余九个都不动——那会让用户完全无法收拾现场。
界面据此回 `移走了 N 项，但…`，且**没搬走的仍保持选中**，用户能看出是哪几个。

### 顺带补的剪贴板

`Ctrl+X` / `Ctrl+C` / `Ctrl+V`，走组件内状态而不是系统剪贴板——
文件名放进系统剪贴板没法表达"这是同一台机器上的路径"，粘到别的应用里
就是一段莫名其妙的文本。只支持应用内、同侧；跨侧请用拖拽或「下载到…」。

### 守卫测试 `tests/file-selection-guard.test.ts`

11 条，盯三件事：选中态必须**不止底色**（防止有人把强调条删了）、
不能退回 `bg-state-info/12`、hover 不能盖掉选中。
注入验证：把强调条删掉并改回 12%，两条立刻红。

`PRELOAD_API_VERSION` 13 → **14**（新增 `movePaths`）。

## 4.12 已完成：登录凭据管理（2026-11-06）

### 要解决的两件事

1. 有些集群只支持密码登录，每次启动都要手输
2. 赠送点数走 LDAP 认证，`transfer` 每次都要再输一遍

存好之后这两处都不用再问。

### 为什么用 `safeStorage` 而不是自己加密

`keytar` 那类库是**原生模块**，编译不过整个项目就装不上——硬约定 7 明令禁止。
`safeStorage` 是 Electron 内置的，各平台落到：

| 平台 | 实现 | 密钥绑什么 |
|---|---|---|
| Windows | DPAPI | 当前**操作系统用户** |
| macOS | Keychain | 登录钥匙串 |
| Linux | libsecret / kwallet | 桌面密钥环；没装就不可用 |

"绑当前系统用户"这点对**「应用发给别人用」**这个目标是白送的好处：
别人拷走 `config/credentials.json` 也解不开，因为密钥在他自己账户下不存在。

### 三类凭据，作用域不同（这是最容易写错的地方）

| 种类 | scope | 为什么 |
|---|---|---|
| `ssh-password` | **profileId** | 每台跳板机可能是不同账号 |
| `key-passphrase` | **私钥绝对路径** | 同一把 key 被多条 profile 复用 |
| `platform-password` | **账号名** | LDAP 是账号级，跨 profile 相同 |

真实错法：把 ssh-password 按账号名存。你在两台机器上都叫 `user01` 但密码不同，
存成一条之后切过去就是"密码错误"，用户会以为自己记错了。

`tests/credentials.test.ts` 里有专门的 scope 隔离断言。

### 三条不能让步的规则

**1. 钥匙串不可用时，拒绝保存，绝不静默存明文。**
Linux 没装 keyring、或 Linux 上 `getSelectedStorageBackend()` 返回 `basic_text`
（意思是"用固定密码加密"，等于没加密）时，都算不可用。
这时只提供「只在本次运行内记住」——进程退出即忘，不落盘。

**2. 明文密码只有一个方向。**
渲染层 → 主进程（`setCredential`）是唯一带明文的一次调用；主进程**永不**回传密码，
所以列表里只有 kind / scope / 时间。

更进一步：**转账用已存密码时，明文完全不经过渲染层**——
界面只发 `{ useStoredPassword: true }`，主进程自己从库里取。

**3. 密码不进日志、不进命令台。**
`transfer` 的密码从 stdin 读，本来就不在命令串里；`setCredential` 只写进加密库。
所以 `trace/store.ts` 里不可能出现密码——这是结构决定的，不是靠过滤。

### 挂在哪个位置

凭据解析在 **`ProfileState.current()`** 里注入（`withCredentials()`）。

理由和"当前用哪台跳板机只有一份状态"完全一样：所有要连网络的地方都从这里拿 profile，
所以在这一处接上，终端/隧道/传输/诊断/转账全都自动用上，不需要各自去问。
在 14 个调用点各取一次凭据，漏掉一处就是"某个功能莫名其妙还在要密码"。

### 配套改的一处配置校验

`profiles.ts` 原来要求 `method: 'password'` 时 `auth.password` **必填**。
这条现在**放开了**：继续强制必填等于逼用户把明文写进 `profiles.json`，
正好是要消掉的东西。

"真没配密码"的报错移到 `session.ts`——那里能说清"去设置里存一下"，
而在加载配置时拦下来会让整个应用起不来。

### 界面

`components/CredentialsCard.tsx`，在设置页最上面。

- 钥匙串不可用时**禁用保存并说明原因**，只留"本次记住"
- 密码框永不回显（主进程不传回来，所以只能显示"已保存"）
- 检测到 `profiles.json` 里有明文时给迁移提示，但**不替用户改那个文件**

`tests/credentials.test.ts`（24 条）+ `tests/credentials-resolve.test.ts`（15 条）。
注入验证：把加密那一步改成直接存明文，"存盘内容里没有明文"那条立刻红。

`PRELOAD_API_VERSION` 15 → **16**（新增 4 个方法）。

### 「测试密码对不对」的原理

密码是**加密存**的。程序解开密文只能证明"密钥还在"，**不能证明里面那串等于用户的真实密码**
——它没有正确答案可以比对。所以唯一可靠的办法是**拿它去问认证方**，看对方接受还是拒绝。

三种凭据的裁决方和代价完全不同：

| 凭据 | 谁来裁决 | 代价 |
|---|---|---|
| `key-passphrase` | 本地用口令解一次私钥，能解出合法结构就对 | 零网络 |
| `ssh-password` | 真发一次 SSH 认证 | 一次连接（1~2 秒） |
| `platform-password` | 只有 `transfer` 走 LDAP | **一次转账请求** |

**平台密码为什么只能用 transfer 验**：`scir-account -d`（查余额）走的是 SSH 权限，
**根本不碰 LDAP**——密码错了它也照样返回余额。拿它测会给出**假阳性**，比不测更糟。

**探针用 `--points=0 --target=<自己>`**：0 点转给自己 = 空操作，但会真的走到 LDAP 那一步。

### 判定的核心规则：只认一个明确的失败信号

```
认证失败（rc:49 / AuthFailed / kind='auth'）→ 密码错
其它一切（业务报错、参数非法、点数必须大于 0）→ 密码对
```

因为**认证是第一道关口**，只要失败原因不是认证，就说明密码已经过了。
反过来：不去猜"成功长什么样"——平台的成功输出格式没有保证，用正面关键词判会误杀。

这条规则写反的代价是不对称的：把"网络不通"或"点数非法"判成"密码错"，
用户会反复去改一个**本来正确**的密码，永远改不对。

`tests/credentials-test.test.ts`（16 条）专门盯这个。注入验证：
把"业务报错也算通过"改成"有 `error:` 就算错"，那条立刻红。

探针的 SSH 连接**不校验主机指纹**：这个探针只回答"密码对不对"，
指纹问题在正常连接时已经会拦，混进来只会让用户看到"连不上"而误以为密码错。

`PRELOAD_API_VERSION` 16 → **17**（新增 `testCredential`）。

## 4.13 视觉规范：马卡龙配色 + 可切换字体（2026-11-06）

### 一条不能让步的约束

**马卡龙粉彩只能做「面」，不能做「字」。**

`#f9d5e5` 衬白底的对比度是 **1.32:1**。写 `text-macaron-pink` 能编译、能渲染、
界面上"有一点东西"，但没人看得清——这类缺陷最难发现，因为它看着**不像坏的**。

而这个项目对对比度的要求是硬的：状态色同时被当作背景、边框、**正文**三种角色，
源码里 170+ 处是正文色。所以配色分成两层：

| 层 | 用什么 | 例子 |
|---|---|---|
| 面（背景、装饰、描边、图表填充） | `macaron-*` 六色粉彩 | 卡片顶条、hover 底、徽章底 |
| 字（正文、语义提示） | 同色系的**深调** `ink-*` / `state-*` | `state-ok` 是薄荷的深调 |

一句话：**色相走马卡龙，明度必须够深才配做字。**

`tests/design-tokens.test.ts` 有守卫禁止 `text-macaron-*`。

### 色板

完整定义在 `tailwind.config.js`，关键值：

```
ink      50 #faf8fd → 900 #2c2637   （带紫调的暖灰，全站地基）
         400 #a99bc0 = 2.58:1，只做边框/禁用，不做文字
         500 #6b5f80 = 5.88:1，文字色的最低档
accent   400 #8b79c9（焦点环）/ 500 #6d5bb8（5.47:1，可做按钮底配白字）
state    ok #0f766e / wait #b45309 / bad #be123c / info #1d4ed8
macaron  pink #f9d5e5 mint #cdeee0 lilac #ddd2f3
         butter #fbeec2 peach #fbdccb sky #cfe4f7
canvas   #fbf9fe（页面底）
night    sub/body/emph/bad（深色底文字，别和 ink 混用）
```

**`state-*` 的四道检查**（改值前必须重算，测试会拦）：

1. 作为文字，衬同色 6% tint ≥ 4.5:1
2. 作为文字，衬纯白 ≥ 4.5:1
3. 作为**实色背景**，衬白字 ≥ 4.5:1 ← 最狠，粉彩在这里必然失败
4. 配置值与 `tests/design-tokens.test.ts` 里的 `STATE` 常量一致

### 字体：方案而不是自由组合

三套在 `src/renderer/src/lib/font-theme.ts` 里登记，`main.css` 里各自对应
一组 CSS 变量，切换只是改 `<html data-font>`：

| id | 标题 | 正文 |
|---|---|---|
| `modern`（默认） | 系统无衬线 | 系统无衬线 |
| `editorial` | 衬线 | 系统无衬线 |
| `technical` | 等宽 | 系统无衬线 |

**为什么不给"标题选一个、正文选一个"两个下拉**：中文可用字体极少
（Windows 上无衬线基本只有微软雅黑），自由组合九成会配出"标题宋体 + 正文雅黑"
那种像误操作的结果，而且衬线中文在 12.5px 上会糊。组合错了用户只会觉得字难看。

首帧前就应用（`main.tsx` 里 render 之前），否则会闪一下"字跳变"。
存 localStorage，读失败退回默认——字体偏好丢了不痛，首屏白掉才是事。

`tests/font-theme.test.ts` 有一条**跨文件一致性**守卫：
`FONT_THEMES` 和 `main.css` 的 `[data-font='x']` 必须一一对应。
加了清单忘写 CSS → 选了没反应；写了 CSS 忘加清单 → 规则永远匹配不到。**两边都不报错。**

### 排版与交互

- 圆角 8/12 → **10/14**（马卡龙偏圆润，但不能再大，否则表格行变成一堆胶囊）
- 阴影换成**带紫的深色** `rgba(76,58,112,…)`，透明度压低——
  马卡龙的"轻"来自几乎看不见的阴影，不是浓重投影
- 正文行高 1.55 → **1.65**（中文比西文更"紧"，12.5px 读三行以上会挤）
- `PageShell` 边距随断点走：窄窗口 `px-5 py-5`，`compact` 起 `px-8 py-7`
- 卡片可选的顶部 3px 色条（`Card` 的 `tone` 属性），**仅装饰不承载语义**——
  语义一律走 `state-*`，否则同一个颜色会有两种含义

## 4.14 主题化改造（2026-11-06）

### 为什么上一轮的"马卡龙"看起来没改到位

上一轮只改了 `tailwind.config.js` 里的 token **值**，但组件里大量用的是**原始色类名**：

| 类名 | 数量 | 问题 |
|---|---|---|
| `bg-white` | 96 处 | 卡片 / 输入框 / 按钮底**混用**，含义完全不同 |
| `bg-ink-900` | 32 处 | 既是主按钮底，启动页和 Dock 也是它 |

这些类名**不属于主题**——改 token 值改不到"白色是不是纯白"。所以视觉上"变了，但又好像没变"。

### 第一步：铺管道（已完成）

给原始色建立语义替身，并做了一次批量替换：

| 新 token | 含义 | 替代 | 数量 |
|---|---|---|---|
| `surface` | 卡面 / 浮层面 | `bg-white` | 96 |
| `inverse` | 反色面（主按钮底） | `bg-ink-900` | 29 |
| `scrim` | **固定深色**（启动页、Dock） | 那两处的 `bg-ink-900` | 3 |
| `field` | 输入框面 | 预留，当前 = surface | — |

`bg-white/10`（2 处）**刻意保留**——那是启动页深色底上的半透明白装饰，
不是"面"，替换成 `surface` 会变成一块白斑。

`scrim` 不随主题变：启动页和 Dock 的深色是品牌锚点，切到别的主题也不能变色。

### 第二步：token 变量化（已完成）

```js
// tailwind.config.js
const c = (name) => `rgb(var(--c-${name}) / <alpha-value>)`
```

用 `rgb(... / <alpha-value>)` 而不是直接塞 hex，是为了保住 `bg-surface/70` 这类
透明度修饰符——标题栏和浮层的玻璃感全靠它。

**一个必须知道的坑**：`main.css` 里不能写 `background: theme('colors.canvas')`。
Tailwind 会把变量色展开成 `rgb(var(--c-canvas) / <alpha-value>)`，
而 `<alpha-value>` 在普通 CSS 属性里**不会被替换** → 整条声明失效、背景变透明。
页面看着"好像还是白的"，其实是 html 的默认白。所以直接写 `rgb(var(--c-canvas))`。

### 主题清单

现在三套：`dunhuang`（默认）、`claude`、`classic`。各维度的具体取值见下一节的对照表——**不要在这里再抄一份**，
两份表格迟早会不一致，而"文档自相矛盾"比"文档没写"更难排查。

默认主题挂在 `:root` 上（不是 `[data-theme='dunhuang']`），
所以"从没选过"和"选了敦煌"在 DOM 上是同一个状态，不会有两套生效路径。

> 本节原来记的是 `classic` + `macaron` 两套。马卡龙已于 2026-11-06 下线、敦煌成为默认、
> Claude 作为第三套保留，变更理由与取舍见下一节。


### 测试：从"验一组硬编码值"升级为"遍历所有主题"

原来的对比度测试写死了 `const STATE = { ok: '#047857', ... }`，
只有一个主题时够用，但**加新主题后新主题的色值完全没人检查**——
而新主题恰恰最容易配错（粉彩做文字必然不达标）。

现在 `readThemeStates()` 直接从 `main.css` 解析 `:root` 和每个
`[data-theme='x']`，逐主题逐色跑三道对比度。加主题不用改测试，测试自动覆盖。

注入验证：把马卡龙主题的 `state-bad` 改成粉彩 → 立刻红；
删掉一个主题变量 → 两条守卫同时红。

`tests/theme.test.ts`（16 条）还有一条**跨文件双向一致性**守卫：
`THEMES` 清单与 `main.css` 的 `[data-theme='x']` 必须一一对应。
加了清单忘写 CSS → 选了没反应；写了 CSS 忘加清单 → 规则永远匹配不到。两边都不报错。

### 纸墨主题：`claude`（Claude · 纸墨）

用户要求加一套 Claude 风格。它不是"更暖的马卡龙"，而是**另一种设计语言**：

| 维度 | 取值 | 为什么 |
|---|---|---|
| 底色 canvas | `#faf9f5` | 带黄的米白，Anthropic 官网主背景 |
| 主色 accent-500 | `#b8552f` | 赤陶橙。**比 logo 色 `#d97757` 深一档**——logo 色做白字底只有 3.12:1 |
| 主色 accent-400 | `#d97757` | logo 原色，只做焦点环（不做白字底） |
| 反色面 inverse | `#2b2a26` | 深墨棕，白字 14.36:1 |
| 圆角 | **8 / 12** | 比经典的 10/14 **更小**。印刷品是方正克制的 |
| 阴影 | `0 1px 2px rgba(38,37,33,.04)` | 几乎没有，层次靠边框和底色差 |
| 动效 | 160ms `cubic-bezier(.2,0,.2,1)` | 干脆、无回弹 |
| 卡片内边距 | 24 / 20 | 留白多，像纸张的页边距 |
| 装饰色 | 赤陶粉 / 鼠尾草 / 沙 / 奶油 / 陶土 / 雾 | 矿物色，和米白底同源 |

**中性色全部带黄**（`#6e6a5f` 而不是冷灰）。这一步是"暖"的真正来源——
如果灰阶不变只换强调色，看起来会像"给旧界面加了个橙色按钮"。

状态色也跟着变"土"：橄榄 `#46700c`、赭石 `#96590d`、砖红 `#b3261e`、石板蓝 `#3a6b8a`。
四色都过了三道对比度（最低 5.18:1）。

**推荐搭配字体**：`editorial`（标题衬线），但**不会自动切换**——
字体是独立选择器，主题擅自改别人的选择是隐藏行为。主题卡片上只标一句"建议搭配"。

### 主题作用到哪些地方

主题是**全局**的，通过 CSS 变量作用到每一个用语义 token 的地方：

| 界面/组件 | 受影响的 token |
|---|---|
| 所有页面底色 | `canvas` |
| 所有卡片、弹窗、下拉、命令面板 | `surface` + `--r-surface` + `--shadow-*` |
| 所有输入框 | `field` |
| 所有主按钮（送点数、确认、提交作业…） | `inverse` / `on-inverse` |
| 全部文字 | `ink-50` ~ `ink-950` |
| 状态标记（跑中/排队/报错/连接灯） | `state-*` |
| 卡片顶部色条 | `macaron-*`（装饰槽位，各主题填自己的色） |
| 焦点环 | `accent-500` / `accent-400` |
| 圆角、阴影、卡片留白、动效 | `--r-*` / `--shadow-*` / `--pad-card-*` / `--dur-*` / `--ease-*` |
| **启动页、左侧 Dock** | **不受影响**（`scrim` 固定深色，不随主题变） |
| 表格行高 | **不受影响**（主题只调大容器留白） |

### 2026-11-06 变更：马卡龙下线、敦煌成为默认；Claude 保留为第三套

用户指定：**取消马卡龙主题**，整体改成敦煌风格，并且**严格使用五个指定色**：
`#ECD98B`、`#AAAAC2`、`#03875C`、`#9A4C43`、`#4E3227`。

现在是三套：

| id | 名称 | 定位 |
|---|---|---|
| `dunhuang` | 敦煌 · 矿物 | **默认**，挂在 `:root` 上，五个指定色 |
| `claude` | 纸墨 · Claude | 米白 + 赤陶 + 墨棕，印刷品语言 |
| `classic` | 暖紫 · 经典 | 应用最初的配色，原样保留 |

#### 三套主题的差异化（不是同一套换个色）

| 维度 | 敦煌 | 纸墨 | 暖紫 |
|---|---|---|---|
| 画布 | `#F8F0DA` 暖沙金 | `#FAF9F5` 米白 | `#FBF9FE` 冷暖紫 |
| accent | `#9A4C43` 赭红 | `#B8552F` 赤陶橙 | `#6D5BB8` 紫 |

#### 五个锚色怎么落到 30 多个槽位上

五个色填不满，而且其中两个**做文字是不可读的**：`#ECD98B` 衬白 1.41:1、
`#AAAAC2` 2.27:1。所以分两步：

**第一步：锚色承担它擅长的角色**

| 锚色 | 名称 | 用途 | 对比度 |
|---|---|---|---|
| `#4E3227` | 深棕（土） | `ink-900` 正文、`inverse` 主按钮底 | 11.61:1 |
| `#9A4C43` | 赭红（赭） | `accent-500` 主色、`state-bad` | 6.02:1 |

所以可以用饱和锚色。这样五个色都真的出现在界面上，而不是只活在"色相"里。

#### 顺手改的命名

`macaron-*` → **`decor-*`**。马卡龙主题删了之后，这个名字会让人以为还有马卡龙主题；
`decor` 才说得清它是"通用装饰槽位"。守卫也同步改成禁止 `text-decor-*`。

#### 敦煌的视觉语言

壁画是**矿物颜料 + 土墙**：饱和但不刺眼、表面是平的、边缘硬朗。所以：

| 维度 | 取值 | 依据 |
|---|---|---|

| 卡片 | 纯白 | 像贴在墙上的纸 |
| 圆角 | **6 / 10** | 比经典(10/14)、纸墨(8/12)都更方 |
| 阴影 | `0 1px 2px rgba(78,50,39,.06)` | 壁画没有投影，层次靠底色差 |
| 动效 | 150ms `cubic-bezier(.2,0,.15,1)` | 沉稳、无回弹 |

## 4.15 打包与分发（2026-11-06）

路线图上最后一个 ⏳。目标不是"能打出 exe"，而是**发给同学、他双击装完就能用**。
这两句话的差别决定了下面四个决定。

### 决定一：配置写到 `%APPDATA%`，不写安装目录

原来是 `join(app.getAppPath(), 'config')`。**打包后 `getAppPath()` 指向 `resources/app.asar` 内部**，
也就是安装目录——`Program Files` 下普通用户**没有写权限**。

这个 bug 的可怕之处在于它不报错：读得到（asar 能读），写凭据 / 写 `known_hosts` /
记默认目录**静默失败**，用户只会觉得"密码存不住""每次都要重选目录"，很难联想到路径权限。

现在**默认**仍然是 `app.getPath('userData')/config`，但"放哪儿"已经是可配置的了
（三档模式 + 便携模式，见 §4.16）。这里只保留那条不能退让的底线：

| 场景 | 目录 |
|---|---|
| 默认 | `app.getPath('userData')/config`（一定可写，按系统账户隔离） |
| 便携（用户显式选，或程序目录下已存在 `config/`） | `<exe 所在目录>/config` |
| 自定义 | 用户选的任意可写目录 |
| 环境变量 `HPC_WORKBENCH_CONFIG_DIR` | 压过以上一切 |

**唯一不变的原则：绝不能因为"打包了"就把配置写进 `app.getAppPath()`**——
那是 asar 内部。便携模式写的是 **exe 旁边**，那是用户真正够得到的地方，而且会先验可写。

**`userData` 的目录名来自 `package.json` 的 `productName`，不是 `name`。**

踩过一次：`name` 是 `hpc-workbench`、`productName` 没写，于是装完弹出来的启动页写着
`C:\Users\xxx\AppData\Roaming\hpc-workbench\config`——而安装目录、exe、开始菜单全都叫
`HPC Workbench`。用户第一反应是"我装错盘了？"。

Electron 的规则（实测确认）：`app.getName()` 取 `productName ?? name`，`userData` 用 `app.getName()`。
所以 `package.json` 里 `productName` 必须写，且要和 `electron-builder.yml` 的 `productName` 一致。

⚠️ 改这个名字等于**换配置目录**：已有凭据不会跟过去，用户会看到"密码又丢了"。
所以要么一开始就定对，要么得同时写迁移逻辑。现在定对了，以后再改就要付这个代价。

启动时还会 `mkdirSync(recursive)` 先建出来——首次运行那个目录**并不存在**，
不建的话第一次写凭据会因为"父目录缺失"失败，而失败点在异步流程里。

### 决定二：装到用户目录，不要管理员

`nsis.perMachine: false` → 装到 `%LOCALAPPDATA%\Programs`，**全程不弹 UAC**。
`oneClick: false` + `allowToChangeInstallationDirectory: true` → 让人能装到 D 盘。

这不是洁癖：目标用户是同学，很多人**不是**自己电脑的管理员。

### 决定三：exe 里不能只有代码，还要"能找到配置"

`extraResources` 把 `profiles.example.json` 放进安装目录的 `resources/`（asar 外面，
资源管理器里能直接看到、双击打开）。

配套加了 `app:open-config-dir`（`PRELOAD_API_VERSION` 17→**18**）：
未配置横幅第一个按钮就是「打开配置目录」。因为打包后那条路径是
`C:\Users\<名字>\AppData\Roaming\HPC Workbench\config`——**没有人会去地址栏手敲它**。
光给文字路径等于没给。

### 决定四：不收 `cpu-features`

`ssh2` 把它列为 *optional* 原生依赖。本机装的时候它根本没编译出 `.node`，
而 ssh2 的用法是 `try { require('cpu-features')() } catch {}`——缺了就走纯 JS，功能不受影响。
收进来反而会让 electron-builder 去 rebuild 原生模块（要 MSVC），并带上一个 ABI 对不上的 `.node`。
所以 `files` 里显式排除，同时 `npmRebuild: false`。

### 产物结构（实测）

```
release/win-unpacked/
  HPC Workbench.exe          180 MB   Electron 本体 + 应用图标
  resources/
    app.asar                 6 MB     只有 node_modules / out / package.json，1080 个条目
    profiles.example.json    1.5 KB   给人复制的模板
```

asar 里**只有**这三样东西：`out/main` ✅、`ssh2` ✅、`electron-store` ✅、
devDependencies ❌、`cpu-features` ❌。这条要经常验——多打进一个 devDep 就是几十 MB。

### 图标是生成的，不是二进制

`scripts/make-icon.py` → `build/icon.ico`（16/32/48/64/128/256 六档）。

深棕圆角方块 + 三根沙金竖条（渐深到浅），就是标题栏那三枚"电量"数字。
小尺寸下唯一的形状是"三根竖条"，16px 也认得出。

用脚本而不是提交 ico，是因为**品牌色跟着主题走**：敦煌锚色一改，图标得重生成。
`.ico` 在仓库里是二进制、diff 里什么都看不见。脚本里画形状用 **SDF**（有符号距离场）
算覆盖率而不是超采样——16px 的边缘干净与否一眼能看出来。

### 命令

```bash
npm run pack   # release/win-unpacked/，调试用，30 秒
npm run dist   # release/HPC Workbench-0.1.0-setup.exe
```

首次 `dist` 会下载 NSIS 工具链（约 2 MB），之后走缓存。

### 还没做的（属于"发出去"的下一层）

1. **没有代码签名** → 别人第一次运行会看到 SmartScreen「Windows 已保护你的电脑」，
   要教他点「更多信息 → 仍要运行」。证书要花钱，自用不发商店可以先不管。
2. **首次配置仍要手改 JSON** → 下一步做「首次运行向导」，在界面里填主机/账号/密码。
   现在的横幅只是把"手改 JSON"变得找得到而已。
3. **只有 x64、只有 Windows**。ARM64 要另加 target；macOS 需要一台 mac 出包
   （`safeStorage` 在 macOS 走 Keychain，代码侧已就绪，但没验过）。

## 4.16 配置目录：可配置 + 便携模式（2026-11-07）

用户诉求很直白：**"配置目录要能改，而且要能放在安装目录旁边用。"**
原来的三分支（env / userData / appPath）只解决了"打包后别写安装目录"，
但把"放哪儿"这件事**定死**了：装到 E 盘、想连配置一起拷走，做不到。

### 模型：三档模式，显式优先

存 `%APPDATA%\<productName>\config-location.json`：

```json
{ "mode": "auto | portable | custom", "dir": "只有 custom 用" }
```

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `HPC_WORKBENCH_CONFIG_DIR` | 环境变量。**优先级最高**，界面上显示"环境变量"并禁用按钮 |
| 2 | `custom` | 用户选的目录 |
| 3 | `portable` | `<程序目录>/config` |
| 4 | `auto` | 程序目录下有 `config/` 就用它，否则用 userData |
| 5 | 默认 | `%APPDATA%\<productName>/config` |

**为什么不用隐式优先级**：如果写成"程序目录下有 config 就优先"，那么用户
在设置里选了 D 盘、程序目录里又有个残留的 config，他的选择就被静默忽略。
所以显式模式**不猜**——选了 custom 就是 custom。

**`auto` 为什么不主动建目录**：探测时顺手 `mkdir -p` 的话，一次启动就把应用
永久变成便携模式，而用户根本没做过这个决定。`auto` 只认**已存在**的目录。

### 需要调整的逻辑（这次改动的全部范围）

| 位置 | 改动 | 为什么必须改 |
|---|---|---|
| `config-dir.ts` | 返回值从 `string` 变成 `{dir, source, portableDir, defaultDir, fallback?}`；新增 `parseConfigLocation` | 界面要显示"为什么是这个目录"，只回一个路径没法解释 |
| `config-location.ts`（新） | 指针读写、`isDirWritable`、`canCreateAt`、`copyConfigFiles` | 这些都碰 `fs`，和纯解析分开才测得动 |
| `appRoot()` | 打包时用 **`dirname(process.execPath)`**，不是 `app.getAppPath()` | 后者指向 `app.asar` **内部**，用户永远够不到；"程序目录"必须是 exe 所在目录 |
| 启动装配 | `configResolution()` **解析一次并缓存** | `known_hosts` / 凭据库 / 能力缓存都在启动时用这个路径构造好。运行中重算会让"一半服务写旧目录、一半读新目录" |
| 换目录 | 写指针 + **`app.relaunch()` 重启** | 上一条的直接后果：不支持热切换，就别假装支持 |
| 换目录 | **先 `copyConfigFiles` 再写指针** | 顺序反了，一旦搬到一半失败，应用已指向新目录而文件还在旧目录 = 真的"配置丢了" |
| 换目录 | 目标已有同名文件**不覆盖** | 新目录里那份可能是用户特意放的、更新的一份 |
| 可写性 | 便携/自定义目录都要**真写一次**探测 | `fs.access(W_OK)` 在 Windows 上对 ACL 判断不可靠，尤其"管理员装的、普通用户跑"。探测不准就又回到"静默写不进去" |
| `ipc.ts` | 新增 `app:config-dir` / `app:set-config-dir` / `app:pick-config-dir`；`app:open-config-dir` 加白名单参数 | `which` 只接受 `current` / `appRoot`——**不把任意路径交给 `shell.openPath`** |
| `api-version.ts` | 18 → **19** | 改了 preload 接口 |
| 设置页 | 新增 `ConfigDirCard` | 三个按钮：更改… / 用程序目录 / 恢复默认；显示来源徽标 |

### 便携模式的正确用法

把 `config\` 放进**安装目录**（exe 旁边），下次启动自动认：

```
E:\HPC Workbench\
  HPC Workbench.exe
  config\            ← 放这儿
    profiles.json
    credentials.json
```

拷走整个文件夹 → 换台机器照样用（凭据解不开是正常的，DPAPI 绑系统账户，重填一次）。

⚠️ **装到 `Program Files` 时便携模式会失败**（普通用户无写权限）。
这时解析器会退回 userData 并在界面上写明原因，**不会静默失败**——
那正是 §4.15 决定一要根治的病。

### 已知边界

- 换目录会**重启**应用，不是热切换。终端/隧道会断（本来也该断）。
- `credentials.json` 搬到新目录后**同机同账户**能解开；换机器解不开，要重填。
- 没有"合并两个目录"的逻辑：目标已有同名文件就跳过，不比对内容。

## 4.17 首次运行向导（2026-11-08）

原来没配置时的界面是「一条横幅 + 让用户把 `profiles.example.json` 复制成
`profiles.json` 再手填」。对写代码的人够用，对"装完想连集群的同学"完全不够：
不知道文件放哪、哪些字段必填、密码该不该写进去。

现在没有配置文件时**整页进入向导**（Dock 藏起来，TitleBar 保留——无边框窗口不能没有关闭按钮）。

### 四步

| 步 | 问什么 | 默认 |
|---|---|---|
| 1 存放位置 | 默认（`%APPDATA%`）/ 程序目录（便携）/ 自选目录 | 默认 |
| 2 连接信息 | 名称、主机、端口、用户名、认证方式（私钥或密码）；可从上一步的 SSH 配置导入 | 端口 22、方式=私钥 |
| 3 隧道端口 | 集群侧监听端口 / 本机代理端口 | **21056 / 7897**，带醒目提醒 |
| 4 完成 | 显示**生成的文件绝对路径** + 下一步做什么 | — |

提交时：`app:setup-apply` → 主进程校验 → 写 `profiles.json` → 密码/口令进钥匙串；
再 `app:set-tunnel-defaults` 把隧道端口存成用户偏好（存在 `capabilities.json` 那个 KV 里，
键 `tunnel.reverseRemotePort` / `tunnel.reverseLocalPort`）。
**隧道端口存失败不挡配置**——配置文件已经能用了，值得为一句话卡住向导吗。

### 多主机：一次导入可以写入多台

向导第 2 步的导入卡片下面有「其它主机也一起加进来」的开关，勾了就一起写进 `profiles`。

**这是必须的，不是加分项**：`profiles` 本来就是数组，标题栏的跳板机切换器列的就是它。
只写一台的后果很具体——用户 `ssh config` 里明明配了两台登录节点（2223 / 2222），
装完却只能连一台，切换器里空空如也。

实现上附带主机是**尽力而为**：校验不过（缺用户名、私钥不存在、id 重名）就跳过并进 `warnings`，
不影响主配置写盘。主配置不合格才整体失败。

### 事后调整：两个入口

改端口 / 换主机不该逼用户去 `%APPDATA%` 里翻文件。设置 → 配置目录给了两个：

| 入口 | 做什么 | 适合 |
|---|---|---|
| **编辑配置文件** | `shell.openPath(profiles.json)` 用系统默认程序打开 | 改一个端口、加一台主机（**推荐**） |
| **重新配置…** | 把 `profiles.json` 改名成 `.bak-<时间戳>` → 重启 → 回到向导 | 推倒重来 |

`重新配置` **不删 `credentials.json`**：密码和主机是分开存的，重配主机通常还想用同一个密码。

⚠️ `重新配置` 是**整体重建**，多 profile 时会全部重写。只改一台时用前者。

### 为什么隧道端口要在向导里问

`21056` 不是随手挑的数字：**必须等于集群 `~/.profile` 里 `http_proxy` 的端口**，
否则集群上 `pip` / `conda` / 各种 CLI 走代理会连不上，而报错只说"连接被拒绝"，
完全指不到端口上来。`7897` 是本机代理（Clash）端口，别人可能是 7890 / 10809。

这两个值以前是 `TunnelsView` 里的**硬编码常量**，改一次只在当前会话有效、
下次打开又变回去。现在它们被持久化，隧道页启动时读回来。

**为什么不默认 55555**（原手工命令里的值）：

| 端口 | 问题 |
|---|---|
| 55555 | 共享登录节点上被别的账号长期占着，绑不上 |
| 55556 | 落在内核临时端口段（32768–60999），会被别人的出站连接临时征用，表现为"时好时坏、`ss` 查不到" |
| **21056** | 32768 以下，不会被临时端口抢走 |

用户自己填进这个区间的，`validateTunnelPorts` 会**警告但不阻止**——他可能确实有分配，
但默认值必须避开。

### 配置文件格式

路径（三选一，见 §4.16）：

| 模式 | 文件位置 |
|---|---|
| 便携 | `<安装目录>\config\profiles.json` |
| 默认 | `%APPDATA%\HPC Workbench\config\profiles.json` |
| 自定义 | 用户选定的目录 |
| 环境变量 | `HPC_WORKBENCH_CONFIG_DIR` 指向的目录 |

向导生成的样本（真实写盘内容）：

```json
{
  "$comment": "由首次运行向导生成。密码不在这里——它在系统钥匙串里（设置 → 登录凭据）。手工编辑也可以，改完重启应用即可生效。",
  "version": 2,
  "defaultProfile": "cluster",
  "profiles": [
    {
      "id": "cluster",
      "label": "我的集群",
      "host": "login.example.edu.cn",
      "port": 22,
      "username": "user01",
      "auth": { "method": "key", "privateKeyPath": "~/.ssh/id_ed25519" }
    }
  ]
}
```

`$comment` 是普通键，`validateProfiles` 会忽略它——**JSON 不允许注释**，想留说明只能用这种键。

### 必填与校验规则

两处都在做校验，但**职责不同**：`shared/setup.ts` 给输入框旁边的即时提示，
`profiles.ts` 是写盘前的最终裁决（同一套 `validateProfiles` 启动时也在用）。
规则只允许在 `profiles.ts` 里定义一次，向导这边是它的**子集**。

| 字段 | 必填 | 规则 | 不满足 |
|---|---|---|---|
| `profiles[].id` | 是 | `[A-Za-z0-9_-]+`，同文件内唯一 | 向导自动生成：中文名 → `cluster` |

| `username` | **是** | 非空、无空格 | 拦下 |
| `auth.method` | **是** | `key` 或 `password` | 拦下 |
| `auth.privateKeyPath` | method=key 时**必填** | 支持 `~`；**写盘前检查文件是否存在**；`.ppk` 拒绝并提示 puttygen 转换 | 拦下（不生成连不上的配置） |

的环境——第一次用就踩坑，比多填一个框糟得多。

### 从 `~/.ssh/config` 导入

第 2 步顶部会自动读 `~/.ssh/config`：**读到就按第一台自动填好**（名称/主机/端口/用户名/私钥路径），
其余主机点一下即可切换；读不到就只显示一句"手填即可"。
「换个位置…」可以指到任意文件**或**目录（`config` 不在默认位置的人）。

> ⚠️ 这里踩过一次：第一版是"列出来等你点"，结果用户看到列表上写着 `:2223`、
> 下面的端口框还是 `22`，第一反应是"导入没生效"。**「导入」意味着"帮我把值填上"，
> 不是"给我看一眼"**。自动填只在表单**没被动过**时发生（`touched` ref），
> 免得覆盖用户已经手敲的内容。

**只认四个关键字**：`HostName` / `User` / `Port` / `IdentityFile`，
外加 `ProxyJump`——但它只用来**报警告**（本应用是直连的），不实现跳转。

三条必须照抄的 ssh 语义（写错了导入就是"给用户塞错值"）：

| 语义 | 说明 | 写错的后果 |
|---|---|---|
| **先到先得** | 同一关键字在多个匹配块里出现，**第一次**生效 | `Host *` 放末尾会把每台主机自己的 `User` 全改掉 |
| **一行多模式** | `Host a b c` 是三个主机 | 少列主机 |
| **`Host *` 不算主机** | 通配块只提供默认值，不进列表 | 列表里出现一堆看不懂的 `*` |

**不做的部分**（都会在界面上给出警告，不静默吞掉）：

- `Include` 不展开 → 少的主机无从解释，所以明说"有 N 处 Include 没展开"
- `Match` 整块跳过（条件匹配超出这个功能的范围）
- `ProxyCommand` 忽略、`%d`/`%h` 之类的 token 不展开

**私钥判断**（渲染层没有 fs，只能在主进程做）：

- `~` 展开成家目录；**相对路径相对 `config` 所在目录**（这是 ssh 的规则，不是相对 cwd）
- 文件是否存在 → 不存在就在按钮上标红，别等生成配置时才拦
- 是否带口令 → 读 OpenSSH 私钥头部的 ciphername（`none` 表示没加密）；
  PEM 老格式看 `Proc-Type: 4,ENCRYPTED`。带口令时提示用户去填「私钥口令」
- `.pub` 公钥**不进候选列表**——拿公钥当私钥只会得到一条看不懂的解析错误

> 实测：本机 `C:\Users\alice\.ssh\config` 里两台（`hpc` 2223 / `hpc-02` 2222，
> 都是 `alice` + `~/.ssh/id_rsa`）能被完整解析出来，私钥存在且无口令。

## 4.18 反向隧道：两处"看着像别人、其实是自己"的误报（2026-11-11）

### 1. 「21056 被占了（账号 alice 的进程）」

用户当场反问：「我就是 alice，难道是 Codex 单独建的隧道？」

**不是别人，就是他自己已经开着的那条。** 反向隧道的监听端口是 sshd 以**你的账号**
在集群上创建的，所以 `ss -ltnp` 查到的 owner 永远是当前账号——这个信息只能说明
"有个进程用你的账号占着"，说明不了"是本应用的哪条隧道"。

修法：`FallbackInfo` 增加 `ownerIsSelf`（`openWithFallback` 接 `selfUsername`，
调用方传 `profile.username`）。命中时文案改成：

> 21056 被占了 —— **就是你自己**（集群上那个监听是 sshd 用你的账号建的，
> 多半是已经开着一条同端口的隧道，看下面「进行中」）

### 2. 「集群出口 A，你本机是 B —— 这条隧道没连到你的电脑」

两边走的是**同一个 Clash、同一个 `api.ipify.org`**，出口却不同。最可能的原因不是
隧道坏了，而是 **Clash 用了 url-test / load-balance 节点组**：两次请求落到不同上游，
出口 IP 天然不同。原来的判定只看"IP 是否相等"，把正常配置说成坏的。

修法：`forward:verify` 在探测前后各读一次**这条隧道的计数器**
（`reverseTunnels.get(tunnelId)` 的 `connections/bytesIn/bytesOut`）：

| `moved` | 含义 | 结论 |
|---|---|---|
| `true` | 字节确实穿过了本机这条隧道 | 降级为 warn：「通，出口不同通常是你代理的上游节点」 |
| `false` | 计数器没动 | 维持 bad：「没连到你的电脑」（端口上确实蹲着别人） |
| `null` | 没传 `tunnelId` | 维持原来的严格判定 |

**为什么计数器比出口 IP 硬**：出口 IP 是间接证据，会被代理链、负载均衡、规则分流
打坏；计数器是本地事实——字节要么穿过来了，要么没穿过。

| E12 | **拿 SSH channel 当 `pipeline` 的终点** | `pipeline` 会等 Duplex 的可读侧也结束，而可读侧要等远端退出、远端又等我们的 EOF → 死锁。改用 `.pipe()` 链 + 显式转发 error |

| E14 | **tar 下载没剥顶层目录名** | `tar -cf - -C <parent> <base>` 的每条 entry 都带 `<base>/` 前缀，直接解到目标会多套一层目录。要在 entry 回调里剥掉，和上传的语义对齐 |
| E15 | **tar-stream 的 `pack.entry()` 不 await 回调就写下一条** | pack 是严格串行的，不等上一条被读走就写会抛错或丢数据。**先 pipe 到下游**再写（否则回调永远不来，死锁） |

| E20 | **改 `src/preload/index.ts` 不会热更新** | 渲染层立刻拿到新代码去调新方法，窗口里跑的却还是旧 preload → 一律 `window.hpc.xxx is not a function`。**不是 bug，是没重启**。踩过两次（`dryRunJob`、`readJobLog`），所以做了版本握手：`src/shared/api-version.ts` 的 `PRELOAD_API_VERSION` 由 preload 挂到 `window.hpc.apiVersion`，渲染层启动时比对，不一致就在顶部顶一条横幅（`lib/preload.ts` 的 `preloadStale()`）。**加/改/删任何 `window.hpc` 方法都要把这个数字 +1** |
| E21 | **`src/preload/index.d.ts` 在 node 侧 tsconfig 里看不见** | 它和 `index.ts` 同名，TypeScript 会当成后者的声明输出而跳过，列进 `include` 也没用。依赖它里面全局 `PlainError` 的模块，在同名文件旁边就编不过——所以 `lib/preload.ts` 自己声明了结构子集 `IpcError` |
| E22 | **`scontrol show job --json` 的字段类型不统一** | `job_id` 是**数字**（不是字符串）；`submit_time`/`start_time`/`end_time` 是**裸 epoch 秒**；而 `cpus`/`node_count`/`time_limit`/`memory_per_node` 又是 `{set,infinite,number}` 包装。混着写是这类解析最容易出错的地方。另外作业被清理时命令**仍然 exit 0**，只是 `jobs: []` + `warnings: ["Zero jobs to dump"]`——不是错误，但绝不能返回空数据冒充成功 |
| E23 | **`--gres=gpu:N` 不带型号会被 scir 扩展拒绝** | 实测 `sbatch --gres=gpu:1` → `tres format not match: gres:gpu:1 (scir extension)!`，必须写成 `--gres=gpu:a100-pcie-40gb:1`。**`--test-only` 能拦住这个**（和配比限制不同）。`explainSbatchError()` 已覆盖；表单在"任意型号 + 卡数>0"时给黄条提醒，但**只提醒不阻止**——别的集群允许不写型号 |
| E24 | **`tail -f` 不能走 exec 的信号量** | 信号量是给"请求-响应"型命令用的（默认并发 5）。`tail -f` 永不结束，占一个槽就是永久少一个，开三个跟随之后所有 exec 都排队，表现为"界面卡住不刷新"。这类长连接必须独立开通道（`Session.tail`）。另外**必须用 `StringDecoder`**：一个汉字 3 字节，chunk 边界随时把它劈开，直接 `chunk.toString('utf8')` 会在中文日志里随机出现 `�` |
| E25 | **`Unable to bind to 127.0.0.1:55555` 不含原因，别拿它当诊断** | 这句是 **ssh2 自己拼的字符串**（`node_modules/ssh2/lib/client.js:1347`）。服务端对 `tcpip-forward` 只回一个 `SSH_MSG_REQUEST_FAILURE`，**协议里没有携带原因的地方**——它的真实含义只是"服务端拒绝了"。第一版据此断言"多半是你手敲的 ssh -R 还开着"，真机一查全错：`127.0.0.1` 在登录节点上**是全体用户共享的一张网卡**，占着 55555 的是另一个账号。要查所有者只能读 `/proc/net/tcp` 的 uid（非 root 可读）：端口是 4 位大写十六进制，只认 `0A`(LISTEN) 状态。见 `domain/port-owner.ts` |
| E26 | **观测代码会反过来搞坏被观测的东西** | 命令记录挂在 `Session.exec` 的收尾路径上，那里一旦抛异常，一条正常跑完的命令就会变成失败。所以三处都要 try/catch：`TraceStore.push` 整体、每个订阅者单独、`Session.emitTrace` 包住回调。有测试断言"onTrace 抛异常时 `exec` 仍返回 code 0"。同理，记录必须**有界**（200 条 + 单条 16 KB），否则轮询跑一天就把内存吃光 |
| E27 | **"spawn 不到就 return"的测试等于没测** | 为了验收"生成的 shell 脚本没有 `do;` 这种语法错"，一开始写的是 `spawnSync('bash', ['-n'])`，失败就 `if (check.error) return`。结果本机沙箱里 `spawnSync('bash')` 直接 **EBUSY**，那条用例一直是"绿的空壳"——`do;` 的 bug 照样能过。现在改成**检查真正会出错的结构特征**：不允许 `/\bdo\s*;/`、`do`/`done` 计数相等、引号成对。另外凡是"远端拼命令、本机解析"的活，都让远端只负责 `grep` 出原文，解析放 JS（`parseProxyLine`），这样才测得动 |
| E28 | **临时端口段里的端口会被"路人"抓走，而且没有 LISTEN** | 实测：55556 连续两次 `Unable to bind`，但 `ss -ltn` 里什么也没有。查 `/proc/net/tcp` 发现是一对 `127.0.0.1:28887 ↔ 127.0.0.1:55556` 的 **ESTAB**，属于另一个 uid——别人的**客户端**把源端口显式绑到了 55556（或 self-connect）。本集群 `ip_local_port_range = 32768 60999`，**55556 就在这个区间里**，任何人的出站连接都可能临时征用它，几秒后又消失。三个后果：① 判"端口被占"不能只看 `0A`(LISTEN)，要看是否有以该端口为**本地端口**的任意状态条目；② 探测到空闲 ≠ bind 时仍空闲，所以退端口要试多个候选；③ **固定端口应该选 32768 以下**（如 21056），而不是 5xxxx——同一天里 21056 一次成功、55556 两次失败 |

## 6. 后续开发上下文

### 6.1 用户与场景

- Windows 用户，**不做跨平台**
- 自用为主，但错误文案按"可以发给同学"的标准写
- 计划放 GitHub 当作品集 → **代码里不能有内网地址、用户名、集群路径**
- 全 AI 辅助开发，**不需要解释编程基础概念**，直接给实现

### 6.2 优先级（明确表态过）

**运行效率与响应速度 > 可视化丰富与界面美观。**

这条已经体现在技术选型里（Electron 的取舍、uPlot 而非 ECharts）。但注意：这个项目的"慢"不来自框架，来自网络和传输策略——优化要花在对的地方。

### 6.3 已确认的产品决策

| # | 决策 | 含义 |
|---|---|---|
| 1 | **乙** 混合形态 | 桌面做启动器，主力全屏分区，工具类浮动窗口 |
| 2 | **乙** 批处理 + 交互式 | 除提交作业外，还要能进终端调试（xterm.js + ssh2 shell，不用 node-pty） |
| 3 | **乙** 多 profile 架构 | 连接层留抽象，UI 只露一条 |

### 6.4 工作方式

- 用户偏好**先方案、后实现**，且要看得到取舍理由
- 用户对"不清楚"的问题会直说，此时**不要继续追问**，而应把不确定的依赖从关键路径上摘掉（降级职责 / 保守处理 / 运行时探测）
- 改代码前先确认改动落在哪个层：解析错→`adapters`，计算错→`domain`，卡顿→`transfer` 或 `renderer`

### 6.5 改代码前的五条自检

1. 这段逻辑碰网络了吗？碰了就该在 `main/`，不该在 `renderer/`
2. 解析失败时会静默返回空吗？**必须是明确的失败 + 原文**
3. 有新信息发 IPC 给 UI 吗？**合并到 100ms 一次**
4. 远程路径拼接用的是 `/` 吗？
5. 引入了原生模块吗？**没有例外，不要引**
