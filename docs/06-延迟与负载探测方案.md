# 跳板机延迟与 sshd 负载探测（2026-11-13 已实施，待验收）

> 目标：按需测一台跳板机的连接耗时，并且**把「网络慢」和「sshd / 登录节点忙」分开说**。
> 只给一个「延迟 1.2s」是没用的——用户会以为是网速，实际上多半是节点太忙。

## 1. 测量：一次连接，四段计时

```
t0 ──── tcp ──── sshd ──── auth ──── exec
        │         │          │         │
       握手      版本串      KEX+认证   echo 往返
      （网络）  （sshd 应答）（节点负载）（用起来卡不卡）
```

| 段 | 取点 | 代表什么 |
|---|---|---|
| `tcpMs` | `net.connect` 的 `connect` 事件 − t0 | 纯网络往返 |
| `sshdMs` | socket **首个 `data`**（`SSH-2.0-...`）− tcp 完成 | sshd 接受连接的速度 |
| `authMs` | `client` 的 `ready` − 首字节 | 密钥交换 + 认证（**登录节点忙不忙就看这段**） |
| `execMs` | `exec('echo')` 往返 | 真正用起来的手感 |

### 实现要点

1. **自己建 socket，再注入给 ssh2**：`new Client()` 不暴露「收到版本串」的时刻，
   但 `ConnectConfig.sock` 允许传入自定义流。所以先用 `net.connect` 建连、
   在 socket 上记首字节时刻，再 `client.connect({ ...authMaterial, sock })`。
   （已确认 `node_modules/ssh2` 的 `cfg.sock` 分支存在。）
2. **必须是一次性连接，不能走 `ConnectionPool`**：池按 `profile.id` 复用会话，
   复用的话测出来是 0.2ms，毫无意义。
3. **复用 `loadAuthMaterial(profile)`**（`src/main/ssh/session.ts` 第 1237 行，
   目前未导出）——把它改成 `export`，不要在探测里再写一份私钥/密码加载逻辑，
   否则「密码在钥匙串里」那套解析会分叉。
4. **主机指纹：未知主机不写入**。测速顺手改变 trust 状态是意外副作用，
   遇到未知主机直接返回 `unknown-host`：「先在主界面正常连一次」。
   指纹**不匹配**则直接失败，并原样带上两边指纹。
5. **1 次采样**（用户拍板）。原打算 3 次取中位数——20s 级超时下 3 次最坏要等一分钟，
   失败场景体验太差。抖动问题改用「结果缓存 + 手动重测」来消化：多测几次看趋势，比一次测 3 遍更直观。

## 2. 判读：把毫秒变成一句人话

纯函数 `judgeLatency(sample)`，阈值集中在一处（初值，可调）：

| 指标 | 正常 | 警告 | 结论 |
|---|---|---|---|
| `tcpMs` | < 80 | > 150 | 网络慢 |
| `sshdMs` | < 120 | > 300 | sshd 应答慢 |
| `authMs` | < 500 | > 1200 | **跳板机忙**（登录节点负载） |
| `execMs` | < 150 | > 400 | 交互会顿 |

输出形如：

```
跳板机忙
登录用了 1.2s，其中认证 1.1s、网络只有 12ms —— 不是网速问题，是这台节点在忙。
```

**「sshd 负载」必须单独成句**，这是这个功能存在的理由。
只显示 `1.2s` 的话，用户会去查自己的宽带。

## 3. 展示位置

| 位置 | 显示 |
|---|---|
| 标题栏切换器，每行 | `● 12ms · 1.2s`（网络 · 登录），悬停出分解 |
| 切换器底部 | 「测一下」按钮 + 「上次：3 分钟前」 |
| 设置页 | 完整四段分解 + 判读结论 |

两台同 IP 的跳板机（本项目的 2223 / 2222）在这里特别有价值：
**网络段必然接近，差异全在 `authMs`** —— 一眼就能挑出不忙的那台干活。

## 4. 触发策略（防刷日志）

| 规则 | 原因 |
|---|---|
| **只手动触发**，不轮询 | 每次探测都是一次真实 SSH 登录，会留下 auth 日志 |
| 同一时刻只允许一个探测 | 避免同时给多台测，把登录节点打出一串并发会话 |
| 结果缓存 5 分钟 | 切回面板不重测 |
| 不放启动页 | 启动时连接池里已有连接，测出来不准 |

### 超时：分段，而不是一个总闸

总预算 **25 秒**（用户定：校网/VPN/首次连接确实可能慢，5 秒会误杀正常的登录），
但**每一段各有自己的上限**，目的是让"卡住了"这件事尽早、尽量具体地暴露出来：

| 阶段 | 上限 | 超时说明 |
|---|---|---|
| TCP 握手 | **5s** | 网络不通/防火墙丢包，通常 1–2 秒就能确定，不该陪着等 |
| sshd 应答 + 认证（`ready`） | **15s** | 登录节点过载、密钥交换慢都发生在这一段 |
| `exec('echo')` | **5s** | 登录成功但 shell 初始化卡住（`.bashrc` 里有慢命令） |

三段上限之和 = 25s > 20s，所以**另外有一个 20s 的全局截止**：任何一段跑完时若已超总预算，直接收工。

**关键：超时也要带数据回来。** 认证在 15s 时超时，`tcpMs`/`sshdMs` 是有效的，
判读结论应是「**认证超时**（网络 12ms 正常，卡在登录）」，而不是一句「连接失败」。
只报"失败"会让人分不清是网线掉了还是节点挂了。

## 5. 数据契约

```ts
interface ProfileLatency {
  profileId: string
  tcpMs: number | null
  sshdMs: number | null      // 首字节 − TCP 完成
  authMs: number | null      // ready − 首字节
  execMs: number | null
  totalMs: number | null     // ready − 开始
  samples: number
  at: number
  /**
   * 卡在哪一段。有值说明是**超时**而不是"连不上"——
   * 前面几段的数字仍然有效，判读要据此说"卡在登录"而不是"连接失败"。
   */
  timedOutAt?: 'tcp' | 'sshd' | 'auth' | 'exec'
  verdict:
    | 'ok' | 'network-slow' | 'sshd-busy' | 'auth-slow' | 'exec-slow'
    | 'timeout'          // 具体卡在哪段见 timedOutAt
    | 'unreachable' | 'auth-failed' | 'exec-failed' | 'unknown-host' | 'hostkey-mismatch'
    | 'unknown'
  headline: string
  detail: string
  error?: string
}
```

失败必须**分类**，不能一句「连接失败」：

- `unreachable` → 网络/端口不通
- `auth-failed` → TCP 通了但认证失败（密钥、用户名、权限问题；带上平台原话）
- `exec-failed` → 登录成功但不能执行命令（少见的 shell/权限问题）

## 7. 明确不做

- **不做后台轮询**（会刷 auth 日志，可能触发 `MaxStartups`）
- 不测**集群内部**节点间延迟（那是另一个功能）
- 不测带宽（会把链路占满，影响正在跑的作业）
- 不把探测结果写进 `profiles.json`（它是瞬时观测，不是配置）

## 8. 风险

| 风险 | 处理 |
|---|---|
| 3 次采样 = 3 条登录记录，管理员可能觉得吵 | 采样次数做成常量，默认 3；必要时降 1 |
| `MaxStartups` 限制下并发建连被拒 | 全局串行 + 5 分钟缓存 |
| 测速被误当成「健康检查」，用户以为会自动更新 | 界面上不显示时间戳就不显示数字，明确写「上次：x 分钟前」 |
| 密码认证下频繁重连触发失败锁定 | 探测只做只读认证，不会产生失败尝试；失败也不会自动重试 |
