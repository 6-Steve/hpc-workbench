# 目录增量同步（2026-11-16 阶段 1 已实施，待验收）

> 目标：把「整个目录重传」换成「只传变了的文件」。
> **这个功能的危险不在技术，在语义**——"同步"在别人的工具里有六种意思，
> 其中一种会删掉你集群上的实验结果。

## 1. 目标与非目标

**做**

- 指定一个本地目录 ↔ 一个远端目录，比对后只传**新增**和**需要更新**的文件
- 传输前给出预览：`新增 12 · 更新 3 · 跳过 1,240 · 冲突 2`，冲突可展开看清单
- 大文件的半截传输可续传（阶段 2）

**不做**

- **不删除目标端多余的文件**（不做镜像/`--delete` 语义）
- 不覆盖"目标比源更新"的文件（默认跳过并计数，可强制）
- 不跟随符号链接（跳过并警告）
- 不处理权限位/属主/ACL（只传内容）
- 不做双向同步（那需要变更日志或版本库，是另一个量级）

## 2. 现状：三条现成的路可以直接复用

| 已有 | 位置 | 怎么用上 |
|---|---|---|
| **计划 → 确认 → 入队** | `transfer/planner.ts` → `service.ts` → `queue.ts` | 增量同步就是"生成一份只含变更项的计划"，`start()` 一行不用改 |
| **计划缓存 10 分钟** | `service.ts` `this.plans` | 预览和真正执行之间不重新扫描（大目录扫一次很贵） |
| **半截文件记录** | `sftp.ts` `PartialTransferInfo`（`.part` + `bytesDone`） | 续传的 offset 已经有现成的来源 |

所以这次的改动集中在 **planner 的一个新分支 + 一个纯函数模块 + 预览界面**。

## 3. 语义：三条铁律

| # | 规则 | 违反的后果 |
|---|---|---|
| 1 | **绝不删除目标端的文件** | 一次误操作删掉 `results/` 是灾难性的；删除必须是另一个独立动作 |
| 2 | **目标更新时不覆盖**（`mtime_target > mtime_source + 2s`） | 集群上刚改过的脚本被本地旧版本盖掉，且**无法从回收站找回** |
| 3 | **目录不参与"覆盖"** | 已有规则（`service.start()` 会拒绝），同步只对**文件**动手 |

> 一句话：**这个功能只会增加或更新，不会减少。** 界面上也要这么写，不要用"同步"两个字含糊过去。

## 4. 比对规则

以「源 → 目标」方向为准（上传时源是本地，下载时源是远端，规则完全对称）：

| 源 | 目标 | 判定 | 动作 |
|---|---|---|---|
| 文件 | 不存在 | `new` | **传** |
| 文件 | 文件，size 不同 | `update` | **传** |
| 文件 | 文件，size 相同，`|Δmtime| ≤ 2s` | `same` | 跳过 |
| 文件 | 文件，size 相同，`Δmtime > 2s` | `update` | **传** |
| 文件 | 文件，`mtime_target > mtime_source + 2s` | `conflict` | **跳过**（默认），可勾选"覆盖更新的目标" |
| 文件 | **目录** | `conflict` | 跳过 + 警告（不能拿文件覆盖目录） |
| 目录 | 文件 | `conflict` | 跳过 + 警告（同上） |
| 目录 | 不存在 | — | 建目录（随第一个文件隐式创建） |
| — | 存在但源里没有 | `orphan` | **只统计，不处理**（清单里显示"N 个目标端独有的文件未改动"） |

**为什么用 size + mtime 而不是 hash**：算 hash 要把两边全读一遍——本地磁盘还好，
远端等于把几 GB 数据经 SSH 拉回本地，正是要省掉的那笔开销。
代价是**"同一秒内改过且大小不变"会漏**（见风险表），所以提供"强制全部重传"的开关。

**为什么容差是 2 秒**：NTFS 与 ext4 的 mtime 精度都够，但**经 tar/SFTP 往返会掉精度**，
而且用户的机器与集群之间可能有秒级偏差。2 秒能吸收这些噪声。

## 5. 数据采集

### 5.1 远端（一次 `find` 拿全树）

```bash
find <dir> -mindepth 1 \( -type f -o -type d -o -type l \) \
  -printf '%y\t%s\t%T@\t%P\0' 2>/dev/null
```

| 片段 | 作用 |
|---|---|
| `-mindepth 1` | 不含根目录自己 |
| `-printf '%y\t%s\t%T@\t%P\0'` | 类型 / 字节数 / mtime(秒.毫秒) / **相对路径** |
| `\0` 结尾 | 文件名里有空格、制表符、换行、中文都安全 |
| `2>/dev/null` | 无权限的子目录不中断整次扫描（但要在警告里说"有目录读不到"） |
| `%P` 而不是 `%p` | 直接拿到相对路径，和本地 walk 的结果天然对齐 |

**解析必须按 `\0` 切**，绝不能 `split('\n')`——中文和空格都不会出问题，
但文件名里真的可以有换行（正规但少见），按行切会错位。

### 5.2 本地

`readdir({ withFileTypes: true })` 递归；`lstat` 取 size/mtime；**`isSymbolicLink()` 直接跳过并记入 `unsupported`**。

### 5.3 规模上限

- 单次扫描上限 **50,000 条**（超过就截断并警告"只比对了前 5 万项，建议改用整包传输"）
- `find` 超时 **30 秒**（NFS home 上可能很慢），超时降级为"不做增量，走整包"

## 6. 什么时候增量反而更慢

**每次 SFTP 传输都有一次往返**（建 channel、open、write、close）。2000 个小文件比 tar 一个流慢一个数量级。

所以加一条自动建议：

```
变更文件数 > 500   或   变更文件占比 > 40%
  → 不推荐增量
  → 提示："这次变动太多（620/1500），整包传输更快"，并给"改为整包"按钮
```

阈值放常量里（`SYNC_SUGGEST_FULL_RATIO = 0.4`、`SYNC_SUGGEST_FULL_COUNT = 500`），别散在界面里。

## 7. 阶段划分

| 阶段 | 内容 | 本次是否做 |
|---|---|---|
| **1** | 比对 + 只传变更文件（逐文件走现有 SFTP 单流） | ✅ 本期 |
| **2** | 大文件断点续传（`.part` + offset） | 设计已给，代码下一期 |
| **3** | 变更集走 tar 一条流（万级小文件提速） | 以后再说 |

### 阶段 2 的设计（先写下来，避免以后走偏）

- 落盘目标先写 `<name>.part`，完成后再 `rename`（现有实现已经是这个行为）
- 下次同步时：若目标侧存在同名 `.part`，取其大小作为 `offset`，用
  `session.sftp().open(path, 'r+')` + `write(buffer, offset)` 续写
- **`.part` 的 mtime 不可信**，比对阶段一律把 `.part` 当作"待续传"，不参与 `same` 判定
- 取消后续传不自动开始：要在预览里明确显示「1 个文件待续传（已传 380MB/1.2GB）」

## 8. 交互

### 8.1 入口

文件页选中一个**目录** → 右键 → **「同步到对面…」**（上传：本机目录 → 远端当前目录；
下载：远端目录 → 本机当前目录）。

> 只对目录开放。单个文件也有"覆盖/跳过"的现有流程，不需要第二套语义。

### 8.2 预览（这一步是功能的一半）

```
同步 results/ → 集群 ~/exp/results

  新增 12    更新 3    未变 1,240    冲突 2    待续传 0

⚠ 2 个冲突（目标比本地新），默认跳过
   gpu.sh          目标 11-16 18:03  >  本地 11-15 09:12
   run_eval.py     目标 11-16 20:41  >  本地 11-14 10:00
                                [展开看全部]

☐ 覆盖目标端更新的文件（谨慎）
☐ 强制全部重传（忽略 size/mtime）
```

按钮：`开始同步（15 个文件）` / `取消`

### 8.3 执行中

复用现有 `TransferBar` 与队列。15 个任务可以接受；超过 500 个时在第 6 节就会被劝退。

**不给批次/折叠视图**（本期）：队列本来就是"一条条任务"，硬折叠需要一个 `batchId`
贯穿队列与界面，收益不抵改动面。等真的出现"每天同步 300 个文件"的用例再说。

### 10.1 `parseFindOutput`

| 文件名含换行 | **不按行切**，解析正确 |
| 空输出 | `[]`（不抛） |
| 少字段的脏行 | 跳过并计入 `warnings` |

### 10.2 `diffTrees`

覆盖第 4 节表格的 8 种组合，每格一条用例。重点两条：

- 目录 vs 文件 → `conflict`，**绝不**产生一个会覆盖目录的传输项
- 目标更新 → `conflict`，且 `overwriteNewer=false` 时不进 `toTransfer`

### 10.3 阈值

| 用例 | 期望 |
|---|---|
| 600 变更 / 1500 总 | `suggestFull: true`（数量超 500） |
| 500 变更 / 2000 总 | 占 25% → `suggestFull: false`（数量正好 500 不算超） |
| 300 变更 / 600 总 | 占 50% → `suggestFull: true` |
| 扫描超 5 万条 | 截断 + 警告 |

## 11. 风险

| 风险 | 对策 |
|---|---|
| **同秒内改动且大小不变 → 漏传** | 预览里给「强制全部重传」；文档写明这是已知边界 |
| 远端 `find` 不支持 `-printf`（非 GNU） | 解析失败即降级为整包，并提示"这台机器的 find 不支持增量比对" |
| NFS home 上 `find` 很慢 | 30 秒超时 → 降级整包 |
| 用户以为"同步"= 镜像，期待多余文件被删 | 按钮文案写「同步（只增不删）」，预览里显示"N 个目标独有文件未改动" |
| 冲突被一路跳过，用户以为传完了 | 预览必须显示冲突数；执行完的提示里再报一次"跳过 2 个冲突" |
| 2000 个小文件把队列刷爆 | 第 6 节的阈值建议 + 500 上限硬提示 |
| 路径穿越（远端 `%P` 里出现 `..`） | 拼接后校验前缀必须是目标根目录 |
